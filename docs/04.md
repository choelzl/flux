# 04 — Target Architecture (Proposal)

Codename **Flux**. This is a proposal, not a decision. Argue with it.

> **Amended by [00 — Phase 0 Decision Record](00-decisions.md):** target domain is full SoC-level
> DSE, not DNN-accelerator-only (D1); full hardware-generation closure is in scope, superseding
> §11's "conformance-checking only" (D2); a new Knowledge/Context layer is added (D3). Read §3, §10,
> and §11 below through those decisions.

---

## 1. Design principles

1. **Contracts over monoliths.** The IR and the evaluator ABI are the product. Everything else is
   a replaceable implementation behind them.
2. **Every number carries its provenance and its uncertainty.** A result without a calibration id
   and a confidence interval is a bug.
3. **Fidelity is a budget, not a mode.** Callers state what they can afford; the framework picks
   the rung and escalates when it matters.
4. **Reuse aggressively at the edges, own the middle.** Don't rewrite Ray, Accelergy plug-ins,
   Verilator, or Hammer. Do own the IR, the contract, the calibration store, and the search core.
5. **Agents are a first-class caller, not an add-on.** Every capability is available as a typed
   function, an MCP tool, and a CLI — from the same definition.
6. **The evaluator is never writable by the thing being evaluated.** Structural isolation, per
   CHIA's containerisation model.
7. **Fast path stays fast.** A single mapping evaluation must be sub-millisecond and allocation-free
   in the hot loop, or agentic-scale search is impossible.

## 3. L2 — The Flux IR

Three orthogonal documents. Orthogonality is the whole point: today they are entangled everywhere.

### 3.1 Workload IR

Not a replacement for ONNX or MLIR — a **lowered, DSE-oriented view** produced from them.

```yaml
workload:
  id: llama3-8b/decode/layer0
  provenance: {source: onnx, file_sha256: ..., importer: flux-onnx@0.3}
  tensors:
    - {name: Q, rank: [B,H,S,D], dtype: fp8_e4m3, scale: per_head_group}
    - {name: KV, rank: [B,H,S_ctx,D], dtype: int8, residency: persistent, growth: append}
  ops:
    - id: attn.qk
      kind: einsum                      # affine core, always present
      expr: "b h s d, b h t d -> b h s t"
      bounds: {b: 1, h: 32, s: {dyn: [1,1]}, t: {dyn: [1, 131072]}, d: 128}
      sparsity: {pattern: causal, density_model: structured_mask}
    - id: moe.route
      kind: data_dependent               # explicitly outside the affine core
      semantics: {top_k: 2, experts: 8, distribution: measured@corpus/moe-v1}
  phases: [prefill, decode]              # first-class, with distinct shapes
  dynamism:
    symbolic_dims: [s, t]
    distributions: {t: empirical@corpus/sharegpt-lens}
```

Key decisions:
- **Einsum/affine core** for everything that is affine, matching the nested-for-loop tradition —
  this preserves compatibility with ZigZag and Timeloop semantics.
- **Explicit escape hatch** (`data_dependent`) with an attached *distribution* rather than a fixed
  shape. This is how MoE, dynamic sequence length, and speculative decoding get modelled without
  pretending they're static. Closes G5.
- **Tensor lifetime and residency** are IR-level, not inferred. This is how KV cache becomes
  modellable.
- **Symbolic dimensions with empirical distributions**, so a result can be a distribution over a
  workload corpus rather than a single number.

### 3.2 Architecture IR

```yaml
architecture:
  id: my-npu/v3
  tech: {node: n5, pdk_class: commercial, vt_flavors: [svt,lvt]}
  hierarchy:
    - level: dram
      class: memory
      attrs: {type: hbm3, channels: 8, bw_gbps: 819}
      estimator_hints: {plugin: dramsim-lite}
    - level: gbuf
      class: memory
      attrs: {size_kb: 4096, banks: 16, ports: {r: 2, w: 1}, width_bits: 512}
    - level: pe_array
      class: compute
      attrs: {dims: {X: 32, Y: 32, Z: 4}, mac: {dtype: [int8,fp8], throughput: 1}}
      interconnect: {X: multicast, Y: systolic, Z: broadcast}
  interconnect:
    noc: {topology: mesh_4x4, flit_bits: 256, model: flux-noc@0.1}
  constraints:
    - {kind: area_mm2, max: 12.0}
    - {kind: tdp_w, max: 15.0}
    - {kind: thermal, model: 3d-ice, max_junction_c: 105}
```

Key decisions:
- **Component classes + attributes + actions**, exactly the Accelergy pattern, generalised beyond
  energy so the same plug-in mechanism serves area, leakage, latency, and thermal.
- **Constraints are part of the architecture document**, machine-checkable and independent of the
  cost model. This is a direct anti-reward-hacking measure (G14): the validity checker enforces
  them even when the cost model has no opinion.
- Thermal and NoC have declared slots even before we have good models — so adding them later isn't
  a schema break.

### 3.3 Mapping IR

The hard one, because it must be a **superset** of what existing tools express, or we recreate the
lock-in we're trying to kill.

```yaml
mapping:
  id: ...
  for_op: attn.qk
  # per-operand loop nests: this is ZigZag's uneven mapping, generalised
  operands:
    Q:  [{level: gbuf, loops: [{dim: h, size: 8, order: 0}, ...]},
         {level: reg,  loops: [...]}]
    KV: [{level: gbuf, loops: [...]}]        # deliberately different from Q
    O:  [{level: gbuf, loops: [...]}]
  spatial:
    - {dim: h, array_dim: X, size: 32}
    - {dim: d, array_dim: Y, size: 32}
  fusion:                                     # this is Stream's contribution
    group: [attn.qk, attn.softmax, attn.av]
    tile: {s: 64}
    granularity: fine
  placement:                                  # multi-core / chiplet
    core: cluster0.core3
  compatibility:
    expressible_in: [flux, zigzag]
    not_expressible_in: [timeloop]            # ← explicit, machine-readable
    reason: uneven_operand_blocking
```

The `compatibility` block is small and does a lot of work: it makes representation lock-in
**visible and queryable** instead of a footnote in a validation section. A search can ask
"restrict to mappings expressible in Timeloop" when cross-validation is required, and range freely
otherwise.

### 3.4 Identity and hashing

Every IR document is canonicalised and content-addressed. `arch_hash`, `workload_hash`,
`mapping_hash` are the cache keys for everything downstream (G9) and the lineage keys for
everything upstream (G10).

## 4. L4 — The Evaluator ABI

### 4.1 The call

```python
Result = evaluate(
    workload : WorkloadRef,        # hash or inline
    arch     : ArchRef,
    mapping  : MappingRef | None,  # None ⇒ evaluator may choose (declares that it did)
    budget   : Budget,             # wall_clock_s, usd, fidelity_floor
    metrics  : set[Metric],        # latency, energy, area, power, edp, temp_max, ...
) -> Result
```

### 4.2 The return — this shape is the contract

```python
Result:
  metrics: {latency_cycles: Estimate, energy_pj: Estimate, area_mm2: Estimate, ...}
  # Estimate = {value, ci_low, ci_high, unit, method: analytic|simulated|measured}

  validity:   {ok: bool, violations: [Constraint], checker_version: str}
  domain:     {in_domain: bool, distance: float, nearest_calibration: id}
  bottleneck: {limiter: memory|compute|noc|dependency,
               per_level_utilisation: {...},
               roofline: {ai, peak, achieved},
               top_costs: [...]}                 # structured explanation, not prose
  provenance: {evaluator: "zigzag@3.1.0", calibration: "cal-2026-07-a",
               inputs: {workload_hash, arch_hash, mapping_hash},
               seed, wall_clock_s, usd_cost}
  escalation: {recommended: bool, next_rung: "verilator", reason: "ci width > 25%"}
```

Four things here are new relative to every existing tool:
- `Estimate` carries an interval, not a scalar (G2).
- `domain.in_domain` says whether the model is extrapolating (G2).
- `bottleneck` is **structured**, so both a human and an agent get *why*, not just *what* — this is
  the Explainable-DSE insight made into an interface guarantee (G4).
- `validity` is computed by an **independent checker**, not by the cost model, and is the primary
  anti-reward-hacking mechanism (G14).

### 4.3 Batch mode is mandatory

```python
evaluate_batch(candidates: list[Candidate], budget) -> list[Result]
```

Agentic and evolutionary search submit 10³–10⁵ candidates at a time. A one-call-per-candidate
interface makes the Python/serialisation overhead dominate. Batch + native core + content-addressed
memoisation is how G9 gets fixed.

### 4.4 Backends at launch

| Backend | Rung | Notes |
|---|---|---|
| `flux-native` | ~µs–ms | Rust core, dense affine + basic sparsity, our own |
| `zigzag` | ms | adapter; gives uneven mapping + IMC immediately |
| `stream` | ms–s | adapter; multi-core + layer fusion |
| `timeloop+accelergy` | ms–s | adapter; cross-validation oracle + energy plug-ins |
| `sparseloop` / `cimloop` | ms–s | adapters for sparsity / CiM |
| `verilator` | min–h | via CHIA node |
| `firesim` | h | via CHIA node |
| `hammer-synth` | h | PPA ground truth via CHIA node |

**Adapters, not forks.** Each adapter is a translation from Flux IR to the tool's native config
plus a parse of its output back into `Result`. Where a mapping is inexpressible, the adapter fails
loudly with `not_expressible_in` — never silently approximates.

## 5. L3 — Calibration and the fidelity ladder

The component nobody has, and the reason to build this.

```
                  ┌──────────────────┐
  candidate ────► │ Rung selector    │◄── budget, required_confidence, pareto_relevance
                  └────────┬─────────┘
                           ▼
              ┌───── analytic (flux/zigzag/timeloop) ─────┐
              │                                             │
              │   Estimate + domain check                   │
              └────────────────┬────────────────────────────┘
                               ▼
                    ci_width > threshold  OR  out_of_domain
                    OR on current Pareto front
                               │ yes
                               ▼
              ┌── coarse-grain sim (SystemC, evaluators/systemc) ──┐
              │   fast functional correctness + timing pre-check    │
              └────────────────┬────────────────────────────────────┘
                               ▼
              ┌───── RTL sim (Verilator) / synth (Hammer) ──┐
              │   measurement → residual                     │
              └────────────────┬────────────────────────────┘
                               ▼
                    ┌────────────────────────┐
                    │ Calibration store      │
                    │  residual model per    │
                    │  (arch class, node,    │
                    │   op class, regime)    │
                    │  → tightens future CIs │
                    └────────────────────────┘
```

- **Active-learning escalation.** Spend high-fidelity budget where it changes the answer: points on
  or near the Pareto front, points where the analytic CI is wide, points out of validated domain.
- **Residual models** are fitted per regime and fold back into the CIs, so the framework gets more
  confident *where you have measured* and stays honest elsewhere.
- **Drift detection in CI.** Nightly re-evaluation of the calibration corpus; a model update that
  moves residuals beyond tolerance fails the build. This is what converts one-off paper-time
  validation into a maintained property (G2).
- **Holdout discipline, borrowed from CHIA.** A portion of the benchmark corpus is never visible to
  the search or to any agent — the mechanism that exposed overfitting in CHIA's gem5 alignment
  study. Enforced by the store, not by convention.
- **Mixed-grain simulation** ([00-decisions.md D5](00-decisions.md)): a coarse-grain rung between
  analytic estimates and cycle-accurate RTL-sim — real functional correctness plus a timing
  estimate at a fraction of RTL-sim's compile+simulate cost, escalating to the RTL rung for the
  authoritative number. Where a design's schedule is fully static and data-independent (no
  arbitration, no variable-latency memory), the coarse-grain estimate can be exact, not merely
  approximate — proven, not assumed, for `evaluators/systemc`'s reference design.

## 6. L5 — Search

```python
class Strategy(Protocol):
    def propose(self, state: SearchState, k: int) -> list[Candidate]: ...
    def observe(self, results: list[Result]) -> None: ...
    def done(self) -> bool: ...
```

Strategies ship in-tree: exhaustive, LOMA-style loop-order enumeration, simulated annealing,
CP/MIP (CoSA-style), gradient descent on a differentiable surrogate (DOSA-style), Bayesian,
evolutionary (via SkyDiscover/AlphaEvolve/OpenEvolve as CHIA already integrates), and LLM-agent.

Two shared services make them all better:
- **Warm start.** Every strategy can query the Result Store for prior results on similar
  `(workload, arch)` pairs. Nobody starts from zero twice.
- **Budget awareness.** `Budget` includes USD and wall-clock. Strategies report cost-to-quality
  curves, so "best design per dollar" becomes measurable (G16) — the metric CHIA's cost tables
  imply but no DSE tool exposes.

## 7. L6 — Flows and the agent surface

### 7.1 Don't rebuild orchestration

CHIA already provides distributed execution, heterogeneous resource matching, containerised
isolation, fault tolerance, subprocess tracking, profiling, and caching/bypass, on Ray. Rebuilding
any of that is pure waste.

**Flux ships CHIA library nodes**: `flux_evaluate`, `flux_search`, `flux_calibrate`,
`flux_conformance_check`, plus Dockerfiles for each evaluator backend. Contribute them upstream.
Two of the four are real now ([00-decisions.md D5](00-decisions.md)) — genuine
`@ChiaFunction()`s in `flows/chia_nodes/`, dispatched through a real local Ray instance:
`flux_evaluate` (`tests/integration/test_chia_flux_evaluate_live.py`) wraps the same evaluator
registry `flux eval` uses; `flux_search` (`tests/integration/test_chia_flux_search_live.py`)
wraps `search/architecture`'s screen→rank→escalate DSE loop, verified with `flux_search` itself
dispatched as one Ray task that internally dispatches more Ray tasks (nested dispatch, not
assumed to work from Ray's docs). `flux_calibrate` and `flux_conformance_check` don't exist yet.

### 7.2 One definition, three surfaces

```python
@flux_tool(resources="cpu:4")
def evaluate_design(arch: ArchRef, workload: WorkloadRef, budget: Budget) -> Result:
    """Evaluate a candidate accelerator design. Returns latency, energy, area,
    bottleneck analysis, and confidence intervals."""     # ← becomes the MCP description
```

Generates: a typed Python function, a CHIA `@ChiaFunction` node, and an MCP tool (fastmcp, the
same stack CHIA uses). Closes G12 at zero marginal cost.

### 7.3 Isolation and redaction

Two boundaries, enforced structurally:

1. **Agent ⇄ evaluator.** The agent proposes IR documents; it does not have write access to the
   evaluator, the validity checker, the calibration store, or the holdout corpus. Container
   boundary, CHIA-style. Threat model matches CHIA's: erroneous, not malicious, models.
2. **Evaluator ⇄ model context.** A **redaction policy** governs what evaluator output may enter a
   model's context. Absolute PPA numbers from a commercial PDK are replaced by normalised values,
   rank orderings, or relative deltas; anything not permitted is routed to a local model endpoint
   instead. This is a direct response to the problem CHIA states plainly: proprietary PDK data
   cannot go to public frontier models, and open-PDK results did not transfer to a commercial
   16nm node (G15).

## 8. L0 — Stores

**Result / artifact store.** Content-addressed. Every design point records inputs, evaluator
versions, calibration id, strategy, seeds, cost, and proposer (human or model id). Backends:
SQLite for local, Postgres + S3 for shared — the same choices CHIA already supports, so a shared
deployment is trivial. Deterministic replay is one command (G10).

**Calibration store.** Ground-truth measurements + residual models + validated-domain descriptors,
versioned and CI-tested.

**Benchmark corpus.** Workload IR documents + reference architectures + objective definitions,
split into public and **holdout** partitions. The seed of the DSE leaderboard that G13 says is
missing — and the natural companion contribution to the hardware benchmark suites CHIA's authors
want to integrate.

## 9. Performance engineering

| Concern | Approach |
|---|---|
| Hot loop | Rust core (or C++, if team skills dictate); no allocation per candidate; SoA layouts |
| Language boundary | PyO3/nanobind; batch across the boundary, never per-candidate |
| Enumeration | Bitset-encoded loop nests; prune by dominance before costing |
| Memoisation | Content-addressed cache keyed on `(w,a,m,evaluator_version)`; shared across users |
| Incrementality | Dependency-tracked re-evaluation — change one arch parameter, recompute only what depends on it |
| Parallelism | Data-parallel within a node (rayon/OpenMP); across nodes via CHIA/Ray |
| Determinism | Explicit seeds everywhere; a deterministic mode that disables nondeterministic parallel reduction |

**Target:** ≥10⁵ dense-layer mapping evaluations/second/core for the native backend, and a full
model × architecture sweep that today takes hours reduced to minutes.

│   │                         calibration + independent validity checker being live
│   ├── rtl_synth/ conformance/ backends/    # backends: Gemmini generator, CIRCT/Chisel wrappers
├── knowledge/              # domain knowledge / context layer (D3), RAG-style

**Conformance tests are the load-bearing directory.** Any new evaluator backend must pass a shared
suite proving it interprets the IR the same way as the reference, or that it fails loudly on the
parts it cannot express. Without this, the contract decays into a suggestion within two releases.
Generated RTL is held to the same conformance suite (`generation/conformance/`), not a separate,
looser standard.

## 11. What this explicitly does *not* do (v1)

> **Superseded in part by [00 §D2](00-decisions.md):** full generation closure is now in scope,
> sequenced as Phase 3.5, gated on the calibration layer and independent validity checker. The
> conformance-checking machinery below is retained as the acceptance gate for every generated
> design, not as a substitute for generating it.

- ~~Does not generate RTL. It *checks conformance* of RTL you supply against the model (G7 scoped
  down).~~ Generation is in scope (D2); conformance-checking remains the gate any generated RTL
  must pass.
- Does not replace CHIA, TVM, Deeploy, or MLIR.
- Does not attempt full-system simulation.
- Does not model training in v1 — the IR reserves room for it (`phases`, tensor lifetimes) but the
  cost models won't cover optimiser state and gradient traffic initially.
- Does not ship its own NoC or thermal model in v1 — the schema slots exist; the models come later
  or via adapters (3D-ICE for thermal is the obvious first integration).
