# 01 — Landscape Survey

Scope: open-source tooling for DNN/tensor accelerator design-space exploration, mapping,
deployment, and (increasingly) agentic co-design. Organised by the layer each tool occupies,
because the layering is the point.

**The gap is between L4 and L5, and between L4 and L3.** Every L4 tool implements its own private
L5, and L3 tools reach into L4 tools through ad-hoc bindings (MATCH literally calls ZigZag's LOMA
mapper as a subroutine).

## 1. KU Leuven — MICAS (Verhelst group)

The most complete academic L4/L5 family, and our primary reference.

| Tool | What it is | Status |
|---|---|---|
| **ZigZag** | Single-core architecture↔mapping DSE. ONNX frontend, >2D MAC arrays, flexible memory hierarchy, analog/digital in-memory-compute (IMC) modelling, YAML outputs. MIT licence. Now majority **C++** (~60%) with a Python shell — the mapping engine was rewritten for speed. | Active |
| **Stream** | Multi-core / heterogeneous extension of ZigZag. Layer-*fused* (depth-first) scheduling across cores, from layer-by-layer down to fine-grained tile granularity. Ships **COALA**, a memory- and communication-aware latency/energy model validated against three real accelerators. Workload allocation via constraint optimisation. | Active |
| **ZigZag-LLM** | LLM-specific rapid modelling on single-core accelerators; early energy-bottleneck identification. | Active |
| **SNAX / snax-mlir** | End-to-end open multi-accelerator cluster: SystemVerilog hardware framework + **MLIR** compilation toolchain. This is MICAS quietly moving to MLIR at L3. | Active |
| **HeMAiA**, **frontend-mess**, **openising** | Heterogeneous multi-AI-accelerator SoC, memory-system frontend, Ising solvers. | Varies |

**Key intellectual contribution:** *uneven mapping.* ZigZag decouples the loop-blocking scheme per
operand (W/I/O), per memory level. Prior tools force all operands to share a blocking scheme.
ZigZag's paper reports this finds design points up to ~20% lower energy than Timeloop's best on the
same Eyeriss architecture — and explicitly notes those mappings **cannot be represented in
Timeloop**, so they cannot be validated back. Remember this: it is the canonical example of
representation lock-in.

**Validation numbers to reuse as our own bar:** within 5% / 7.5% energy error vs. published
Eyeriss and ENVISION silicon; ≤6% energy and ≤9% PE-utilisation error vs. in-house RTL.

Links: <https://github.com/KULeuven-MICAS/zigzag> · <https://github.com/KULeuven-MICAS/stream> ·
<https://kuleuven-micas.github.io/stream/>

## 2. MIT — CSAIL / EEMS (Emer & Sze), with NVIDIA

The other major L4 family, and the one with the deepest *modelling* research.

| Tool | What it is |
|---|---|
| **Timeloop** | The reference architecture-mapping model + mapper. C++ core; exhaustive/random/heuristic mapper. Widely used as *the* baseline cost model; validated against real chips. |
| **Accelergy** | Architecture-level **energy** estimation, decoupled as a plug-in system (CACTI, Aladdin, NeuroSim, custom tables). This plug-in split is the single best structural idea in the family — copy it. |
| **Sparseloop** | Sparsity/compression layer on top: unified taxonomy of sparse-accelerator design space, stochastic density models. **>2000× faster than cycle-level simulation, 0.1–8% average error.** |
| **CiMLoop** | Compute-in-memory modelling (ISPASS 2024). Directly comparable to ZigZag's IMC support. |
| **PyTimeloop / TimeloopFE** | Python frontend + bindings; requires `islpy` with **Barvinok** support (polyhedral counting) — a notable, and painful, dependency. |
| **Ruby** | Imperfect factorisation for mapping (ISPASS 2022) — handles the non-divisible tile-size problem. |
| **Fibertree / TeAAL** | Formal notation for sparse tensor dataflow; the theoretical substrate. |

Links: <https://timeloop.csail.mit.edu> · <https://accelergy.mit.edu> ·
<https://github.com/Accelergy-Project/timeloop-accelergy-exercises>

**Takeaway:** MIT has the better *decomposition* (Accelergy plug-ins, fibertree formalism);
KU Leuven has the better *mapping space* (uneven mapping) and the more modern frontend (ONNX,
Python-first ergonomics). Neither has both.

## 3. ETH Zürich + University of Bologna — PULP Platform

Strongest at **L3 (deployment compilers)** and **L1 (silicon that actually exists)**. This is the
group to copy for "the model must eventually run on real hardware."

| Tool | What it is |
|---|---|
| **Deeploy** | ONNX→C compiler for multi-cluster heterogeneous SoCs. Architecture-agnostic tinyML optimisations: memory-aware operator tiling, double buffering, DMA-aware codegen, **fully static offline memory layout**. Bottom-up: offloads what the accelerator supports, falls back to optimised cluster kernels otherwise. Demonstrated end-to-end transformers on Siracusa with <10% data-movement overhead. |
| **DORY** | Predecessor: formulates DNN tiling as a **constraint-programming** problem maximising L1 utilisation, emits ANSI C orchestrating DMA + compute. |
| **MATCH** | TVM extension adding hardware-aware DSE for heterogeneous SoCs; assigns layers/fused patterns to accelerators. **Internally uses ZigZag's LOMA mapper and cost model** for L1/L2 tiling. |
| **MATCHA** | (DAC '26) Async multi-accelerator extension — concurrent offloading, tile-level + layer-level parallelism, OS-less SoCs. |
| **Snitch / Occamy / MemPool / Siracusa / N-EUREKA** | The silicon: RISC-V clusters, NPUs, taped out repeatedly. |
| **PULP-TrainLib** | On-device *training* primitives + AutoTuner + code generator. Rare and useful — almost nobody else models training. |

Links: <https://github.com/pulp-platform/Deeploy> · <https://github.com/eml-eda/match>

**Takeaway:** MATCH calling ZigZag as a library is the existing proof that our proposed
"evaluator-as-a-service" contract is wanted. It is currently done by direct import, which is
exactly the brittleness we want to fix.

## 4. EPFL — ESL (Atienza) and collaborators

Strongest at **L1 platform + L0 physical/thermal**, weaker at L4/L5. Complementary rather than
competitive.

| Tool | What it is |
|---|---|
| **X-HEEP** | Configurable, extendable RISC-V MCU platform for exploring ultra-low-power edge accelerators. SystemVerilog templates for configuration, FuseSoC build system (Verilator, QuestaSim, VCS, Xcelium, Design Compiler, Genus, Vivado), FPGA + ASIC flows. Accelerators attach via **CV-X-IF** or as memory-mapped peripherals — no MCU surgery required. Silicon: HEEPocrates, HEEPnosis (GF 22nm FDX). Now co-maintained with UPM CEI and POLITO; built on PULP + OpenTitan IP. |
| **gem5-X / gXR5** | gem5 with architectural extensions; full-system RISC-V. |
| **3D-ICE** | 3D interlayer cooling / thermal emulator. **Nobody in the L4 DSE world models thermals. This is a real gap and EPFL already owns the tool.** |
| **FEMU** | RISC-V emulation platform for accelerator-based edge applications. |

Links: <https://github.com/x-heep/x-heep> · <https://www.epfl.ch/labs/esl/research/open-source-tools/>

## 5. UC Berkeley — BAR / SLICE

Owns **L6 and L0–L1**, and is now the most aggressive on agentic co-design.

| Tool | What it is |
|---|---|
| **CHIA** | The agentic orchestration framework (see [02](02-architecture-teardown.md) for the teardown). BSD-3. |
| **Chipyard** | Integrated SoC design/simulation/implementation framework — the substrate CHIA drives. |
| **Gemmini** | Systolic-array NPU generator with full RTL + software stack. The standard "real accelerator" target for validating cost models. |
| **FireSim** | FPGA-accelerated cycle-exact simulation. CHIA's case studies run 25.5 trillion SPEC06 instructions this way. |
| **Hammer** | Modular physical-design flow (fronts commercial CAD). |
| **DOSA** | Differentiable analytical performance model + gradient-descent **one-loop** HW/mapping co-search. Reports EDP 2.80× better than random search and 12.59× better than Bayesian optimisation. Validated against Gemmini RTL. <https://github.com/ucb-bar/dosa> |
| **CoSA** | Constrained-optimisation (MIP) scheduling for accelerators. |
| **ArchAgent** | AlphaEvolve + large simulation cluster discovering cache-replacement policies that beat human SOTA. |

**Takeaway:** DOSA is the most important prior art for our search layer. It proves the analytical
model can be made *differentiable* without losing Timeloop-class accuracy, which collapses the
sample complexity of DSE. Any new tool that ships a black-box-only search in 2026 is behind.

## 6. Others worth knowing

| Tool | Origin | Note |
|---|---|---|
| **MAESTRO** | Georgia Tech (Krishna) | Data-centric cost model; analyses a *fixed* dataflow rather than searching. Fast, coarse. |
| **Interstellar** | Stanford (Horowitz) | Halide-based; coarse memory/compute energy model with heuristic pruning. Historically important, low activity. |
| **SCALE-Sim** | ARM | Systolic-array-specific cycle-accurate-ish simulator. Narrow but trusted. |
| **STONNE** | Murcia | Cycle-level simulator for flexible DNN accelerators — useful as a *fidelity oracle*. |
| **dMazeRunner** | ASU | Coarse-grained programmable accelerator dataflow optimisation. |
| **Voyager** | (arXiv 2509.15205) | End-to-end DSE **and hardware generation** — explicitly positions against Timeloop/MAESTRO/ZigZag/Interstellar on the grounds that "these tools do not generate hardware." Directly relevant to our closure goal. |
| **StreamTensor** | — | MLIR-based dataflow streaming for LLMs on FPGA. |
| **ESP** | Columbia | Agile SoC integration platform, SystemC/HLS-friendly. |
| **LLM-DSE** | (arXiv 2505.12188) | LLM agents searching DSA parameters. Honest limitations: no code transformations; still needs *hours* to converge. |
| **Explainable-DSE** | — | Bottleneck-analysis-driven search; argues black-box exploration wastes trials because it cannot reason about *why* a design is inefficient. |
| **ArchGym** | Google/Harvard | Gymnasium-style sandbox connecting search algorithms to architectural simulators. Closest existing attempt at the "contract" idea — and it did not take over the field, which is worth understanding before we repeat it. |

## 8. Things that do *not* need rebuilding

State this early to keep scope honest:

- **Distributed, fault-tolerant, heterogeneous orchestration** → CHIA/Ray solved it.
- **Energy primitive estimation** → Accelergy's plug-in ecosystem (CACTI, NeuroSim, Aladdin).
- **Cycle-exact ground truth** → Verilator / FireSim / gem5.
- **Physical design** → Hammer / OpenROAD.
- **Workload ingest** → ONNX + MLIR importers.
- **Silicon targets for validation** → Gemmini, Snitch/Siracusa, X-HEEP-based designs.

## 9. Open questions to resolve before Doc 04 is committed

1. Is our target **edge/tinyML** (favours Deeploy/DORY/X-HEEP alignment) or
   **datacentre/LLM-serving** (favours Stream/chiplet/NoC and KV-cache modelling)? The IR can
   cover both but the validation corpus and search priors cannot be built for both at once.
2. Do we require **HW generation closure** (Voyager/Gemmini-style) in v1, or is
   model→RTL-handoff enough?
3. Do we need **training** workloads (PULP-TrainLib territory) or inference only?
4. What is the licensing floor? ZigZag is MIT, CHIA is BSD-3, Timeloop/Accelergy differ — check
   before vendoring anything.
