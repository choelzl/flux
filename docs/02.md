# 02 — Architecture Teardown

What the reference tools actually are internally: features, data flow, layout, extension points,
and the design decisions that will constrain us if we reuse them.

---

## 1. ZigZag (KU Leuven MICAS)

### 1.1 Feature set (as documented)

- **ONNX integration** — parses ONNX models directly, no bespoke workload format required.
- **Flexible hardware description** — multi-dimensional (>2D) MAC arrays, non-trivial
  interconnect patterns, arbitrary memory hierarchies.
- **Cost model** — energy and latency, including memory port structures, with spatial and temporal
  data-sharing/reuse patterns *inferred* rather than declared.
- **In-memory computing** — digital and analog IMC cores as first-class citizens.
- **Object-oriented, modular** rewrite intended for extension.
- **YAML outputs** for downstream consumption.
- Licence: MIT. Roughly 600 commits, ~200 stars, ~60 forks — healthy academic project, not a
  large engineering organisation. Implementation has shifted to **~60% C++ / ~40% Python**.

### 1.2 Conceptual architecture

```
   ONNX model ──┐
                ├──► Workload parser ──► LayerNode(s)  (nested-for-loop representation)
   arch YAML ───┤                              │
   mapping YAML─┘                              ▼
                        ┌───────────────────────────────────────┐
                        │  Spatial mapping generator            │
                        └───────────────┬───────────────────────┘
                                        ▼
                        ┌───────────────────────────────────────┐
                        │  Temporal mapping engine              │
                        │    LOMA  (loop-order → memory alloc)  │
                        │    SALSA (simulated-annealing search)  │
                        └───────────────┬───────────────────────┘
                                        ▼
                        ┌───────────────────────────────────────┐
                        │  Cost model: memory allocation,       │
                        │  data reuse, port contention,         │
                        │  latency (uniform latency model),     │
                        │  energy (per-access + MAC)            │
                        └───────────────┬───────────────────────┘
                                        ▼
                            CostModelEvaluation → YAML / plots
```

Execution is organised as a **Stage pipeline** — composable stages wrap each other
(workload parsing → accelerator parsing → spatial mapping → temporal mapping → cost model →
reduction/aggregation). This is genuinely good design and worth preserving conceptually.

### 1.3 The central abstraction

An **enhanced nested-for-loop format** as the uniform representation unifying algorithm,
architecture, and mapping. Three key components per the original paper: (1) analytical
energy/performance/area **cost estimator**, (2) **two mapping search engines** covering
spatial/temporal and even/uneven mapping, (3) an **architecture generator** that auto-explores
memory-hierarchy design space.

### 1.4 Extension points

- New workloads: ONNX operator handlers.
- New hardware: YAML arch description + optionally new memory/operational-array classes.
- New search: implement a temporal-mapping generator conforming to the stage interface.
- New cost terms: subclass the cost model.

### 1.5 Constraints we inherit if we build on it

- The nested-for-loop representation is **affine, dense, static-shape**. Dynamic shapes,
  data-dependent control flow, and irregular sparsity do not fit naturally.
- The stage pipeline is Python-level; the C++ core is reached through it, so per-candidate
  overhead is bounded below by Python object construction.
- Architecture YAML is a *template instantiation*, not a general hardware description — modelling
  something structurally novel means writing Python, not YAML.
- No notion of confidence, error bars, or calibration state attached to a result.

## 2. Stream (KU Leuven MICAS)

Built **on top of** ZigZag; extends it to multi-core and fine-grained scheduling.

### 2.1 What it adds

- **Layer fusion / depth-first**: layers are split into tiles and scheduled across cores, spanning
  the spectrum from classical layer-by-layer to fine-grained fused execution.
- **Heterogeneous multi-core modelling**: cores with different compute/memory capability, plus
  explicit interconnect.
- **COALA**: memory- and communication-aware latency+energy model, validated against three
  distinct state-of-the-art accelerator implementations.
- **Constraint-optimisation workload allocation** across cores.
- Reported result: layer fusion on heterogeneous dataflow accelerators yields up to **2.2× lower
  EDP**.

### 2.2 Architecture

```
   ONNX ──► workload graph ──► node splitting (tiles) ──► ComputationNode DAG
                                                              │
   multi-core arch YAML ──────────────────────────────────────┤
                                                              ▼
                                    ┌──────────────────────────────────────┐
                                    │ Intra-core mapping   (ZigZag reused) │
                                    └──────────────┬───────────────────────┘
                                                   ▼
                                    ┌──────────────────────────────────────┐
                                    │ Allocation (constraint optimisation) │
                                    │ Scheduling  (list scheduler)          │
                                    │ COALA: comms + memory contention      │
                                    └──────────────┬───────────────────────┘
                                                   ▼
                                          latency / energy / EDP
```

Stages are customisable, same as ZigZag.

### 2.3 Constraints inherited

- The tile DAG explodes combinatorially with fusion granularity — this is where Stream's runtime
  goes, and it is the natural target for a native rewrite.
- Interconnect modelling is at the level of links and bandwidths, not a real NoC model (no
  routing, no congestion under adversarial traffic, no topology-aware placement).

## 3. Timeloop + Accelergy (+ Sparseloop, CiMLoop) — MIT/NVIDIA

### 3.1 Architecture — and why the split matters

```
   workload YAML ─┐
   arch YAML ─────┼──► Timeloop model ──► cycles, accesses ──┐
   mapping/       │       ▲                                   ├──► results
   constraints ───┘       │                                   │
                    Timeloop mapper                           │
                    (exhaustive / random / heuristic)          │
                                                               │
   arch YAML ─────────► Accelergy ──► energy ─────────────────┘
                          │
                          ├── plug-in: CACTI      (SRAM/DRAM)
                          ├── plug-in: Aladdin    (logic)
                          ├── plug-in: NeuroSim   (CiM)
                          └── plug-in: user tables
```

**Accelergy's estimator plug-in interface is the best structural idea in this entire ecosystem.**
Energy primitives are *not* baked into the model; they are supplied by pluggable estimators keyed
on component class + attributes + action. This is precisely the pattern we should generalise to
*all* cost dimensions (energy, area, latency, leakage, thermal).

### 3.2 The variants

- **Sparseloop** layers a sparsity taxonomy on top: compression formats, gating/skipping,
  stochastic density models. Speed/accuracy: >2000× vs cycle-level, 0.1–8% average error.
- **CiMLoop** covers compute-in-memory.
- **PyTimeloop / TimeloopFE** provide the Python surface (`import pytimeloop.timeloopfe`).

### 3.3 Constraints and friction

- **Build complexity is a real adoption tax.** PyTimeloop needs Timeloop built as shared libs plus
  `islpy` **with Barvinok enabled**. Barvinok is a polyhedral lattice-point counter and is
  notoriously awkward to build. Most users end up in the provided Docker image, which then becomes
  the de-facto interface.
- **Representation is narrower than ZigZag's**: even mappings only, so uneven-mapping results are
  inexpressible. Cross-tool validation is therefore structurally one-directional.
- Configuration is a sprawl of YAML with implicit coupling between arch, constraints, and mapper
  settings — a frequent source of silently-wrong results.

## 4. Deeploy / DORY / MATCH (ETH + UniBO + PoliTo)

These are **L3 deployment compilers**, not DSE tools, but they define the interface a DSE tool must
eventually satisfy if its answers are to mean anything.

### 4.1 Deeploy

- **ONNX → C** for multi-cluster heterogeneous SoCs.
- Bottom-up target modelling: fine-grained, modular hardware description; kernels are *templates*
  the compiler fills in.
- Optimisations: memory-aware operator tiling, **double buffering**, **DMA-aware code generation**,
  **fully static offline memory layout**.
- Fallback strategy: offload supported ops to accelerators, run everything else on cluster cores
  with optimised kernels. This is what makes it survive new operators.

### 4.2 DORY

- Tiling as a **constraint-programming** problem: maximise L1 utilisation subject to topological
  constraints, augmented with heuristics favouring backend-friendly tile shapes.
- Emits ANSI C orchestrating off-/on-chip transfers and compute phases.

### 4.3 MATCH / MATCHA

- **MATCH**: TVM extension; hardware-aware DSE for heterogeneous SoCs; assigns layers or fused
  patterns to accelerators; **delegates L1/L2 tiling to ZigZag's LOMA mapper + cost model**.
- **MATCHA**: adds concurrent asynchronous execution across multiple accelerators, exploring
  layer-level *and* tile-level parallelism simultaneously for OS-less SoCs.

### 4.4 The lesson

MATCH's reuse of ZigZag is the strongest existing evidence for the "evaluator as a callable
service" thesis — and it is implemented as a source-level dependency, which means every ZigZag
refactor is a potential MATCH breakage. **A stable versioned contract would have prevented that.**

## 5. CHIA (UC Berkeley)

### 5.1 What it is

An open-source framework whose premise is that *the productive construction and scalable
deployment of the co-design flow itself* is a first-class objective. BSD-3 licensed, Python
(97%), requires Python 3.10.19 to match its Docker images.

### 5.2 The two abstractions

**A CHIA workflow = a CHIA cluster + a CHIA loop.**

**Cluster** — physical machines → *logical workers* → containers.
- Logical workers declare *virtualised resources* (`FPGA: 1`, `vivado: 1`, `claude_creds: 1`,
  `verilator: 1`). Nodes request resources; the runtime matches.
- Declared in YAML; managed by CLI: `chia up cfg.yaml`, `chia down cfg.yaml`,
  `chia up cfg.yaml --add` (dynamic expansion / dead-worker restart).
- **Containerisation is the isolation mechanism**, and it is doing real work: it prevents an LLM
  from reading the golden reference implementation (experiment integrity) and from touching
  proprietary PDKs (confidentiality). Threat model explicitly assumes *erroneous, not malicious*
  models. It also collapses setup time — a fresh Chipyard environment goes from ~1 hour to seconds.
- Clusters span on-prem and public cloud (AWS/GCP) transparently.

**Loop** — a Python program forming a **directed cyclic graph**.
- **Nodes**: `@ChiaFunction(resources="...")`-annotated Python functions. Scheduled when inputs are
  ready and a worker with matching resources is free. `fn.chia_remote(args)` returns a future;
  calling directly runs in-process. Nodes are the unit of retry, caching, bypass, subprocess
  tracking, and profiling.
- **Edges**: *programmatic* (explicit in the orchestration program) or **agentic** (an agent invokes
  the node as an **MCP tool**). `ChiaTool` objects host an MCP server; `ChiaTool.mcp.add_tool(fn)`
  registers a tool and **the function's docstring becomes the LLM-facing description**. Passing
  `fn.chia_remote_blocking` lets the tool server live on one worker while the tool executes on
  another.
- This two-edge design is the key generalisation: it spans the whole spectrum from
  fully-scripted to fully-agent-driven flows, tunable per node.

### 5.3 Runtime features

| Feature | Mechanism / value |
|---|---|
| Scheduling | Ray's distributed scheduler; handles nondeterministic agent-driven graphs where the node set isn't known ahead of time |
| Fault tolerance | Ray-based; dead worker → no new work scheduled there, in-flight tasks requeued to compatible workers |
| Subprocess tracking | Kills spawned processes on cancel — prevents stray multi-hour Vivado runs leaking memory |
| Profiling | Every `@ChiaFunction` auto-profiled to disk (start time, wall-clock, worker id, user fields); **reconstructs the task graph by tracking object identity** |
| Caching + bypass | Persist node results; inject stand-in outputs. Together they give fast-forward-after-crash, deterministic replay over nondeterministic LLM nodes, and cheap flow testing without long-running nodes |

### 5.4 Implementation stack

**Ray** (chosen over LangGraph, Microsoft Agent Framework, Airflow for expressive cyclic control
flow + fine-grained scheduling + distributed fault tolerance), Docker, PrefectHQ **fastmcp**,
boto3 / google-cloud-python, TensorBoard + Weights & Biases + GraphViz for profiling and
visualisation.

### 5.5 Library nodes shipped

LLM/agents (Claude Code, Codex, Antigravity, Vertex/Gemini, Bedrock, Ollama, vLLM, OpenCode,
OpenRouter, Groq, Fireworks); SoC design (Chipyard); HW compilation (CIRCT, Scala FIRRTL);
simulators (Verilator, FireSim, gem5, ChampSim); verification (riscv-torture, Spike co-sim);
VLSI (Hammer → commercial CAD); storage (Postgres, SQLite, S3); repo management (GitHub);
evolution (**SkyDiscover** wrapping AlphaEvolve, AdaEvolve, EvoX, GEPA, OpenEvolve).

### 5.7 What CHIA demonstrably achieved

| Case study | Result |
|---|---|
| RTL → gem5 alignment | 202 iterations / ~10.5 days → **2.80%** cycle-count error on training set, **6.12%** on a *withheld* Embench suite the agent never saw. ~$11.72/iteration, $2,356 total. |
| RISC-V ISA extensions in MegaBOOM | Bitmanip +5.6% and Zicond +3.5% geomean on full SPEC06 ref (25.5T instructions); Crypto up to ~10× on OpenSSL. ~2–5% area overhead in Sky130, 0.8–6% in commercial 16nm, no timing regressions. $5–46 per extension. |
| Critical-path optimisation | MegaBOOM 47 MHz → 95 MHz in Sky130 (**2.03×**), IPC −3.28% → net iron-law **1.97×**, for **$202** in API cost. |
| CIRCT issue fixing | 16 issues triaged, 5 fixed, 3 PRs merged upstream, all 16 processed in parallel in <45 min. |

### 5.8 What CHIA's authors themselves flag as unsolved

Quoted in substance from their discussion section — these are directly actionable for us:

1. **The bottleneck moved to evaluation and verification.** Parallelism alone is insufficient
   (Amdahl). We need shorter representative benchmarks, faster simulation and PPA estimation,
   and rapid verification without losing fidelity.
2. **Privileged information.** Proprietary PDKs cannot be fed to public frontier models. Open PDKs
   are used instead — and **Sky130 results did not generalise to a commercial 16nm node** beyond
   the first optimisation. Abstracting QoR data before it reaches a model is an open problem.
3. **Reward hacking is observed, not hypothetical.** In an early ArchAgent experiment, AlphaEvolve
   exploited an improperly-enforced assertion to drop memory traffic and claim a fake speedup.
4. **Evaluation fidelity gates discovery.** ChampSim cannot give reliable power/area/critical-path
   feedback, so the hardware-realisability of designs evolved against it is questionable; and
   ChampSim needed *days* per billion-instruction SimPoint on a quad-core, throttling the whole
   search.
5. **Overfitting to the training benchmark set** was observed directly — the agent introduced a
   threshold parameter explicitly "calibrated to [training benchmark]'s inner loop," which then
   degraded a holdout benchmark.

**Point 4 is our opening.** CHIA's evaluator cascade currently jumps from ChampSim-class
(fast, low fidelity, no PPA) straight to Verilator/FireSim/Hammer (high fidelity, slow, expensive).
The rung of the ladder that is missing — fast, *PPA-aware*, calibrated, uncertainty-quantified
analytical evaluation for tensor accelerators — is exactly what the ZigZag/Timeloop family
provides for a narrow slice of the space and nobody provides in a form CHIA can consume.

## 6. ONNX's role, honestly assessed

ONNX is the de-facto ingest format (ZigZag, Stream, Deeploy all take it) and should remain one.
But it is a **model interchange format, not a compiler IR**, and for our purposes:

- Opset drift and vendor-specific ops mean coverage is a permanent maintenance treadmill; ZigZag's
  own roadmap lists "expanding ONNX operator support for modern generative AI workloads" as open
  work.
- No affine/loop structure — every consumer re-derives iteration spaces from op semantics, and each
  does it slightly differently.
- Poor fit for dynamic shapes, KV-cache lifetime, paged attention, MoE routing, speculative
  decoding — i.e. most of what matters for current LLM serving.
- No place to attach hardware-relevant annotations (quantisation schemes beyond QDQ, sparsity
  structure, tiling hints, residency constraints).

**Conclusion:** keep ONNX as a *frontend*, not as the internal representation. MLIR
(`linalg`/`tosa`/`stablehlo`) is where the rest of the field is heading — snax-mlir, StreamTensor,
CIRCT, and TVM's Relax all point the same way.
