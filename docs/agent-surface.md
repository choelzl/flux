# The agent surface

Packages: `interfaces/chia_nodes/`, `interfaces/mcp/`, `interfaces/cli/`, `mentor/knowledge/`,
`mentor/records/ (`flux_records.mining`)`. Part of [architecture.md](architecture.md)'s layering.

## Don't rebuild orchestration

CHIA already provides distributed execution, heterogeneous resource matching, containerized
isolation, fault tolerance, subprocess tracking, profiling, and caching/bypass, on Ray (see
[landscape.md](history/landscape.md) for the full teardown). Rebuilding any of that would be pure waste —
this repo ships CHIA library nodes and MCP tools on top of it instead.

## One definition, three surfaces

Every capability is a typed Python function (`interfaces/chia_nodes/`), a real `@ChiaFunction()` node
(same module), and a real MCP tool (`interfaces/mcp/`'s `FluxTool`, a genuine `chia.base.tools.
ChiaTool` subclass modeled on CHIA's own `BashTool`/`ChiaToolTemplate`) — from one definition, not
generated by any code-generation layer (each surface is hand-written). `FluxTool("flux")` starts
a real Ray-actor-backed uvicorn server at `http://{host}:{port}/{name}/mcp`.

**Adding one is one edit per surface, and the lists are derived** ([D452](decisions.md)). A
`FluxTool` method IS a tool: `setup()` registers every public method the class defines
(`FluxTool.tools()`), so no hand-written list of `add_tool` lines exists and a method cannot be left
unregistered. The method is where the tool's agent-facing documentation
lives — its description and, for most tools, the per-argument `Args:` block the MCP schema is
built from — which is why the nodes are not registered directly: the node is typed Python, the
tool is documented for a model. The omni catalog reads the same registration by running `setup()`
against a recorder, and `tests/unit/test_mcp_surface_parity.py` checks the two lists that remain
hand-written -- the node package's `__all__` and this page's table -- in both directions.

## LLM access

A model is an OpenAI-compatible server ([D508](decisions.md)): a hosted LocalAI
(`FLUX_LLM_REMOTE=1`, `FLUX_REMOTE_BASE_URL`, `FLUX_REMOTE_MODEL`, `FLUX_REMOTE_API_KEY`,
[D469](decisions.md)) or a local Ollama (`FLUX_LLM_MODEL`); `chia.models.ollama.OllamaLLM` is
what the generation nodes (RTL, SystemC, architecture candidates, the design-spec author, the
prose-faithfulness check) use. Every loop runs without one; the roles a model would fill say
they were skipped.

**The agentic halves** ([D505](decisions.md)). With a model that populates `tool_calls`
(LocalAI + qwen3.6-35b-a3b-apex, measured 2026-09-18), the loop offers three agentic halves,
each off by default and switchable per run (`flux task run --agent tools|orchestrate|plan|all`,
a document's `roles:`, a plan file's fields):

| half | manual (the code's rules) | agentic |
|---|---|---|
| a model turn | one message, JSON back, no tools (`tools: false`) | `flux_llm.tools.Tool`s the model calls inside the turn: `compute`, `check` (the problem's own test with its report), `history`, `knowledge`, `timing`, and the world's instruments (`error_map`, `compare`, `quantisation`, `family`, [D530](decisions.md), [D535](decisions.md)) |
| orchestration | `rules` / `given` / `llm` menus, the improve ladder's first due step | `agent`: reads `standings()`, `history(part)`, `decisions()`, `knowledge()`, picks from the same menus, every pick on the ledger |
| the loop's shape | a plan file (`--plan`): parts and order, budgets, stages, roles, tools | `--agent plan`: the agent writes the plan, validated by the same `flux_loop.plan.check_plan`, kept on the record |

What none of the halves may decide: admission. The gate stays the exhaustive test's.

## Isolation and redaction

Two boundaries:

1. **Agent ⇄ evaluator.** The agent proposes IR documents; it does not have write access to the
   evaluator, the validity checker, the calibration store, or the holdout corpus. Container
   boundary, CHIA-style — threat model matches CHIA's: erroneous, not malicious, models. **Real**:
   `flux_list_public_corpus` (the only corpus-reading MCP tool) accepts no parameter that could
   reach the holdout partition, verified both behaviorally and via `inspect.signature`.
2. **Evaluator ⇄ model context.** A redaction policy governing what evaluator output may enter a
   model's context (absolute PPA numbers from a commercial PDK replaced by normalized values or
   relative deltas) — **real now** ([decisions.md D93](decisions.md)/[D94](decisions.md),
   `redaction/`, closing [gap-analysis.md](history/gap-analysis.md) G15): `redact_relative`/
   `redact_ranking` return types with no field that could ever hold the real absolute value
   (checked directly via `dataclasses.fields()`, not just unprinted by convention), and a real,
   structural enforcement point — `flux_synthesize_with_asap7` (the raw node) refuses outright
   (`ConfidentialPdkError`) if its own PDK is ever registered confidential, rather than trusting a
   caller to reach for the redacted surface instead. Real, honest limit: only wired for ASAP7 —
   this repo's own one real PDK-derived metric ([decisions.md D92](decisions.md)) — and ASAP7
   itself is real, BSD-3-Clause, not actually confidential; no genuinely confidential PDK exists
   in this sandbox to enforce this against for real, only a real, tested mechanism ready for one.

## Not yet built

- `flux_evaluate` resolving `Candidate.workload`/`arch` from a `ResultStore` hash — only inline
  IR dicts today, same v0.1 limitation `interfaces/cli` has.
- `flux_calibrate`/`flux_conformance_check` default to a relative `calibration_db_path` rather
  than a shared, well-known store location — pass an explicit path to accumulate records across
  calls.
- No "put" tool for an agent to store a result directly — storing stays the search/generation
  loop's job, a deliberate scope limit, not an oversight ([decisions.md D11](decisions.md)).
- No container/deployment story for running `FluxTool` on a real multi-node CHIA cluster — only
  proven with a local Ray instance.

## Knowledge layer

`mentor/knowledge/` — `knowledge_lookup(query, standard_id=None)`, backed by a pure-Python BM25
index (`retrieval.py`, no embeddings/API key) over a real, ingested corpus of three provenance classes,
kept distinguishable on every chunk: five hand-picked chapters of the RISC-V unprivileged ISA
manual (CC BY 4.0, parsed from their actual upstream AsciiDoc source), real ingested distribution
data (`distributions/`, ShareGPT-derived KV-cache lengths, [decisions.md D87](decisions.md)), and
the curated `design-guidance` corpus (original prose, [D244](decisions.md)/[D267](decisions.md) — memory implementation, multi-port composition, datapath PPA, and interconnect fabric selection, the last carrying this repo's own measured arity/frequency and Clos packet-mode numbers with their scope attached). All three surfaces
real via `flux_knowledge_lookup`. The sibling `mentor/records/ (`flux_records.mining`)` package computes typed facts
from the campaign/calibration stores — never ingested into the BM25 index, a deliberate
provenance boundary ([D243](decisions.md)) — rendered into proposer/authoring prompts via
`render_facts_for_prompt` ([D245](decisions.md)). Not implemented: any licensed standard beyond
`riscv-unpriv`, a real (non-lexical) embedding backend, connectors for any format other than
AsciiDoc. AMBA/JEDEC/PCIe/I2C checked and found closed, not ingestable without a paid license;
WISHBONE B4 checked and found genuinely public domain but not ingested (no functional use for it
in this repo yet) — see [decisions.md D31](decisions.md).

## CLI

`interfaces/cli/` — the installed `flux` console script. The loop: `flux task check <doc>`
(is the document answerable, which tools it needs, which roles can be switched) and `flux task
run <doc> --db <record> [--tui --think --agent ... --role ... --passes N]` ([D519](decisions.md)).
The campaign and its record: `flux report` ([D512](decisions.md)), `flux run`, `flux status`,
`flux stop`, `flux attach` ([D513](decisions.md)), `flux migrate` ([D524](decisions.md)),
`flux gc` ([D510](decisions.md)). The IR-and-evaluator path: `flux import` (validate + hash),
`flux eval` (a workload and architecture through a named backend, optionally persisted), `flux
replay` (re-run a stored result's exact inputs through its recorded backend and diff every
metric).
