# Flows and the agent surface (L6)

Packages: `flows/chia_nodes/`, `flows/mcp/`, `flows/cli/`, `knowledge/`, `knowledge/mining/`.
Part of [architecture.md](architecture.md)'s layering.

## Don't rebuild orchestration

CHIA already provides distributed execution, heterogeneous resource matching, containerized
isolation, fault tolerance, subprocess tracking, profiling, and caching/bypass, on Ray (see
[landscape.md](landscape.md) for the full teardown). Rebuilding any of that would be pure waste —
this repo ships CHIA library nodes and MCP tools on top of it instead.

## One definition, three surfaces

Every capability is a typed Python function (`flows/chia_nodes/`), a real `@ChiaFunction()` node
(same module), and a real MCP tool (`flows/mcp/`'s `FluxTool`, a genuine `chia.base.tools.
ChiaTool` subclass modeled on CHIA's own `BashTool`/`ChiaToolTemplate`) — from one definition, not
generated by any code-generation layer (each surface is hand-written). `FluxTool("flux")` starts
a real Ray-actor-backed uvicorn server at `http://{host}:{port}/{name}/mcp`.

## LLM access

This sandbox runs a real local Ollama server (`chia.models.ollama.OllamaLLM`, no API credentials
needed — [decisions.md D9](decisions.md)), used by many of the surfaces above: the five agentic
search tools, RTL/SystemC/architecture-candidate generation, agentic and generative campaign
strategies ([D219](decisions.md)/[D233](decisions.md)), and the NL authoring tools
(`flux_author_objective`/`flux_author_design_spec`, [D232](decisions.md)/[D235](decisions.md)).
**Autonomous multi-turn tool-calling** (an LLM directly driving a running `FluxTool` MCP server,
deciding what to call across turns) was tried and does not work reliably with the local models
available — neither `qwen2.5-coder:7b` nor `gemma4:e2b` populates a structured `tool_calls` field
via Ollama 0.20.4's native or OpenAI-compatible endpoints ([decisions.md D12](decisions.md)).
The LLM-driven surfaces instead each run a complete **harness-driven propose/observe (or
generate-validate-repair) loop** internally — see [search.md](search.md) — so a live LLM round
trip against this MCP server is real, just not in that specific autonomous shape.

## Isolation and redaction

Two boundaries:

1. **Agent ⇄ evaluator.** The agent proposes IR documents; it does not have write access to the
   evaluator, the validity checker, the calibration store, or the holdout corpus. Container
   boundary, CHIA-style — threat model matches CHIA's: erroneous, not malicious, models. **Real**:
   `flux_list_public_corpus` (the only corpus-reading MCP tool) accepts no parameter that could
   reach the holdout partition, verified both behaviorally and via `inspect.signature`.
2. **Evaluator ⇄ model context.** A redaction policy governing what evaluator output may enter a
   model's context (absolute PPA numbers from a commercial PDK replaced by normalized values or
   relative deltas) — **real now** ([decisions.md D93](decisions.md)/[D94](decisions.md),
   `redaction/`, closing [gap-analysis.md](gap-analysis.md) G15): `redact_relative`/
   `redact_ranking` return types with no field that could ever hold the real absolute value
   (checked directly via `dataclasses.fields()`, not just unprinted by convention), and a real,
   structural enforcement point — `flux_synthesize_with_asap7` (the raw node) refuses outright
   (`ConfidentialPdkError`) if its own PDK is ever registered confidential, rather than trusting a
   caller to reach for the redacted surface instead. Real, honest limit: only wired for ASAP7 —
   this repo's own one real PDK-derived metric ([decisions.md D92](decisions.md)) — and ASAP7
   itself is real, BSD-3-Clause, not actually confidential; no genuinely confidential PDK exists
   in this sandbox to enforce this against for real, only a real, tested mechanism ready for one.

## Not yet built

- Dockerfiles per evaluator backend (`containers/`).
- `flux_evaluate` resolving `Candidate.workload`/`arch` from a `ResultStore` hash — only inline
  IR dicts today, same v0.1 limitation `flows/cli` has.
- `flux_calibrate`/`flux_conformance_check` default to a relative `calibration_db_path` rather
  than a shared, well-known store location — pass an explicit path to accumulate records across
  calls.
- No "put" tool for an agent to store a result directly — storing stays the search/generation
  loop's job, a deliberate scope limit, not an oversight ([decisions.md D11](decisions.md)).
- No container/deployment story for running `FluxTool` on a real multi-node CHIA cluster — only
  proven with a local Ray instance.

## Knowledge layer

`knowledge/` — `knowledge_lookup(query, standard_id=None)`, backed by a pure-Python BM25 index
(`retrieval.py`, no embeddings/API key) over a real, ingested corpus of three provenance classes,
kept distinguishable on every chunk: five hand-picked chapters of the RISC-V unprivileged ISA
manual (CC BY 4.0, parsed from their actual upstream AsciiDoc source), real ingested distribution
data (`distributions/`, ShareGPT-derived KV-cache lengths, [decisions.md D87](decisions.md)), and
the curated `design-guidance` corpus (original prose, [D244](decisions.md)/[D267](decisions.md) — memory implementation, multi-port composition, datapath PPA, and interconnect fabric selection, the last carrying this repo's own measured arity/frequency and Clos packet-mode numbers with their scope attached). All three surfaces
real via `flux_knowledge_lookup`. The sibling `knowledge/mining/` package computes typed facts
from the campaign/calibration stores — never ingested into the BM25 index, a deliberate
provenance boundary ([D243](decisions.md)) — rendered into proposer/authoring prompts via
`render_facts_for_prompt` ([D245](decisions.md)). Not implemented: any licensed standard beyond
`riscv-unpriv`, a real (non-lexical) embedding backend, connectors for any format other than
AsciiDoc. AMBA/JEDEC/PCIe/I2C checked and found closed, not ingestable without a paid license;
WISHBONE B4 checked and found genuinely public domain but not ingested (no functional use for it
in this repo yet) — see [decisions.md D31](decisions.md).

## Interconnect layer

`interconnect/` — topology families (direct, hierarchical, multistage, parallel-switch, Clos,
butterfly) as a structural model plus deterministic RTL, with three things kept separate on
purpose ([D265](decisions.md)-[D267](decisions.md)): `topology.py` builds and enumerates the
space and carries the analytic screen model; `fabric.py` generates the WHOLE fabric as
SystemVerilog, computes routing tables constructively (refusing any topology in which some
client cannot reach some bank), and measures throughput with real Verilator under
uniform-random traffic; `catalog.py` is the referenceable IP list behind `flux_ip_catalog`,
where an entry is listed only if a generator can build it. Two evaluators consume it:
`evaluators/interconnect_struct` (instant analytic screen) and `evaluators/interconnect_phys`
(real Yosys + OpenROAD per distinct selector arity, plus the Verilator throughput measurement).
Not implemented: buffered/virtual-channel switches, ring and mesh generators (a mesh is
evaluable through the BookSim/Noxim adapters, whose numbers are not comparable to placed
silicon), and routing policy as a searchable dimension — though it is measurably the largest
single lever found ([D267](decisions.md)).

## CLI

`flows/cli/` — a real, installed `flux` console script: `flux import` (validate + hash), `flux
eval` (run a workload/architecture through a named backend, optionally persisting to a store),
`flux replay` (re-run a stored result's exact inputs through its recorded backend and diff every
metric).
