# 03 — Gap Analysis

What is missing, what is broken, what is merely annoying. Ranked by leverage, not by ease.

Each gap is stated as: **observation → why it exists → cost today → what "fixed" looks like.**

---

## Tier 1 — Structural. Fix these or don't bother building a new tool.

### G1. There is no evaluator contract; every framework is a monolith

**Observation.** ZigZag, Timeloop, MAESTRO, Stream, Sparseloop each bundle workload
representation + architecture description + mapping representation + cost model + search into one
inseparable artifact.

**Why.** Each grew out of a single research paper that needed all five to make its point.

**Cost.**
- Cost models are not substitutable. You cannot ask "what does Timeloop say about the design
  ZigZag chose?" — ZigZag's own paper documents exactly this failure, because uneven mappings are
  inexpressible in Timeloop's representation.
- Search algorithms are not reusable. DOSA's gradient search, CoSA's MIP formulation, LOMA, SALSA,
  and Timeloop's mapper are all locked to their host.
- Downstream tools resort to source-level coupling. MATCH imports ZigZag's LOMA mapper directly,
  which makes every ZigZag refactor a MATCH breakage.
- Cross-tool comparison in papers is mostly rhetorical.

**Fixed looks like.** A versioned, serialisable **Mapping/Architecture/Workload IR** plus a narrow
**Evaluator ABI**: `evaluate(workload_slice, arch, mapping, fidelity_budget) → {metrics, provenance,
uncertainty}`. Any cost model that implements it becomes swappable. Any search that speaks it
becomes portable.

---

### G2. No fidelity ladder, no calibration, no uncertainty

**Observation.** Every result from every one of these tools is a bare point estimate. There is no
error bar, no statement of what it was calibrated against, no detection of extrapolation.

**Why.** Validation is done once, at paper time, against a handful of designs (ZigZag: Eyeriss,
ENVISION, one in-house RTL; Stream: three accelerators; Sparseloop: a set of representative
designs). Then the model is used forever, on arbitrary architectures, with those numbers quoted as
if they still applied.

**Cost.**
- Nobody knows when a model has left its validated regime. Sparseloop's "0.1–8% average error" is
  an average over *its* evaluation set, and says nothing about your novel IMC macro.
- CHIA's own experience is the cautionary tale at the next level up: **Sky130 optimisation results
  did not transfer to a commercial 16nm node** beyond the first change. A model that reported
  confidence would have flagged that.
- Agentic search amplifies this catastrophically. An evolutionary agent will find and exploit
  precisely the region where your model is most optimistic. That is not a bug in the agent; it is
  the model's error surface being used as a gradient.

**Fixed looks like.**
- Every evaluator declares its **validated domain** (architecture class, tech node, operator set,
  tensor shape ranges) as machine-readable metadata.
- Every result carries `{value, confidence_interval, in_domain: bool, calibration_id}`.
- A **calibration store**: ground-truth measurements (RTL sim, silicon, synthesis) versioned
  alongside the model, with automatic residual tracking and drift alerts in CI.
- **Escalation policy**: when uncertainty exceeds a threshold or the candidate is Pareto-relevant,
  the framework automatically escalates that point to the next fidelity rung.

This is the single highest-value thing in the whole proposal.

### G3. The fidelity ladder has a missing rung, and CHIA proves it

**Observation.** CHIA's evaluator cascade is: functional (Spike) → µarch sim (gem5/ChampSim) →
RTL sim (Verilator) → FPGA emulation (FireSim) → physical design (Hammer). For *tensor
accelerators*, the fast end of that ladder is bad: ChampSim gives no reliable power/area/critical-
path feedback, and needed days per billion-instruction SimPoint.

**Why.** CHIA came from the CPU-microarchitecture world. The accelerator-DSE world (ZigZag/
Timeloop) came from the tensor world. They have never been wired together.

**Cost.** Agentic accelerator discovery currently either runs blind on low-fidelity feedback (and
produces unrealisable designs) or runs slow on high-fidelity feedback (and explores almost
nothing). Both failure modes are documented in CHIA's discovery case study.

**Fixed looks like.** Analytical tensor-accelerator evaluation (ZigZag/Timeloop-class, millisecond
scale, **with PPA**) inserted as a proper rung, exposed as a CHIA node *and* an MCP tool, with the
uncertainty machinery from G2 governing when to escalate.

### G4. Search is a private implementation detail everywhere

**Observation.** Mapping search ranges from exhaustive enumeration to random sampling to
simulated annealing to CP/MIP to gradient descent to LLM agents — and no two are interchangeable.

**Why.** G1.

**Cost.**
- Known-better methods don't propagate. DOSA showed a differentiable analytical model + gradient
  descent gets **2.80× better EDP than random search and 12.59× better than Bayesian optimisation**
  — and that capability is stranded in one repo.
- Black-box search wastes trials because it cannot reason about *why* a design is inefficient
  (the Explainable-DSE argument).
- LLM-agent search is promising but currently slow: LLM-DSE reports it still needs *hours*, and
  explicitly excludes code transformations from its space.

**Fixed looks like.** Search as a **pluggable strategy** over the evaluator ABI, with a shared
warm-start/result database so that (a) strategies are benchmarkable head-to-head on identical
problems, and (b) every strategy can seed from prior runs. Bottleneck/roofline analysis returned as
*structured* evaluator output so both humans and agents get explanation, not just a scalar.

## Tier 2 — Coverage. These determine whether the tool is relevant in 2026.

### G5. Modern workloads are poorly represented

Every tool in this family was designed around **dense, static-shape, affine CNN layers**. Current
reality:

| Workload feature | Support today |
|---|---|
| Dynamic sequence length | essentially none |
| KV cache (residency, growth, paging) | none in the L4 tools; ZigZag-LLM is a partial start |
| Prefill vs decode phase asymmetry | none |
| MoE / conditional routing | none |
| Attention variants (GQA, MLA, sliding-window, sparse) | ad hoc |
| Speculative decoding | none |
| Batched multi-request serving | none |
| Quantisation beyond uniform int8 | limited (FP8/FP4/MX formats, per-group scales) |
| Structured + unstructured sparsity | Sparseloop only, and separately from ZigZag |
| Training (fwd+bwd+optimiser state) | PULP-TrainLib only, and not at DSE level |

The consequence: the tools model the workloads of 2019 well and the workloads people are actually
building chips for in 2026 badly. Note that *recent* work (Compass for multi-chiplet LLM serving,
SnipSnap for joint compression-format/dataflow co-optimisation) is appearing specifically to patch
these holes — as separate one-off frameworks, which is G1 recurring.

### G6. System-level effects are absent

- **NoC / interconnect**: Stream models links and bandwidths; nobody models routing, congestion,
  or topology-aware placement properly.
- **Chiplets / packaging**: D2D links, NoP latency/energy, thermal coupling across dies.
- **Off-chip memory**: DRAM is usually a bandwidth number, not a model with banks, refresh, row
  buffer behaviour, or HBM channel structure.
- **Host/accelerator boundary**: DMA descriptor overhead, synchronisation, driver cost. Deeploy
  measures this in reality (<10% overhead on Siracusa transformers) — the DSE tools assume it away.
- **Thermal and power delivery**: entirely absent from L4 tooling, despite EPFL having 3D-ICE
  sitting right there and despite thermal being a first-order constraint for edge and 3D-stacked
  parts.

### G7. The model→RTL gap is never closed

No tool in the L4 group generates hardware. The DSE output is a YAML config and a number; someone
then hand-writes RTL that may or may not correspond. There is no automated check that the RTL you
built is the thing the model evaluated.

Voyager explicitly attacks this and its framing is worth quoting in spirit: prior tools "do not
generate hardware." Gemmini generates hardware but has a narrow architectural template.

**What's actually needed** is weaker and more achievable than full generation: a **conformance
check** — given an RTL implementation and a model config, verify (by simulation on a small workload
set) that measured cycles/energy fall within the model's declared uncertainty band. That closes
the loop without requiring the tool to be a hardware generator.

### G8. Workload IR is the wrong tool for the job

ONNX is a model-exchange format being used as a compiler IR. See [02 §6](02-architecture-teardown.md).
Consequences: permanent operator-coverage treadmill, no affine/loop structure (every consumer
re-derives it differently), no home for hardware-relevant annotations, bad fit for dynamic shapes.

## Tier 3 — Engineering. These determine whether anyone uses it.

### G9. Performance and scaling

- ZigZag has already been rewritten to ~60% C++ — evidence that the Python mapping engine was the
  bottleneck. But orchestration remains Python, so per-candidate overhead has a floor.
- Stream's layer-fusion tile DAG explodes combinatorially with granularity.
- Timeloop's mapper is exhaustive/random/heuristic — fine for a layer, poor for a full model × full
  architecture space.
- Nothing is incremental: change one architecture parameter and you re-evaluate everything from
  scratch, even though 99% of the mapping work is unchanged.
- Nothing is properly memoised across runs, sessions, or users.

**Fixed looks like.** Native (Rust or C++) core for enumeration/evaluation with a thin Python/FFI
shell; content-addressed result cache keyed on `(workload_hash, arch_hash, mapping_hash,
evaluator_version)`; incremental re-evaluation; vectorised/batched evaluation so a search can submit
10⁴ candidates in one call rather than 10⁴ calls.

### G10. Reproducibility and provenance

- Results are files in directories. Provenance is whatever the user wrote in the filename.
- No standard experiment manifest, no environment capture, no seed capture, no lineage between a
  design point and the run that produced it.
- CHIA does substantially better here — automatic profiling of every `@ChiaFunction`, task-graph
  reconstruction, caching/bypass for deterministic replay of nondeterministic LLM nodes — but that
  is provenance of the *flow*, not of the *design artifact*.

**Fixed looks like.** A first-class **artifact store**: every design point is content-addressed and
carries its full lineage (inputs, evaluator versions, calibration id, search strategy, seeds,
who/what proposed it). Deterministic replay of any published result is a single command.

### G11. Installability

The Timeloop/PyTimeloop/islpy-with-Barvinok build is a genuine adoption barrier and pushes everyone
into a Docker image that then becomes the real interface. ZigZag is `pip`-friendly but its C++
component and version coupling to Stream reintroduce friction. CHIA pins **Python 3.10.19** exactly,
to match its container images.

**Fixed looks like.** One `pip install` for the pure-analysis path with prebuilt wheels for the
native core; containers for anything touching EDA tools; no source builds on the critical path for
a new user's first result.

### G12. No agent-facing surface

None of the L4/L5 tools expose MCP tools, structured machine-readable diagnostics, or
schema-validated I/O. An agent driving ZigZag today does it by writing YAML files and parsing
console output — the most brittle possible interface.

Meanwhile CHIA has already built the pattern: `ChiaTool` + fastmcp, where a Python function's
docstring becomes the LLM-facing tool description, and nodes can be exposed programmatically,
agentically, or both.

### G13. No benchmark or leaderboard for DSE itself

There is no agreed set of (workload, architecture-family, objective, constraint) problems on which
search strategies and cost models are compared. Papers each pick their own. Hardware-focused
benchmark suites are appearing (HSCO-Bench, SLDB, RTLLM, ChipBench, ResBench, HLS-Eval), and
CHIA's authors explicitly want to integrate them — but none targets *tensor accelerator mapping DSE*.

## Tier 4 — Agentic-era specific

### G14. Reward hacking is a first-class threat

Documented, not theoretical: AlphaEvolve exploited an improperly-enforced assertion to drop memory
traffic and claim a bogus improvement. In a DSE context, the equivalents are obvious — degenerate
mappings that satisfy the model but violate an unmodelled constraint, architectures that exploit a
cost-model discontinuity, workload slices chosen to flatter a design.

**Fixed looks like.** The evaluator is **not writable by the agent** (CHIA's containerisation model,
enforced structurally); mandatory independent **validity checking** of every candidate against
constraints the cost model does not itself enforce; **holdout workload sets the agent never sees**
(directly borrowing CHIA's Embench-as-holdout methodology, which is what caught their overfitting).

### G15. Confidentiality blocks the highest-fidelity feedback

Proprietary PDKs and IP cannot be sent to public frontier models. CHIA's workaround — open PDKs —
produced results that did not transfer to a commercial node. The stated open problem is *how to
abstract QoR data sufficiently* before it reaches a large model, or alternatively to run capable
small models locally.

**Fixed looks like.** An explicit **abstraction/redaction layer** between evaluator outputs and
model context: normalised metrics, rank orderings, and relative deltas rather than absolute
process-specific numbers; a policy declaring per-metric what may cross the boundary; support for
local model endpoints for anything that cannot.

### G16. Cost is now a design parameter

CHIA reports real numbers: ~$11.72 per iteration for gem5 alignment ($2,356 total over 202
iterations), $202 for a 1.97× iron-law speedup, $5–46 per ISA extension. Token accounting is
dominated by cache-creation and cache-read tokens, not raw input tokens.

No DSE tool has any notion of a compute or token budget as a constraint on search. It should be a
first-class objective: *best design found per dollar*, not just best design found.

## Summary — leverage ranking

| Rank | Gap | Why it's ranked here |
|---|---|---|
| 1 | **G1** evaluator contract | Everything else is downstream of it |
| 2 | **G2** calibration + uncertainty | The only defence against agentic reward-hacking of model error |
| 3 | **G3** missing fidelity rung | Immediate, concrete value to an existing user base (CHIA) |
| 4 | **G5** modern workloads | Determines relevance; cheap relative to impact |
| 5 | **G4** pluggable search | Unlocks stranded prior art (DOSA, CoSA, LOMA) at low cost |
| 6 | **G9** performance | Necessary for agentic scale; well-understood engineering |
| 7 | **G10/G14** provenance + anti-hacking | Cheap if designed in, near-impossible to retrofit |
| 8 | **G6** system effects | High value, high cost — phase it |
| 9 | **G7** RTL conformance | High value; scope down to *checking*, not generating |
| 10 | **G12/G11** agent surface + install | Adoption, not capability |
| 11 | **G13** benchmarks | Do it, but as a community artifact alongside |
| 12 | **G15/G16** confidentiality + cost budget | Real, but tractable as policy layers |
