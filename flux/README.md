# flux

Design and design-space-exploration loops that aim to beat an engineer's result with the
engineer's own tools. A Flux loop takes a stated problem (an FP16 non-linear unit at 800 MHz,
a prefetcher to tune, a bank mapping to prove, a PE to shrink), searches it with real tools on
a chain of rising cost, gives a model one or more NAMED roles inside the loop, and prints a
decision-first report that separates what was measured from what was estimated, what was
established from what was refused, and what remains open. Every loop runs end to end with no
model; the model makes it better, never possible.

Documentation site: <https://choelzl.github.io/flux/> (sources in `../website/`; the catalog
pages are generated by `../website/generate_catalog.py`, docs/decisions.md D387). The plan and
what is still open: [`../docs/loop-review-2026-09.md`](../docs/loop-review-2026-09.md). The
why of everything: [`../docs/decisions.md`](../docs/decisions.md).

## Run a problem

A problem is a DOCUMENT (`applications/<name>/<name>.problem.yaml`) plus the world it runs in
(a package named once under `world:`). Everything enters through `nix develop` (the first entry
builds tools; later entries take seconds):

```bash
cd flux
nix develop --command flux task check applications/nlu/nlu.problem.yaml          # is it answerable, are the tools here
nix develop --command flux task run applications/nlu/nlu.problem.yaml --db demo-nlu.db --tui         # model-paced
nix develop --command flux task run applications/macarray/macarray.problem.yaml --db demo-macarray.db  # ~90 s
nix develop --command flux task run applications/bankmap/bankmap.problem.yaml --db demo-bankmap.db     # ~1 min
nix develop --command flux task run applications/prefetcher/prefetcher.problem.yaml --db demo-prefetcher.db   # ~40 min
nix develop --command flux task run applications/interconnect_mapping/interconnect_mapping.problem.yaml --db demo-imapping.db
nix develop --command flux task run applications/omni/omni.problem.yaml --db demo-omni.db             # params.prompt
```

Another ask in the same world -- other operators, a 1 GHz clock, 16 lanes -- is a copy of the
document with those numbers changed and its own `campaign:`; not a program, not a flag.

- **nlu** and **macarray** measure real silicon: Yosys + OpenSTA to screen, OpenROAD placement
  to confirm, full place-and-route for the NLU's finalists, Verilator for correctness. A stage
  whose tool is absent is skipped and the report says so (`needs:` in the document).
- **prefetcher** needs the three 5G traces (~380 MB, not in git; see
  [`applications/prefetcher/traces/README.md`](applications/prefetcher/traces/README.md)); the
  ChampSim simulator comes from the flake.
- **bankmap** and **interconnect_mapping** need only the default shell (z3 + numpy).
- **omni** is the loop that picks loops: `params.prompt` is the ask, a model plans over the
  introspected tool surface, and running a tool is the measurement (D377, D458).
- A model is an OpenAI-compatible server: `FLUX_LLM_REMOTE=1` with `FLUX_REMOTE_BASE_URL`,
  `FLUX_REMOTE_MODEL` and `FLUX_REMOTE_API_KEY` (D469, D508), or a local Ollama
  (`FLUX_LLM_MODEL`). Without one, the roles a model would fill report themselves skipped and
  the rule-based halves run anyway (D460).
- `--db PATH` is the record: measurements accumulate there, a relaunch resumes from what the
  record already knows, and nothing measured is paid for twice (D367, D510). `--tui` shows the
  loop's roles, the current turn, the timing tree and the front; `f` types operator guidance
  into the next prompt (D388, D391).

Operating a long campaign: `flux status <db> --campaign <name>`, `flux stop`, `flux attach`
(D513); `flux report <db>` writes the campaign report with the fronts per pass, the best so
far and the parts' ledger (D512); `flux migrate` upgrades a record's schema (D524); `flux gc`
removes trace directories no record names.

What a report looks like: a DECISION block first (the thing to build, every number from the
stage the report names), then the front across the objectives, then WHAT THIS RUN ESTABLISHED /
NOT ESTABLISHED / REFUSED with reasons, then the cost. If a run proves the request impossible,
the proof and the nearest feasible answers are the report.

## The shape every loop shares

One loop, `core/loop` (`flux_loop`, D454 onward), runs every problem. The document says WHAT:

```yaml
id: nlu                              # the record is keyed by it
statement: ...                       # the problem, in words a model and a person both read
parts: [recip, rsqrt, ...]           # pieces of one artifact, or "decompose"; or `subtasks:` for child loops
world: flux_nlu.world:World          # the package that knows the domain, named once
params: {ulp_budget: 1, ...}         # what the world is built from
campaign: {name: nlu}                # the record's identity
knowledge: {sheet: knowledge/nlu-methods.md}
objectives:                          # a vector: the first is the goal, the rest break ties
  - {metric: fmax_mhz, direction: maximize, goal: 800, stage: deepest, margin: 0.03}
  - {metric: area_um2, direction: minimize}
ladder: {alone: confirm}             # the improve ladder: sweep, take, import, depth, contender, redesign
stages:                              # the costed chain; `needs:` skips a stage whose tool is absent
  - {name: screen, metrics: [fmax_mhz, area_um2], needs: [yosys]}
  - {name: confirm, metrics: [fmax_mhz, area_um2, power_w], needs: [openroad], timeout_s: 1800}
budget: {steps: 24, repair_attempts: 20, ...}
roles: {orchestrator: rules}         # who fills each of the four roles: a model or a pre-written half
```

and the world says HOW, through the hooks it chooses to implement: `judge` (the gate, never
delegated), `measure` (the tools), `transpile`/`build` (prototype to target), `prepare`,
`knowledge`, `report`. A world-less document -- a gate command, a generator command, a stage
command with a regex -- runs too: [`core/loop/examples/digits.task.json`](core/loop/examples/digits.task.json).

Inside, every pass runs the same phases: the orchestrator picks the work (a part, a batch,
an improve step), the generator drafts (a model with a prototype stage and repair turns, or a
template, a catalog, a solver), the gate judges, the chain measures on rising cost (analytic
stages order, simulated stages decide), the calibration between stages goes on the record,
the winner is decided by the objective vector, and every row carries its provenance (the
revision, the toolchain, the prompt's hash, the seconds, the tokens). Four roles, each with a
model half and a pre-written half, swappable from the document or `--role` (D460):

| role | model half | pre-written half |
|---|---|---|
| orchestrator | `llm`, `agent` (with tools, every pick on the ledger) | `rules`, `given` |
| generator | `model` (prototype, transpile, repair) | `command` (a template or solver), `catalog` |
| evaluator | -- (a surrogate that orders, never decides: plan R9) | the stages' tools |
| knowledge (mentor) | `mined` from the record | the sheet, the library, the record read back |

The discipline that holds it together, each rule citing the decision that paid for it:

- **Measured, not modelled.** A number in a report came from a real tool run, or it is labelled
  analytic. Screened numbers order; confirmed numbers get quoted (D351, D522).
- **A constraint is a refusal, not a low rank** -- below the floor, over the budget, failed its
  golden vectors: refused, with the reason on the record (D352, D362).
- **One vector, one frontier.** The objectives are coordinates; the report lays the trade-off
  out and the vector's own rule picks a point (D511).
- **The model is a participant with a job title** -- proposer, inventor, repairer, orchestrator
  -- judged by the same gates as everything else, told what was measured and refused, and
  never the only path to a result (D287, D355, D460).
- **Resume means the record, read back** (D340, D367, D510): every row carries its provenance;
  the reload re-verifies what it trusts by version.
- **No hand-written designs**: the instruments give the model measurements, never solutions
  (D478, D530).

## Build your own loop

Start from [`applications/bankmap/`](applications/bankmap/) (the smallest complete world: a
space, an exhaustive checker, a solver, a proof, no simulators) or
[`applications/macarray/`](applications/macarray/) (the smallest world over real physical
tools), and read [`core/loop/examples/digits.task.json`](core/loop/examples/digits.task.json)
for a problem with no world at all. Then:

1. **Write the document**: the statement, the parts, the objectives with their goal and
   stage, the stages with what they measure, the budget. `flux task check` tells you what is
   not answerable as written (a metric no stage measures, a missing tool) before a step is
   spent.
2. **Write the world's gate first**: what is a candidate, what makes one invalid, what can be
   refused for free. `judge` is never delegated to a model.
3. **Pick the chain**: which real tool is the screen, which is the confirmation, and in which
   direction the screen is wrong -- then declare the goal on the deepest stage with a margin
   on the shallower ones (D522). Reuse an `evaluator/` adapter or call your tool from
   `measure`.
4. **Wire the shared pieces** (the table below): the cache, the record, the frontier
   arithmetic, `flux_llm` for the model's roles, `flux_knowledge` for what it reads.
5. **Register it**: add `applications/<name>/lib/src` to `flake.nix`'s `localSrcDirs`; a CHIA
   node and its MCP tool over the document if agents should call it (`interfaces/`).
6. **Test the behaviour, not the tools**: unit tests drive the world with a scripted model and
   a fake measurer and pin the ORDER of what it asks for and refuses; tests that need a tool
   are marked `heavy` (`tests/unit/conftest.py`).
7. **Record the decisions**: every non-trivial choice gets a numbered entry in
   [docs/decisions.md](../docs/decisions.md).

## Layout

The tree follows the four module types the architecture is built from, so where a thing lives
tells you what kind of thing it is:

| directory | what lives there |
|---|---|
| `core/` | THE ONE LOOP (`core/loop`), the frontier arithmetic, the IR, the stores, the LLM layer, profiling, the TUI, the report grammar, workload dynamism |
| `evaluator/` | scoring designs with real tools: the ABI and its registry, the adapters (zigzag, timeloop, rtl, openroad; the prefetcher's ChampSim adapter registers there too), calibration, validity, redaction, the measurement cache |
| `generator/` | making code from instructions: the RTL and SystemC harnesses, the harness spec, architecture generation |
| `mentor/` | what guides the rest: the document corpus and its retrieval, mined facts, records read back as laws, operator feedback, protocol specs, benchmarks |
| `applications/` | one folder per design problem: its document, its world package, its README |
| `interfaces/` | how it is driven: the CLI, the CHIA nodes, the MCP server |
| `docs/` `tests/` | the exit-criterion reports; the unit suite (core + heavy), the integration suite, the golden campaign |

`applications/` is the one that grows. A design problem is a document naming its world; adding
one does not change the top level. Six today, each runnable without a model:

| application | the problem | the chain | the model's roles |
|---|---|---|---|
| [`nlu/`](applications/nlu/) | an FP16 non-linear unit of seven operators, each within 1 ULP on all 65536 inputs, composed under one mux at 800 MHz routed with the least area and power | a Python prototype proven exhaustively, transpiled to SystemVerilog, Yosys + OpenSTA screen, OpenROAD placement, full place-and-route for the whole | writes and repairs the prototype, invents algorithms, orchestrates with tools |
| [`macarray/`](applications/macarray/) | the MAC processing element's microarchitecture at a workload's precision | Verilator on golden vectors, Yosys + OpenSTA screen, OpenROAD placement along the fmax-vs-area front | invents multiplier structures beyond the four built in |
| [`prefetcher/`](applications/prefetcher/) | tune, compose and invent ChampSim L2 prefetchers for three 5G traces | validity gate, a 10M+15M screen, confirmation at 100M+150M along the speedup-vs-storage front | proposes knob settings and invents prefetchers |
| [`bankmap/`](applications/bankmap/) | a conflict-free bank mapping for given strides through a given interconnect | pigeonhole or SAT-colouring proof, z3 over XOR folds, an exhaustive checker | proposes mappings past the solver's reach |
| [`interconnect_mapping/`](applications/interconnect_mapping/) | a banked L1's hash and fabric against tensor tiles: two little loops (hash per fabric, fabric fit per hash) under a big one | the exact GF(2) injectivity gate, a cycle law over train and holdout traffic, a four-way front | proposes hashes |
| [`omni/`](applications/omni/) | the loop that picks loops: a prompt, the introspected tool surface, typed plans, replayable runs | the catalog's signature check is the gate; running the tool is the measurement | plans every round |

Evaluators live under `evaluator/` (an application's own, like the prefetcher's ChampSim
adapter, registers in the same registry). The domain LIBRARY they evaluate lives with its
application, because it is not an evaluator. `mentor/knowledge/corpus/` is a corpus of
DOCUMENTS to retrieve from; `mentor/benchmarks/` holds design POINTS with public and holdout
partitions (both were once called "corpus").

There is no `build/` directory: this repository builds no third-party tool itself. Timeloop,
Accelergy, ZigZag, Verilator, Yosys, OpenROAD and Pythia/ChampSim come from the `nixchip` flake
input as `chipPkgs.*`; adding a tool means adding it to nixchip or to `flake.nix` from nixpkgs.

## Where the shared pieces live

Everything a world needs already exists as a package; building a loop is mostly wiring:

| you need | use | from |
|---|---|---|
| the one loop: parts, a prototype stage, a costed chain, the ladder, the record, the roles | `flux_loop.run_loop` over a problem document (D454-D540) | `core/loop` |
| a measurement cache that survives resumes and dies with a tool bump | `MeasurementCache`, namespaced by tool fingerprints (D340/D361); `cache:` in the document | `evaluator/cache` |
| a queryable record of every trial, readable back | `CampaignStore` (schema v2, D524) through `flux_records.Records` | `core/stores`, `mentor/records` |
| the frontier, the knee, the cheapest point meeting a goal, the hypervolume | `flux_frontier` (D362, D368) | `core/frontier` |
| one model call, schema-constrained or with tools, thinking per request | `flux_llm.OpenAIChatProposer -> Reply` (D508) | `core/llm` |
| the mentor's sources: a sheet, a library, the record read back, facts mined | `flux_knowledge.Mentor` + `Corpus`/`Library`/`RecordReadback`/`Mined` | `mentor/knowledge`, `mentor/extract` |
| operator guidance typed while the loop runs | `FeedbackChannel` (D388) | `mentor/feedback` |
| real silicon numbers on ASAP7 | `run_synthesis_flow` (seconds), `run_ppa_flow` (placement or routed) | `evaluator/openroad` |
| Verilator verification of generated RTL against golden vectors | `compile_and_run` + `DesignSpec` | `generator/harness_rtl` |
| the evaluator contract and the backend registry | the `Evaluator` ABI; `make_evaluator(name)` | `evaluator/abi` |
| tool fingerprints for cache keys and provenance | `toolchain_fingerprint` (D316) | `evaluator/abi` |

## Development setup

No venv, no `pip install`; `nix develop` alone gives a working environment:

```sh
cd flux
nix develop --command python3 -m pytest -q tests/unit            # the core suite, ~90 s on 64 workers with -n auto
nix develop --command python3 -m pytest -q tests/unit -m heavy    # the tool-backed tests (yosys, openroad, verilator, z3, ChampSim)
nix develop --command flux --help
```

The unit suite is split (D531): `pytest.ini` deselects `heavy` by default; the heavy files are
listed in `tests/unit/conftest.py`. CI runs both. `tests/integration/` needs whichever real
backend each test targets (Docker for Timeloop, Verilator for the RTL harness, a model for the
prose checks); run the files relevant to what you touch. Every test gets its own trace root, so
a test run never disturbs a live campaign's registration.

`flake.nix` builds the third-party Python dependencies as nix derivations, including
`zigzag-dse` and `chia` (neither is on PyPI). The local `flux-*` packages are not built: the
shell's `PYTHONPATH` points at each package's `src/`, an editable install without a venv.
`evaluator/timeloop` needs a `docker` daemon at runtime and pulls its image on first run;
`nix develop .#timeloop` opts into a hermetic local Timeloop instead (`FLUX_TIMELOOP_LOCAL=1`).

`flake.nix` provides ONE dev shell (`.#python` and `.#physical` are aliases of it): the Python
environment, Verilator, Yosys with the slang front end, OpenROAD and Pythia/ChampSim, as
standalone nixchip packages. The scratch directory the loop writes to is `FLUX_TMPDIR`
(the shell sets it to the shared scratch disk); trace directories live under
`FLUX_TRACE_ROOT` by campaign.
