exploration, sitting between agentic orchestration (CHIA) and the cost-model/deployment ecosystem
(ZigZag, Timeloop, Stream, Deeploy, ...).

## Layout

The tree follows the four module types the architecture is built from, so where a thing lives
tells you what kind of thing it is:

| directory | what lives there |
|---|---|
| `orchestrator/` | deciding what to try next: campaigns, agentic and grid strategies, budgets |
| `generator/` | making designs and code from instructions: architectures, RTL, SystemC, harnesses |
| `evaluator/` | scoring designs with real tools: the ABI, 13 tool adapters, validity, calibration, redaction |
| `mentor/` | knowledge that guides the rest: document corpus, mined facts, protocol specs, benchmarks |
| `applications/` | one folder per design problem: its domain library, its demo, its experiments |
| `core/` | the shared substrate everything depends on: IR, stores, LLM helpers, profiling, frontends, the Rust core |
| `interfaces/` | how it is driven: the CLI, the MCP server, the CHIA nodes |
| `build/` | inputs that build things rather than run them: Nix derivations for third-party tools, backend Dockerfiles |
| `docs/ tests/ experiments/` | records, the suite, cross-cutting studies |

`applications/` is the one that matters for growth. An interconnect study is not infrastructure
and should not sit beside `core/ir/`: it is one problem domain, and the next one gets the same
shape (`lib/`, `demo.py`, `experiments/`) rather than three more top-level directories. Adding a design problem should not change the top level at all.

Evaluators all live under `evaluator/`, including the ones that only make sense for one problem
(`interconnect_struct`, `interconnect_phys`). They implement the same contract and register in
the same registry, so filing them under their application would split a module type across two
trees. The domain LIBRARY they evaluate does live with its application, because it is not an
evaluator.

`build/nix/` cannot move outside `flux/`: the flake is `flux/flake.nix` and Nix can only
reference paths inside the flake directory.

Two names deserve care because they used to collide: `mentor/knowledge/corpus/` is a corpus of
DOCUMENTS to retrieve from, while `mentor/benchmarks/` holds design POINTS with public and holdout
partitions. Both were called "corpus" before, and code pointed at the wrong one during the move.

and ZigZag's `mem_energy_breakdown`, not asserted (see
[docs/calibration-report.md](docs/calibration-report.md)'s Finding 6). Two follow-up hypotheses
that mechanism raised are now both empirically refuted, the second against Timeloop's own real
mapper output: (1) that ZigZag's auto-search simply settled for a worse mapping than a person
would pick — an exhaustive sweep of every hand-designed flat mapping `mapping_translator.py` can
express for this pair never beats the auto-search's own result, and two configurations reproduce
it exactly; (2) that Timeloop's winning mapping needs a structure (e.g. multi-level tiling) this
translator's flat scope can't reach — read Timeloop's real `timeloop-mapper.map.yaml` output,
translated its literal topology (one spatial split, one flat temporal level, DRAM touched exactly
once) into Flux Mapping IR, and ran it through ZigZag: **1666 cycles, not 512**, for the
textually identical mapping. What's left is a genuine cost-model accounting difference between
the two tools, not a search or expressiveness gap. That round trip was then formalized as a real
adapter feature: `evaluator/timeloop/mapping_translator.py` now translates Flux Mapping IR into
Timeloop `mapspace_constraints` (temporal loop order only — spatial mapping stays fixed by the
architecture translator's own `maximize_dims`, verified by round-tripping Timeloop's own winning
mapping back in as a constraint and reproducing its result exactly). Full write-up, including the
earlier and weaker comparisons that led
here: [docs/phase1-exit-criterion-report.md](docs/phase1-exit-criterion-report.md).

## Development setup

No venv, no `pip install` — `nix develop` alone gives a working environment:

```sh
cd flux
nix develop .#python
python -m pytest tests/unit -q
flux --help                       # the flux-cli console script
```

That command now works on its own — **1003 passed, 22 skipped**, no environment preparation. (A count in prose ages the moment a test is added; it is here because the *claim* being made is "this runs with no setup", and a number is how that claim stays falsifiable.)

It did not, until [decisions.md D123](../docs/decisions.md). Seven evaluator adapters
(`thermal`/`dramsim3`/`native`/`booksim`/`noxim`/`cacti`/`gem5`) were missing from `flake.nix`'s
`localSrcDirs`, so this exact command failed with 9 collection errors and every documented test
invocation carried a seven-entry `PYTHONPATH` prefix to compensate. The stated reason was that
these are heavy, build-on-first-use adapters — true of the *backends*, and irrelevant to the
*Python packages*: adding a `src/` path to `PYTHONPATH` clones nothing and builds nothing, and
only actually invoking a backend does. A setup step every caller has to remember is a defect, not
a convention.

`tests/integration/` needs whichever real backend each test targets — Docker for Timeloop, real
local Ollama for the agentic-search suites, `nix develop .#default` for evaluator/rtl's
Verilator tests — so it isn't a single blanket `pytest -q` the way `tests/unit` is; run the
specific files relevant to what you're touching.

`flake.nix` builds third-party Python deps (jsonschema, pyyaml, onnx, pytest, ray, mcp,
pydantic, fastapi, ...) as real nix derivations, including `zigzag-dse` and `chia` itself —
neither is on PyPI/packaged by nixpkgs, so both are built from source, pinned to the exact
versions (or, for `chia`'s dependencies, the closest compatible newer nixpkgs versions — verified
compatible, not assumed, [decisions.md D23](../docs/decisions.md)) this repo is tested against.
The repo holds 31 local `flux-*` packages, and the dev shell's `PYTHONPATH` now wires up all 31
automatically (the authoritative list is `flake.nix`'s `localSrcDirs`). None of them are built as
nix derivations — they're this repo's actively-edited code, and packaging them immutably would
mean a full flake rebuild after every source edit before a test could see the change. Instead the
shell's `PYTHONPATH` points directly at each package's `src/` — equivalent to an editable
install, but it's an env var nix's shellHook sets, not a venv.

`evaluator/timeloop` needs a working `docker` daemon on `PATH` at runtime (not a Python
dependency — see its README for why) and pulls the
`timeloopaccelergy/accelergy-timeloop-infrastructure` image on first run; nixchip doesn't package
Timeloop either. Integration tests in `tests/integration/` actually invoke both real tools —
seconds per test, not milliseconds.
