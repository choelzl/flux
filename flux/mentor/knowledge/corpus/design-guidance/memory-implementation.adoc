= Memory implementation choices: flip-flops, latches, SRAM macros

== Choosing a storage primitive

Guidance, not measurement: on-chip storage is implemented as flip-flop arrays, latch arrays, or SRAM macros, and the right choice is set by capacity, port count, and process — small multi-ported storage favors flip-flops, large single- or dual-ported storage favors SRAM macros, and latch arrays sit between as a power/area compromise that costs verification effort. Quantify any specific case with this repo's real CACTI path (flux_characterize_memory_level) rather than extrapolating from these directions.

A flip-flop array is ordinary synthesized logic: every bit is a register, every read port is a mux tree over all entries, every write port is an enable/mux per entry. Its costs grow with entries x width x ports, but it needs no macro, no special process support, supports any port combination, and synthesis/place-and-route can optimize it with the surrounding logic. For small register files it is routinely the best answer even in ASICs: the SweRV RISC-V core's 32x32 register file with 4 read and 2 write ports is a flip-flop array and occupies roughly 9% of that core's area (public SweRV physical-design material, via T. Verbeure's 2019 write-up — one data point on one core and process, not a scaling rule).

Latch-based arrays replace each bit's flip-flop with a level-sensitive latch plus shared clock/write pulse generation, saving the second storage element of a master-slave flop — typically meaningful area and clock power at the same capacity (direction only; magnitude is process- and library-specific). The cost is design risk: latch arrays need carefully engineered write-pulse timing and are harder to verify with standard static timing flows. They appear in production register files and buffers where the savings justify the engineering; they are a poor default for generated RTL, and this repo's generation paths do not emit them.

SRAM macros amortize storage into dense custom bitcells (e.g. 6T for a single-ported cell) with shared sense amplifiers and decoders, so beyond a capacity threshold — commonly cited around a few hundred to a few thousand bits, but library-specific — they beat flip-flop arrays on area and read/write energy. The trade: macros come from a compiler or vendor library in fixed port configurations (1RW, 1R1W, sometimes 2RW), have fixed synchronous timing, and anything beyond the offered port count requires the composition techniques described under "Multi-port memory techniques" or a custom (expensive) macro. In ASIC flows the macro library is part of the PDK; this repo's ASAP7-based OpenROAD flow places standard cells only, so any SRAM-macro area/energy claim here must come from CACTI characterization, not from the placement flow.

== Port count is a first-order cost on SRAM

Direction with mechanism, not a formula: each additional physical port on an SRAM adds a wordline and bitline (or bitline pair) that must reach every bitcell, growing the bitcell in both dimensions — so bitcell area grows faster than linearly with port count, and read energy grows with the longer, more heavily loaded bitlines. This is why multi-ported register files are famously expensive: the Alpha 21464's 512x64b register file with 16 read and 8 write ports is reported at roughly five times the area of its 64 KB data cache (widely cited figure from the Alpha literature, repeated in Verbeure 2019 — a single historical design point). When a design wants many ports, the usual economical answer is to compose them from few-ported RAMs (see "Multi-port memory techniques") rather than to ask for a many-ported macro.

Latency direction: SRAM access time grows with capacity (longer word/bitlines, deeper decoders), which is why memory hierarchies exist at all — small close storage backed by larger slower storage. For concrete area/energy/latency numbers at a given capacity, technology and port configuration, run CACTI through flux_characterize_memory_level; the numbers it returns carry their own provenance and are preferable to any rule of thumb in this file.
