# demos/ — runnable capability demonstrations

Scripts here drive Flux's own machinery on a stated problem and print a result. Each one RUNS
with no LLM — every candidate can be generated by code, so a demo is reproducible and reviewable
on a machine with no model installed. Where a local model is available, `interconnect_dse.py`
also uses it in two roles, and says at the end what it directed and what it left unexplored
([D287](../../docs/decisions.md)); nothing it produces reaches a results table unmeasured.

## `interconnect_dse.py` — 28 clients, 32 banks, concurrent, area-optimal at >= 600 MHz

```bash
cd /path/to/AEDAF/flux
nix develop .#physical --command python3 applications/interconnect/demo.py            # all 4 rounds
nix develop .#physical --command python3 applications/interconnect/demo.py --rounds 2 # narrow rounds only
nix develop .#physical --command python3 applications/interconnect/demo.py --help     # flags
```

Flags: `--rounds N` (how many steps an UNDIRECTED run takes; a directed one stops when the orchestrator does, bounded by `--max-rounds`), `--budget N` (evaluation grant per round),
`--db PATH` (campaign store; delete it to start fresh, keep it to resume),
`--llm-round N` (let the local model propose N fabrics), `--decide-on-finalists N` (rank the N
best on the vendored core).

Environment:

| variable | effect |
|---|---|
| `FLUX_LLM_MODEL` | which local Ollama tag to use (default `qwen3.8:latest`) |
| `FLUX_LLM_THINK=1` | let a reasoning model think before answering (see below) |
| `FLUX_ESCALATION_WORKERS` | how many fabrics to MEASURE at once (default: cores/4, capped at 8) |
| `FLUX_PROMPT_BUDGET_CHARS` | size of the knowledge block sent to the generator (default 9000) |

The last one is where the wall-clock is. Screening a topology is instant; measuring one runs
OpenROAD, Yosys and Verilator, each a single-threaded process that pins one core
([D290](../../docs/decisions.md)). Measured on this repo's own store, 41 escalations took 12.2
minutes end to end at a median of 17.6 s each, on a machine with 64 cores and nothing else to do.

It REFUSES TO START if `openroad`, `yosys` or `verilator` is missing, naming which and printing
the shell that carries them. That is deliberate and was learned the hard way: run it from the
wrong nix shell and every escalation fails one line at a time while the run continues, and against
a warm store it still prints a full table — of rows measured on some earlier day, with nothing
saying this run measured none of them ([D288](../../docs/decisions.md)).

### If the local model is a reasoning model

qwen3-family models think before answering, and the trace is charged to the same budget as the
answer. Under Ollama's default 4,096-token serving window that is fatal rather than wasteful: the
generator's prompt is ~1,800 tokens of guidance, leaving so little room that every proposal in a
round died mid-thought with `finish_reason="length"`. The demo therefore appends qwen3's
`/no_think` switch by default, measured at 108.7 s -> 36.1 s per call, clean JSON either way.

That is a workaround for a trace that does not FIT, and NOT a finding that reasoning hurts —
whether it produces better fabrics is untested. `FLUX_LLM_THINK=1` restores it, which needs a
serving window with room for it (`OLLAMA_CONTEXT_LENGTH`), and note that systemd's `Environment=`
is space-separated: semicolon-joined assignments are silently swallowed whole, leaving the default
4,096 in place while the unit file appears to say otherwise ([D289](../../docs/decisions.md)).

The problem: 28 clients of 128 bits must reach 32 banks (512 rows x 128b each)
**concurrently**; minimize fabric area subject to a 600 MHz floor.

### Letting the local model propose (optional)

```bash
nix develop .#physical --command python3 applications/interconnect/demo.py --rounds 4 --llm-round 10
```

Adds a round in which the local model (Ollama, nothing leaves the machine) proposes
fabrics of its own, having been handed the problem, this repo's own measured
arity-to-frequency table, and everything measured so far. The enumerated rounds only reach
within families someone wrote down; this one lets the model name structures directly.

The model is on the PROPOSING side and nowhere else. Every fabric it names is built by the real
constructor, routed constructively, screened, placed and simulated with the correctness checks
below, exactly like an enumerated candidate. A bad proposal costs one evaluation and is recorded
as a fallback with its reason; it cannot reach the results table without being measured
([D269](../../docs/decisions.md)).

Measured on `qwen2.5-coder:7b` — named because the numbers below are that model's, not a
claim about whichever model is installed now — given 7,607 characters of catalog and corpus guidance plus 33 facts
mined from its own store: ten proposals, **eight of them hybrids** mixing Clos, radix and
crossbar layers. Three were escalated, taking the table from sixteen measured fabrics to
nineteen — and the model's `hybrid Clos(n=2,m=4) -> radix-8 -> xbar` tops it at **17.5
words/cycle**, above anything the 1,101-candidate enumeration reached.

It can, because hybrids are not enumerable: the deterministic search widens only WITHIN families
someone wrote, and mixing families is exactly the gap a proposer fills. Read honestly, the win
costs 2.7x the area, eight cycles of latency and 21,504 link bits — it extends the frontier at
the throughput end rather than dominating, which is the right kind of contribution from a
proposer whose output everything else then measures.

Two things had to be fixed to get there, both instructive: the model could not keep consecutive
stages' link counts consistent, so it now chooses only switch count and fan-out and the input
counts are derived; and it needed to be told WHY a proposal was rejected before its next
attempt ([D269](../../docs/decisions.md)).

### Is it correct, not just fast?

Every measured fabric is generated as complete SystemVerilog and elaborated and simulated by
Verilator — and since D268 the simulation CHECKS it rather than only timing it. The destination
is derived from the payload, so each bank verifies its own mail (`data mod BANKS == b`); the
payload carries its own complement, so dropped or crossed bits are caught; and the client id
rides along, giving a per-client delivery census that exposes starvation no aggregate number
would show. All families pass with zero misroutes and zero corrupted payloads, at per-client
delivery ratios of 0.86-0.96. A routing failure raises rather than returning a number, and the
evaluator does not catch it into its model fallback — a fabric that delivers to the wrong bank
is broken, not slow.

The negative control is what makes that worth reading: one swapped entry in a crossbar's
last-stage routing table produces 3,269 misdelivered words over 3,000 cycles and fails the
measurement (`tests/integration/test_interconnect_fabric_live.py`).

What is NOT verified: this is behavioural checking under uniform-random traffic on the
generated netlist, not a proof and not a check of the placed silicon (which remains a per-arity
block composition, not one placed fabric). Adversarial traffic and fairness under hotspotting
are untested.

### Resuming a store across a change of method

The store is durable and outlives the code that filled it, so results carry the evaluator's
METHOD version (`interconnect_phys@asap7/m2`). A resumed store whose rows came from an earlier
method has those rows excluded from the final table, counted and named — that is not a
formality: a store from before the shared-width fit reported a radix-32 butterfly at 1012 MHz
and 0.0250 mm2 next to current numbers, and both were wrong ([D268](../../docs/decisions.md)).
Delete the store to re-measure.

### What is measured, and what is modelled

Nothing on the final table is an estimate. Area and frequency come from real Yosys synthesis
and real OpenROAD placement on ASAP7, run per distinct arbitrated-selector arity over one
shared width set (8, 16, 32 bits) and evaluated at 128 — one set for every arity, because
fitting different arities over different widths once produced a 32:1 selector with a faster
128-bit path than a 28:1 one ([decisions.md D265](../../docs/decisions.md)). Throughput comes
from real Verilator simulation of the WHOLE generated fabric under uniform-random traffic
([D266](../../docs/decisions.md)), not from a formula.

An analytic model still ranks the space — a thousand candidates cannot each be placed — but its
error is characterised rather than assumed: exact for a direct crossbar, within ~10% wherever
each destination has one path, and 21% LOW for a Clos at m = n, whose router load-balances
across several valid paths better than the model's assumed random choice.

### Convincing yourself it is Flux doing the work

The script contains no evaluation logic. Its entire interaction with the system is four
function calls — `flux_campaign_start`, `flux_campaign_step`, `flux_campaign_status`,
`flux_campaign_frontier` — which are exactly the functions exposed as MCP tools:

```bash
grep -n "flux_campaign_\|flux_chia_nodes" applications/interconnect/demo.py   # the only entry points
grep -n "OllamaLLM" applications/interconnect/demo.py                          # one call site, one role
```

The model appears exactly once, in `local_model()`, and both roles go through it: it DIRECTS the
search and it PROPOSES fabrics. Neither role can measure, score, or admit anything. A model that
returns nonsense costs a step its direction or a proposal its slot, and the run continues on the
fixed plan — which is why the same script produces a full result on a machine with no model at
all.

Everything else — enumerating the space, screening, choosing contenders, escalating to real
tools, applying the frequency constraint, building the frontier — happens inside Flux. The
campaign store is the evidence and it outlives the run:

```bash
# the frontier, re-queried independently through the same tool the demo used
nix develop .#physical --command python3 -c "
from flux_chia_nodes import flux_campaign_status, flux_campaign_frontier
from flux_store import CampaignStore
import json
db = 'demo-interconnect.db'
for row in CampaignStore(db).list_campaigns():
    print(row['campaign_id'][:16], row['status'])
    print(json.dumps(flux_campaign_frontier(db, row['campaign_id']), indent=2)[:800])
"

# every measured number's provenance: which evaluator, which blocks, which fit widths, and
# how throughput was obtained (verilator, with the model's prediction alongside it)
nix develop .#physical --command python3 -c "
from flux_store import CampaignStore
s = CampaignStore('demo-interconnect.db')
for row in s.list_campaigns():
    for t in s.ok_trials(row['campaign_id'], phase='escalate')[:2]:
        print(t.candidate['label'], t.result.provenance.evaluator)
        for k, v in t.result.provenance.inputs.items(): print('   ', k, '=', v)
"
```

The rerun is cheap and honest: a second run resumes the same store, and anything already
measured comes back as a cache hit rather than a fresh place-and-route. A cold run is not
cheap — every distinct selector arity costs three real place-and-route jobs — so budget
roughly 35 minutes for a cold run that covers every family.

### What a round enumerates, and how much it actually covers

A round enumerates one FAMILY of the space, at full depth and breadth. The families are disjoint,
so which ones were covered is a claim that means something:

| family | candidates | reaches |
|---|---|---|
| `staged` | 7,272 | crossbars and parallel-switch fabrics over every interesting rank |
| `clos` | 90 | three-stage C(n, m, r), at the published thresholds and between |
| `hybrid` | 37 | one family feeding another, which no single family expresses |
| `butterfly` | 11 | radix-R networks the port count admits |
| `router` | 9 | ring, mesh and torus |

This replaced a WIDENING scheme of `narrow`/`wide` breadth at up to 2, 3 or 4 stages, and the
reason is worth stating because it looked reasonable for a long time
([D308](../../../docs/decisions.md)): those six scopes NESTED. Every one was a strict subset of
`wide/4` with zero candidates unique to it, so choosing between them was a budget decision rather
than a search decision, and the coverage line was wrong in both directions — a run enumerating
`wide/4` alone reported "1 of 6" while covering the whole space, and one doing the two narrow
scopes reported "2 of 6" while covering 2.4% of it.

The family sizes are wildly uneven: `staged` is 98% of the candidates. That is a real property of
the space rather than a bug, but it means a round's cost depends heavily on which family it picks,
and splitting `staged` into disjoint depth bands is an obvious follow-up that has not been done.

### The result (all numbers measured, ~40 minutes cold)

Sixteen fabrics meet the 600 MHz floor; thirty-one do not. Re-measured after
[decisions.md D278](../../docs/decisions.md), which found that the synthesis flow had never
been asked to optimise for timing — every earlier number in this file came from a netlist with
minimum-effort technology mapping, no timing-repair pass, and a wire-RC setting that was
silently a no-op. Selectors came out ~35% smaller and 20-30% faster, and the whole table moved
with them.

| topology | area mm2 | fmax MHz | served/cycle | link bits | cycles |
|---|---|---|---|---|---|
| staged 14x(2x3) -> 2x(21x16) | 0.0278 | 600 | **17.3** | 5,376 | 4 |
| staged 7x(4x8) -> 8x(7x4) | 0.0212 | **871** | 17.1 | 7,168 | 4 |
| Clos C(n=2, m=3) | 0.0375 | 683 | 16.2 | 12,288 | 6 |
| staged 2x(14x16) -> 16x(2x2) | 0.0212 | 683 | 16.2 | 4,096 | 4 |
| staged 14x(2x2) -> 2x(14x16) | 0.0206 | 683 | 15.7 | 3,584 | 4 |
| staged 15x(2x2) -> 2x(15x16) | 0.0200 | 683 | 15.7 | 3,840 | 4 |
| butterfly radix-8 | 0.0195 | **871** | 15.3 | 4,096 | 4 |
| staged 7x(4x4) -> 4x(7x8) | 0.0153 | **871** | 14.9 | 3,584 | 4 |
| staged 5x(6x4) -> 4x(5x8) | 0.0128 | 871 | 13.0 | 2,560 | 4 |
| staged 3x(10x4) -> 4x(3x8) | 0.0104 | 785 | 9.9 | 1,536 | 4 |
| staged 2x(14x4) -> 4x(2x8) | 0.0088 | 707 | 7.4 | 1,024 | 4 |
| **staged 2x(14x2) -> 2x(2x16)** | **0.0065** | 683 | 3.9 | 512 | 4 |

(twelve of the sixteen shown; the rest sit between.) Latency is four cycles rather than two
because the generated switch is pipelined into a decode stage and an arbitrate-and-mux stage
([D273](../../docs/decisions.md)) — the evaluator reports two cycles per stage, which it did not
before that pipeline existed.

What the table says, read as an answer rather than a list:

* **There is no single best fabric, there is a curve.** The qualifying set runs from 3.9
  words/cycle at 0.0065 mm2 to 17.3 at 0.0278 — a 4.3x area span buying a 4.4x throughput span,
  very nearly linear. Which point is right depends on the offered load, which the problem
  statement deliberately did not pin down.
* **Frequency stopped being the binding constraint.** Under the old flow only eleven fabrics
  cleared 600 MHz and the fastest managed 754. Now sixteen clear it and three sit at 871, so the
  interesting question moved from "what can close timing" to "what is the cheapest structure at
  the throughput I need" — which is the question worth asking.
* **The classical answer is still dominated.** Clos C(n=2, m=3) delivers 16.2 words/cycle for
  0.0375 mm2, 12,288 link bits and six cycles; the discovered `2x(14x16) -> 16x(2x2)` delivers
  the same 16.2 for 0.0212 mm2, 4,096 link bits and four. Same throughput, 56% of the area, a
  third of the wiring, two cycles shorter. Clos earns its reputation on circuit-switched
  non-blocking guarantees, and this problem does not ask for those
  ([decisions.md D267](../../docs/decisions.md)).
* **The fabric named for comparison is also the frequency winner.** `7x(4x4) -> 4x(7x8)` — the
  structure handed in via `extra_variants`, and independently rediscovered by the wide rounds —
  closes at 871 MHz for 0.0153 mm2 at 14.9 words/cycle. Two other fabrics reach 871 with it, so
  there is real headroom above the 600 MHz floor to trade back for area.
* **A vendored switch does better still.** Rebuilding that same fabric on the vendored PULP
  `xbar_varlat` core instead of the generated switch measures 737 MHz at 0.0154 mm2 and 67.8 mW
  against the generated 622 MHz at 0.0209 mm2 and 72.9 mW — 18% faster, 26% smaller
  ([D279](../../docs/decisions.md)). The search still ranks by the generated selector, so this
  is available for verification rather than driving the choice.

### The decision rung — and why the screen may not make the call

```bash
nix develop .#physical --command python3 applications/interconnect/demo.py --rounds 4 --decide-on-finalists 8
```

Everything above this point is a SCREEN. The decision rung places each finalist WHOLE, on the
vendored PULP `xbar_varlat` core rather than this repo's generated switch, and ranks on what
that measures ([D280](../../docs/decisions.md)). It changed the answer:

| topology | mm2 | MHz | mW | served | cyc | screen said |
|---|---|---|---|---|---|---|
| hybrid Clos -> radix-8 -> xbar | 0.0489 | 430 | 135.0 | 17.5 | 8 | 0.0748 mm2 |
| staged 14x(2x3) -> 2x(21x16) | 0.0249 | 501 | 73.0 | 17.3 | 4 | 0.0278 mm2 |
| staged 7x(4x8) -> 8x(7x4) | 0.0189 | 575 | 86.2 | 17.1 | 4 | 0.0212 mm2 |
| Clos C(n=2, m=3) | 0.0281 | 542 | 98.5 | 16.2 | 6 | 0.0375 mm2 |
| **staged 2x(14x16) -> 16x(2x2)** | **0.0182** | **600** | 79.1 | 16.2 | 4 | 0.0212 mm2 |
| staged 14x(2x2) -> 2x(14x16) | 0.0181 | 599 | 56.5 | 15.7 | 4 | 0.0206 mm2 |
| staged 15x(2x2) -> 2x(15x16) | 0.0180 | 685 | 56.3 | 15.7 | 4 | 0.0200 mm2 |
| butterfly radix-8 | 0.0174 | 739 | 72.5 | 15.3 | 4 | 0.0195 mm2 |

**DECISION: `staged 2x(14x16) -> 16x(2x2)`** — 16.2 words/cycle at 0.0182 mm2 and 600 MHz
(79.1 mW), 892 words/cycle per mm2, the best ratio among finalists that clear the floor on
placed silicon.

Three things this makes visible that no screen could:

* **Only three of the eight clear 600 MHz once placed whole.** The composed rung's frequencies
  come from selectors measured in isolation; placing the fabric adds every wire between them,
  and half the shortlist loses the floor.
* **The screen's favourite is disqualified.** The hybrid the local model proposed tops the
  throughput table at 17.5 words/cycle and places at 430 MHz — the slowest of the eight. It is
  a real fabric and a real proposal; it is not buildable at this frequency.
* **The decision lands fifth on the screen's own ordering.** Which is the argument for having a
  decision rung at all: a screen that mis-ranks is still useful for pruning a thousand
  candidates down to eight, and must not be the thing that picks one of them.

Composed area, for its part, is consistently HIGH — 0.0212 mm2 screened against 0.0182 placed —
because composition multiplies a standalone block's periphery by count where synthesis optimises
across the whole design.

One candidate errored rather than being rejected: `28x(1x4) -> 1x(112x32)`, whose 112:1
selector OpenROAD could not place. The campaign recorded the error, kept its budget accounting,
and carried on — a failed tool run is data, not a crash.

The memory being served is 32 banks x 512 rows x 128b = 0.0765 mm2 (real CACTI, scaled to 7nm
against a published bitcell floor, [D255](../../docs/decisions.md)/[D256](../../docs/decisions.md)),
so the highest-throughput fabric costs 42% of the memory it feeds and the smallest costs 15%.
