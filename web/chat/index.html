    Chat¶

    Chat, in the top bar, is a conversation with an agent or FluxAgent that belongs to no loop. Ask it about your loops, a paper, an idea; let it write a script or keep notes for next time. It is there when an admin gives it to you (Admin › Chat).

    The page¶

    Your chats are in a slim rail at the left and the open conversation is in the middle. The Settings panel opens at the right from the Settings button at the top right.

    • New chat starts one. The rail groups chats under Today, This week and Older. A chat whose answer is still being written shows a spinner. ✕ hides the rail and ☰ brings it back.
    • A chat's ⋯ menu, shown on hover and for the open chat, has Rename… and Delete…. Deleting removes its messages and answers; the workbench stays.
    • Open any chat to go on with it: each answer reads the conversation before it.

    Your messages are on the right and answers under them. Under each answer one line names the agent and how long it took, and Thinking & commands shows how the answer was made, as in a loop's Chat. When an answer writes or changes files in the workbench, they are listed under it (↳ designs/adder8_csel4.sv). Click one to open it in the panel.

    The message box stays at the bottom. Enter sends and Shift+Enter starts a new line (Ctrl+Enter and ⌘+Enter send too). The agent is picked inside the box, from the agents offered for Ask, with your own agent settings (Models and agents). A small ! beside it means the agent is not ready (its connection untested, failed, or changed since its test); click it for Test and Set up.

    Think, beside the agent, asks for a slower, more considered answer: FluxAgent reasons before it answers, its thinking shown live in Thinking & commands; a coding agent works at its effort for thinking, and off, at its effort for not (by default its own, and its kind's lowest: Claude Code --effort low, Codex model_reasoning_effort="minimal", OpenCode --variant minimal). Think follows the agent picker: each agent starts as the admin set it (thinking by default) -- every agent on, FluxAgent off unless said -- and your browser remembers your own choice for each agent. A loop's Chat has the same switch. A thinking model that answers nothing is asked again without thinking.

    While Think is on, Effort beside it picks how hard a coding agent reasons for this message: the levels its kind takes (Claude Code low to max, Codex and OpenCode minimal to their top; an agent added under a name of its own by its kind), default its effort for thinking. It is sent with the message (flux chat|consult --effort), comes first -- before Think, the loop's box and the admin's default -- and your browser remembers it per agent.

    FluxAgent has an Effort too, shown whether Think is on or not: one dial over its thinking, its tool rounds and the length of its answer. default is its effort for Think as set (Admin › Agents: built in medium not thinking -- the answer as before -- and high thinking).

    Effort Thinks Tool rounds Answer up to (tokens) Also
    low no 6 3000
    medium no 20 6000
    high yes 30 10000
    max yes 50 16000 re-reads its draft against the question and what its tools found, and fixes what they do not back (one more call)

    Thinking, it asks for the matching reasoning level (reasoning_effort low, medium or high; high at max) where the endpoint takes levels -- asked once per endpoint and model, and left out where refused.

    Attached files¶

    Attach files to a message with the paperclip beside the agent, by dropping them on the conversation, or by pasting (a screenshot too, named pasted--.png). Each is sent at once: a chip above the box shows its name and size (its progress while it goes), and ✕ removes it. The files go with your next message and show as chips under it; click one to open it (a text highlighted, a picture shown) or download it. Any type is kept as it is. The admin sets the largest file and how many go with one message, 50 MB and 10 unless set otherwise (Admin › Chat).

    Where they are kept: with the chat's workbench on, in the workbench's uploads/ (kept across your chats, listed under Settings › Workbench); with it off, with the answer, in its folder's attached/. A name already taken gets a number, notes (2).md: nothing is overwritten.

    The answer's brief lists them where its answerer reads them. A coding agent opens them with its own tools (/workbench/uploads/... in its sandbox), pictures too where it reads images. Flux's own model reads a text file as it is, and a document as its text: a PDF through pdftotext (when the server has poppler), Word, Excel, PowerPoint and OpenDocument files directly. The first part of each text is in its brief and read_file reads the rest. It cannot see a picture or read another binary file; its brief says so, and it says so too when the answer depends on one.

    In a loop's Chat (the loop's page, or a loop chat here) files attach the same way, for whoever may ask about the loop. They wait in your own folder until the question is sent, then live with its answer, never in the loop's own folders. To put a file in the loop's library, use the loop's Files upload, or accept a chat's proposal.

    A coding agent's answer has limits of its own, 8 minutes and 40 tool calls unless the admin set others (Admin › Chat), and it ends as soon as the agent has written its answer and goes quiet, repeats itself or only updates its plan.

    Your answers run in a sandbox of your own, kept between messages for a while (30 minutes unless the admin set otherwise, Admin › Chat): the next answer starts sooner. When the admin changes what it runs with, or Flux is updated, an answer being written is written again on the new settings; its row says restarted: … and why, your message is not sent twice.

    One answer is written at a time in a chat. Your message shows at once (Sending…). While the answer starts, the row says what is starting: Starting the sandbox…, Preparing the brief…, then Starting OpenCode… (the agent's name). That takes a few seconds, more on a busy server, and is never an error. Once the agent works, the row shows what it is doing now (its latest command, or thinking…) with Stop. Only an answer that ended without answering shows a red notice. An answer stopped after the agent wrote it is kept, marked Stopped before it ended, with its question if it asked one. An answer that fails says why (a rate limit, say) with Ask again, which sends the same message again, to the same agent. When you open a chat, the box starts with the agent of its last answer.

    Loop chats¶

    Under your chats, the rail folds Loop chats: the conversations held in each loop's own Chat panel, for every loop you can read (yours and those shared with you), one fold per loop that has any. A fold lists the loop's conversations newest first, each titled by its first question, with a count when it has several messages. Whether Loop chats and each loop's fold are open is remembered by this browser.

    • Click a conversation to open it in the middle, with the loop's name as a small tag in its head. It reads as a chat does: Thinking & commands under each answer, Stop while one is being written, and the loop agent's open question on its card while the loop runs. Write in the box to continue it. The answer comes from the loop's own Chat, so the same rules apply: one answer at a time per loop, an agent that reads the loop and changes nothing, and only people allowed to ask about the loop can ask there. Someone you shared the loop with without Ask can read its conversations but not ask, and a conversation asked privately (by someone who may not edit the loop) is shown only to them.
    • Open in NAME opens the loop's page with its Chat panel on that conversation.
    • + New chat on NAME, last in a loop's fold, starts a conversation on that loop. + Chat on another loop does the same for a loop with no conversations yet.

    Questions¶

    Most answers ask nothing. An agent asks only when it cannot go on without your choice or a value only you know, never to offer more help or to ask permission (a "Would you like me to…?" after a long answer is dropped, and the turn's log says so; so is a question that only says your message back, or asks again what you just answered). The question then ends the answer, shown as a card under it. An answer may ask up to four questions at once; each has a short header, and the headers are chips at the top of the card (✓ Type · Widths · Target, 2 of 3) that move between them. Each question shows

    • its options, one per line: a label, a line on what it means, and Recommended on the one the agent would pick (listed first); pick one, or any for a question that takes several;
    • named values it needs, such as a width or a library, as text, number or list fields;
    • Other, for anything else in your own words (for a free question, the only box).

    1–8 pick an option and Enter goes on from anywhere in the card: to the next question, then Send. Next › and Back move too. Send stays off until something is answered; in a card of several, a question left blank is the agent's to decide. You decide lets the agent choose them all and say what it chose.

    Your answer goes as one message, to the agent that asked (whichever agent is picked in the box), written plainly, a block per question:

    Answer to: Which adder families should adder16's generator try?
- choice: carry-select
- choice: Kogge-Stone

Answer to: Which cell library?
- choice: sky130
keep it small

    Your message then shows the answers as chips (Families carry-select, Library sky130), and the card shrinks to what was asked. A chat waiting on your answer is marked ? in the rail. Typing a message in the box instead also answers the question.

    A coding agent asks by writing question.json in its folder; FluxAgent ends its answer with a fenced question block, which is taken out of the answer. Either way the questions are

    {"questions": [{"header": "Width", "question": "...", "kind": "one" | "many" | "text",
                "options": [{"label": "...", "detail": "...", "recommended": true}],
                "fields": [{"name", "label", "type": "text" | "number" | "choice", "options"}]}],
 "why": "..."}

    with at most 4 questions, 8 options and 5 fields each. One question alone, {"question", "kind", "options": ["..."], "fields", "why"}, is read too. Claude Code may ask with its own AskUserQuestion tool instead: when its turn calls it, the call becomes the card (its options' descriptions their detail lines) and the turn ends there.

    The server checks every question: one longer than 200 characters asks with its last asking sentence (the rest becomes its reason), an "Other" option is dropped (the card has its own box), and one that is malformed is shown as its text, with a box for a free answer. After You decide, the next answer reads that you delegated the choice, and decides.

    Actions¶

    An agent never changes your loops itself: in its sandbox they are read-only. When you ask for a change, or one clearly helps, it proposes it, and each proposal is a card under the answer: what it does and in which loop, why, and a preview. Accept makes it, as you, with the same checks and the same audit trail as the page that does it by hand; Reject drops it. Each proposal is answered on its own; nothing is made without your click. The card then says Done (and what was done), Rejected, or Refused with why. The next answer reads what became of each proposal.

    Kind What it does Its preview
    Library copies files from your workbench into the loop's library/ (papers, notes its agents read) each file, its size and where it goes; replaces when it overwrites one
    Document writes a text file (.md, .txt, .rst) under the loop's library/, where its agents read it; a lesson (what a run taught) goes under library/lessons/ the text, or the change to the file it replaces
    Note sends a note to the running loop, as its Notes box does the note
    Hidden from AI hides paths from the loop's agents, or shows them again (Hidden from AI) the hidden paths before and after
    Idea adds an idea to the loop's notebook its title, hypothesis and test
    Queue queues an idea for testing, or takes it off the queue the idea and its place in line
    Merge ideas merges ideas that say the same thing, as the notebook's cleanup does (it can be undone) the idea kept and those merged into it
    Design note pins a note on a design, shown in Results' design detail and in Live's inspector the design, its numbers, the note
    Reference marks a design as a reference for comparison the design and its numbers
    Settings changes settings of the loop's problem document -- its budget, who works a box, its model, anything the Configure page sets -- saved as the Configure page saves each setting now and proposed; when it takes effect
    Problem document replaces the text of the loop's problem document (its flow, checks, measurements), saved as Direct edit saves the change, line by line; when it takes effect
    Measure again measures a design again (a flaky timeout, a tool that failed), as Results' Reject with Measure again does the design, its numbers, the stages, and when it is measured

    A note on a design and a reference are for reading only: the loop's decisions, its baseline and its search do not change. A loop reads its problem document when it starts: a Settings or Problem document change reaches a running loop at its next start (Restart starts it again after the pass it is on), and the card says so. Either is proposed only when the document would still load (as Check and flux task check load it); one that would not is refused with the loader's words, and one proposed on a document changed since is refused on Accept, nothing written. Saving settings drops the document's comments, as the Configure page's save does. Until a design is measured again its numbers count as rejected: shown, never chosen; a running loop measures it before its next pass, a loop at rest starts a run of its own. Files the agent brings (a paper it downloaded) go to your workbench first, and the proposal names them there.

    The server checks every proposal, when the answer ends and again when you accept it: a loop you own or one shared with you with Edit, not archived. A loop you may only view or ask about gets no proposals at all: the agent is told which loops it may change, and anything it proposes for another is dropped, never shown. Then, the files in your workbench and at most 64 MB each, never an overwrite unless the proposal says so, the problem document only as Settings or Problem document. A coding agent proposes by writing actions.json in its folder; FluxAgent ends its answer with a fenced actions block, which is taken out of the answer. Either way a list of at most 10:

    [{"kind": "library.add", "loop": "bob/adder8", "files": ["papers/fast-adders.pdf"], "why": "..."},
 {"kind": "idea.add", "loop": "bob/adder8", "title": "...", "hypothesis": "...", "test": "..."},
 {"kind": "loop.settings", "loop": "bob/adder8", "set": {"budget.passes": 3}, "why": "..."},
 {"kind": "design.recheck", "loop": "bob/adder8", "design": "adder8#3", "why": "its fmax read a timeout"}]

    Settings¶

    The panel's Uses says what this chat's answers may use:

    Switch On
    Loops The agent may read your loops: your own, and those shared with you with Ask. The line says how many.
    Workbench The agent may read and write your workbench.
    Network The agent may reach the hosts the admin allows for chat, or any host when the admin opens it. Off, it has the sandbox's base allowlist only, which agents need to work. The line says which.

    A switch the admin keeps off is greyed, and its line says why. Make these my defaults has new chats start with the current switches. Each answer uses the switches as they were when you sent the message.

    In focus (with Loops on) picks one loop from a list you can search, with your loops under Yours and the others under Shared with you. Its record is copied for the answer. FluxAgent asks it with its flux_loop commands first, and queries the copy with the same read-only sql tool as in a loop's Chat only for what no command can say. FluxAgent has no web tool. A coding agent uses its own web tools, within the network the chat allows.

    FluxAgent reads no files. With no loop in focus it sees each of your loops' records in a few lines (its objective, how many passes and measurements, its baseline, the best design at each stage and the first objective against the baseline, its last decision), and when an answer needs more it says so and suggests putting that loop in focus. The loop in focus comes with its baseline and how far the best design and the standing pick are from it, objective by objective.

    Under Uses is the workbench (see below).

    The panel is closed until you open it with the button at the top right (the loop in focus · Settings), and it stays open or closed as you last left it in this browser. Opening a file an answer wrote opens it too. On a wide screen it sits beside the conversation; narrower than about 1360 px it opens over the conversation. On a phone the conversation fills the screen, ☰ opens the chats, and the panel takes the whole screen.

    Your loops, read-only¶

    With Loops on, every loop you may read is mounted read-only in the answer's sandbox, at /loops/<owner>/<loop>. That includes archived loops and loops shared with you with Ask (a loop you may only view is not there). Another user's loop is never there unless it is shared with you, even for an admin. Each loop's folder has its document, its record and results (out/), its log (runs/loop.log) and its workbench. LOOPS.md, in the answer's folder, lists them with these paths. A coding agent reads a loop with Flux's own read-only commands first -- flux loop summary --loop <its document> (the baseline, the best per objective and the standing pick against it), passes, results, compare, tried, show NAME, events, ideas, notes -- and queries the SQLite record itself last, only for what no command can say.

    The questions people ask most are each one command. results ranks the designs at a stage with every metric, a dictionary metric's cases as metric.case (--metrics sim_lost keeps a metric and its cases); --by sim_lost_w ranks by one metric alone; --goals keeps the designs that meet every limit, --stage all shows each design at every stage it reached, --match swizzle keeps those whose text, idea or rationale says the word. compare #6 #12 puts designs side by side, metric by metric, the best on each objective marked. tried --gate consistent lists the designs a stage or a check stopped, with why. events --kind decision reads the record's decisions, conclusions and notes; without --kind it counts each kind.

    FluxAgent, which runs no shell, has these as tools: flux_loop runs the same read-only commands on a loop of this chat (summary, passes, results, compare, tried, show, events, design, diff, ideas, notes, library, digest, with the same filters), and list_files and read_file read the loops' folders, the workbench (read-only for it) and the answer's own folder -- nothing else: a path that leads elsewhere, through a link too, is refused, and so is a file a loop hides from AI (Hidden from AI) and another person's conversation about a loop. With a loop in focus it also queries that loop's record (sql), last: its brief and its tools say the commands first. Each query it ran is kept in the answer's folder (sql.jsonl), and asking the same query twice in one answer is not run again. Each call and what came back is in Thinking & commands. A loop's Chat gives FluxAgent the same tools on that one loop.

    The workbench¶

    The workbench is one folder for all your chats. Agents keep their tools in tools/, notes in notes/ and drafts in drafts/, so a later chat can use what an earlier one made. Chat does not create or run loops: a loop starts from New loop, and a draft for one (a document, a generator) waits in drafts/. In the sandbox it is /workbench; nothing else outside the answer's own folder is writable.

    The panel's Workbench shows it as a tree: a folder opens in place, and a file opens in place of the tree, read-only, with Download, Delete and ⛶ Fullscreen. A text is highlighted as in Files, and a picture (PNG, JPEG, GIF, WebP, SVG) is shown. ‹ Workbench goes back. Refresh reads it again; it is also read again when an answer ends. Each answer records the workbench files it wrote: those its agent's writing steps name, and any other file made or changed while it ran. When another of your chats was answering at the same time, a file no step of this answer names may be the other's: it is dimmed, changed meanwhile.

    Where it is kept¶

    On the server, under users/<you>/chat/: workbench/, and chats/<id>/ for each chat; files attached but not sent yet wait in pending/, outside the folders a sandbox mounts. Your chat sandbox has the chats/ folder at /chats and the workbench at /workbench: an answer's agent can read and write your other chats' folders as well as its own. So nothing the server acts on is taken from there: which process Stop ends, or a restart starts again, is the server's own record of what it launched (kept outside every sandbox, each process checked by its start time), never the pid a message's turn.json shows. A chat's folder holds its name, its switches and one folder per message: the message, the answer, the agent's turn, its log, the files attached to it (attached/, and attached.json naming each one, those in the workbench's uploads/ too), the workbench files it wrote, the question it asked and its proposals with what became of them. Creating and deleting a chat is in the audit trail, and so is each accepted proposal (from chat).
