    Files and settings¶

    Files¶

    A loop's Files tab shows its folder four ways, each a view in the row under the tabs with its count: Workbench, Library, Inputs and All files. Every file of the loop is in one of the first three, or in what they leave out: out/ and runs/ (what runs write), the document (its place is Settings › Problem) and what All files hides unless asked. On a phone each view lists first; a file opens on its own, with ‹ Back to the list.

    Workbench¶

    The agents' own folder, workbench/: a search over names and first lines, then Overview (the setup's workbench/README.md, opened first when there is one), Tools (five shown, then "N more"), the notes by age (Today, Yesterday, This week, and Older folded with its count), Numbered notes -- notes named one name and a number (draft1297-…, orch-pass12-…), three or more of a name, folded into one row with their count and the newest's age -- and Other for the rest. Each row is a file's name, its age and its first line; it opens in the same viewer as All files (edit, save, download, Actions).

    Library¶

    What the agents read: the loop's own library/, one row a document (its kind -- PDF, MD, SRC for a folder of source code -- its title, its pages, lines or files), ✓ digested once the setup's model has digested it, not relevant when its digest says it does not bear on the problem. N of M digested sums it up; a search filters the list; ↻ reads it again and {} shows the digests as recorded. + Add a document opens the uploader: files and folders dropped or chosen go into library/. Each project library the loop reads (library/<project>@<group>/) follows as its own group, read-only, Library › opening the project's Library tab. Digests of files outside the library (the loop's notes, its knowledge files) are listed under Also digested, and so are the digests of files no longer in the library: a paper deleted or moved, a project library the loop no longer reads.

    The record keeps a digest whatever happens to its file, and the prompts read every digest it keeps. To remove the digests of files that are gone, open one and use Delete (the bin) on its head, or Delete all N on the group's head; either asks first. Only those can go: a digest of a document still in the library, or of a knowledge file still there, stays -- it is what the prompts read. A running loop need not be stopped. Put a file back and the next pass digests it again, from the copy kept of its digest (no model call when its text and the problem are the same). Deleting needs Edit on the loop, and is in the audit log.

    Open a document and it shows beside the list: what it is, Download and Raw, Actions on your own, then its Digest (the text the prompts read, who made it, how much it read, from where) and its Outline -- its sections with their pages or lines, read as flux library outline reads them (a PDF needs pdftotext on the server; without it the outline says so). A folder shows its files.

    Inputs¶

    Everything else the loop was given: In the problem -- the files and folders the document names beside it (its golden model, the files of its commands, the files its knowledge library lists, its sub-loops), as the loop's own check reads them -- then Skills (a skills/ folder, or the one the document's skills names) and Other. A folder whose files all belong to one group is one row; a lock marks what is hidden from AI. Its foot names the document and links Settings › Problem.

    Large folders¶

    The three views stay quick on a loop of hundreds of thousands of files. A folder of the workbench holding more than 500 files (but tools/ and notes/ themselves) is one row, data/ with 12345 files and its newest change; it opens as a folder. A list shows at most 2000 rows, newest first in the workbench; the rest are counted -- "102 more older files not listed here · All files". The counts in the sub-row are of every file. Nothing behind a link, nor another file system mounted in the loop, is walked; a dot folder, __pycache__ and a folder .gitignore ignores are not entered. The views are kept while the folder stands as it was: opening the tab again is instant, a change made here shows at once, and one made by a running loop shows on the next look (on a very large loop, on the look after: the views are made again in the background).

    The configurator's Files (under Prompt) and its Library's list read the loop's files the same way: a folder holding more than 500 files is one row, build/ with 12345 files and its size; click it and its files are listed in its place (its own large folders folded in turn), and it stays open while you edit. library/, skills/ and each skill's own folder are never folded, so every paper and each SKILL.md stays listed. Neither the document nor what .gitignore ignores is listed (as before), and a folder .gitignore ignores is not entered. The counts (the Prompt card's, the Library's folders) are of every file. The list is kept while the folder stands as it was; a file saved, added or deleted here shows at once.

    All files¶

    The folder as it is: the document, your scripts, library/, the workbench and what Flux writes (out/, runs/). Open a file to view, edit, save or download it; Raw and Fullscreen show the whole of it. Drop files or folders onto the list, or use Add files and Add folder.

    • Actions on a file or folder: Rename…, Move…, Delete…, and Hide from AI (or Show to AI), which adds the path to knowledge.hidden (Knowledge, skills, hidden paths).
    • A name with @ at the top of library/ is refused (when adding, renaming or moving): that is where a project's library appears, library/<project>@<group>/.
    • Under library/, after the loop's own folders, each project the loop is linked into shows its library, in the loop's project order, marked project · read-only (a link to the project's Library tab): browse and download it here, change it on the project's page. The loop's agents read it there with flux library (its own files and the projects', by name, in capped pieces: Reading the library), the project's hidden paths hidden from them too. You see the projects whose link you see (a global project's only to its owner, admins and the project's keepers), and open those whose library you view.
    • The loop's .gitignore files hide what they ignore; show ignored lists them greyed.

    Settings¶

    A loop's Settings has two parts, Preferences and Problem. Each card of Preferences is drawn as soon as what it shows is read, the others a few grey lines under their title meanwhile.

    Preferences¶

    • Measurements: per metric, whether it is shown, whether it is a main one (in lists and summaries), and whether it shows as change from the baseline. Charts and the decision always use every measurement.
    • Environment variables: the loop's own, over your account's and the server's.
    • Sharing: the member grid of groups and projects (the words): the Owner row fixed on top, then a row a user or a group shared with, a Level (Viewer, Asker, Contributor, Maintainer; Custom a mix) and a box per word: view (runs, log, results, files; always on), ask (ask an agent about it in its Chat; a chat's agent reads it), edit (its files, the document, its settings, notes; accept Chat's proposals for it), run (start, stop, restart, measure again) and share (this list); there is no Member column on a loop, view is what being shared gives. + Share with… under the grid searches the users and groups and adds the one picked as a Viewer; its level menu or boxes give the rest. Ticking a box saves the row; one with share who is not the owner gives at most what they hold (hover a word's column for its meaning). Edit without Run changes the loop but cannot start or stop it; Ask without Edit chats about it and changes nothing. Under the shares, a read-only row per project the loop is linked into (its title, a project badge, its address as a link) ticks the most any of its people gets on the loop; a global project "gives no rights". ▸ unrolls its people: each member (the words their level gives), a member of its group who gets more through their membership ("via group"), and one row for what its group access gives everyone in the group ("Everyone in hw · open (Asker+)"); Change on the project › opens its page, where they are set. Your rights on a loop are your row, your groups' rows and what its projects give you, together; being in a group with its owner gives nothing. A run started by someone else uses the owner's record, model settings and limits.
    • Projects: the projects the loop is linked into, in its order: a grip to drag a row, or ▲ ▼ (the order its projects' libraries come in, each read-only at library/<project>@<group>/ after the loop's own files; an exact copy of a paper in a later one is read once). Each row has the project and its address, learns from runs (whether the project may learn from its runs) and ✕ to take it out. Add to a project… searches the projects you may link it into: those where you hold the link role, and the global ones that take loops. Linking it is your consent: each of the project's members gets their loop words on it (view, ask, edit, run; never share), and the group's members what its access gives. A global project gives no rights; its learning is off until an admin or one of its managers turns it on, and you may turn it off. Others see the card read-only.
    • Name & ownership: rename the loop (1 to 60 letters, digits, _ and -), or transfer it to another user. The loop must be stopped, with no agent and no chat answer reading it at work. Everything that names the loop moves with it -- its record, results, runs and settings, chats that focus on it or proposed changes to it, scheduled changes, waiting notices' links, its usage (counted once). There are no redirects: the old address stops working. A transfer leaves the admin's overrides, the shares and the agents' tests behind (they were the old owner's); the log, transcripts and the audit keep the old name where it was written.
    • Advanced (admins): whether the loop runs in the sandbox, its memory, CPU, process and scratch limits (under each, the server's default and maximum; an ask above the maximum is clamped to it, see Sandbox limits), parallel work (how much, the configurator's Extra › Running, which says whether it is allowed), extra hosts it may reach, raw TCP/UDP, host folders mounted inside, and extra Nixpkgs or Nixchip packages. Everyone else sees what they are, in a line under Name & ownership.
    • Maintenance (folded): run a clean-up on this loop now, and Re-Evaluate, which asks the next start to measure the pending designs again -- its boxes add pass 0 (Rerun baseline), the failed designs (Rerun failed) or every design (Rerun all). What waits for the next start is said on its row and on the Overview, with Cancel; it can be asked while the loop runs. Invalidate all sets every design aside without measuring anything, on this loop at rest only -- it is no admin task, so this is the one place it runs, after its confirmation; Show hidden evaluations brings back what an older invalidation hid. The tasks that change what the record counts are red and ask first. While an invalidation's designs wait to be measured again, its row says how many are done (Results).
    • Archive, reset or delete: Archive… keeps a finished loop read-only and frees its disk (see Archive). Reset clears what the runs generated (you choose what to keep: the workbench, results and history, caches); the document, your files and the settings stay. Delete removes the whole loop. All need the loop stopped and cannot be undone.

    Archive¶

    Archive… (the loop's owner, or an admin) asks for the loop's name and lists, with their sizes, what goes and what stays.

    Kept Deleted
    The record, out/: designs, measurements, decisions (Results and its exports) Each pass's agent folders: prompts, drafts, sessions, probes
    The document, your files and the library The tools' whole outputs (the journal keeps each one's end)
    The workbench's notes and tools The sandbox's tool caches and scratch
    The last start's log, the answer, notes and Chat The author's work in progress, __pycache__, the workbench's build folders
    The task journals and transcripts Live reads The log of the starts before the last; stopped sandbox containers

    An archived loop is read-only: Overview, Live, Results, Files and Chat (an agent answers from the record) still read it; the document, files, settings, ideas queue, starts and resets are refused until Unarchive (a plain confirm). A start then rebuilds the deleted scratch. The loop lists hide archived loops; their Archived chip shows them, each with its date, and a search or a link still finds them. Run clean-ups leave them alone; the integrity checks, compaction and journal format updates still include them.

    Problem¶

    Someone who may view the loop but not edit it reads the problem here: the configurator's steps beside the document as written, the chosen step's lines lit. Nothing can be saved or checked.

    • Configurator: the document in six steps, as the Loop crafter shows it. A save shows its diff first; what the form cannot express is kept as written, greyed at the end of the document beside each step (Copy and Download give it whole) and listed on Save. A check or measurement the loader refuses is outlined on its row, with why. Save counts the document as checked once Check passed on its files as they are, or a start on those files got going. Every step but Graph and Save is a few light cards of rows, as the Graph's panel below: a label, then its box or menu, a greyed value its default, a unit (s, MHz, %, a number's own) inside its box, and no hint under a field -- the line at the step's foot says what the setting pointed at or in focus does. Prompt is the name, language, what to make and the rules, then Files; Check & Measure a Checks card (the list, a row opened to set it, the critic set in Graph) and a Measurements card (the list, then how many finalists the last one takes); Objective how designs are compared, then the numbers, a goal's unit in its box. Extra's sections (Parts, Baseline, Parameters, Running, Resources, More) are cards that fold, each saying what is set while folded; one set away from its default, or at fault, opens. On the Graph, a box clicked opens its panel: the box's name and what it does, then a few light cards. Worker says who works it, the same rows wherever a worker is chosen (a box, its Critic, Choose's Tie-break, a Knowledge section, an AI search): the kinds -- off first where it may be off (the workbench digest too), then agent, then the box's own (rules, mined, script, files, goals) -- then with agent an Agent menu, FluxAgent first, then the agents the server offers (their program found, as in the chat), then its Thinking and effort -- an agent the document names that is not offered here (written by hand, or its program gone since) stays picked, greyed and marked (not available), never offered for another box, the Graph's error saying the loop won't start until it is fixed; Search's How it picks (FluxAgent only) follows, and right under them, folded, the agent's own card, titled <agent> · options: Questions and at most, Wait, Time limit and last turn, May time out, Session, Probe and its runs -- the same rows in every place, a row the place cannot say greyed (FluxAgent's are all an agent's; turns past the time limit and the probe are Design's agent's; Design keeps one session per part), its help line saying why. A box with a worker and a critic reads as two such blocks. Switching to another kind or agent and back brings back what it had (an agent's own settings, FluxAgent's thinking). The box's own card follows (Design's Per pass, Search's Policy card: the Policy (the intent), the Search once there are settings (an algorithm, or AI -- who proposes the points, FluxAgent with its Thinking and effort, or an agent with its card, picked under it) and the settings it searches), and Limits, folded (Design's prototype limits, Search's exploration and FluxAgent's tool turns, which are the whole loop's: always in Design's panel, elsewhere where FluxAgent works). Under a search over settings Design is off, a script or files; with a script or files making each point, all its kinds. Check, Measure, Choose and Record are one block saying who works them, linked to where their commands or goals are set; Knowledge is a card per section. A card folds, its values said beside its title while folded; a dot marks a value the document sets, a greyed one is the default, and the line at the panel's foot says what the setting pointed at or in focus does. The document's issues (what Check and Direct edit list: an error stops the loop, a warning is a key it ignores) are shown where they are set. A step's line in the rail says them with their mark -- a round "!" for an error, a triangle for a warning: "▲ 1 warning", "● 1 error · 1 warning" -- and Save's line counts them all ("1 to fix · 2 warnings"). On the Graph, the box the setting belongs to wears the mark in its top-right corner, its look otherwise unchanged (flow.plan on Plan, flow.generate on Design, flow.orchestrate on Search, flow.test on Check, flow.measure on Measure, flow.feedback on Notes, flow.knowledge on Knowledge, ...); with an error, the box shows the value as written (codx), not the default it would fall back to. Its panel outlines the setting at fault and says each issue in a note: the plain words, "Did you mean X?", its fix (Use codex, Remove) and Open line N to Direct edit there. A check's or a measurement's setting is said at the top of Check & Measure, an objective's on Objective, one in a sub-loop's file on Save. A fix is written to the file (refused if the file changed meanwhile), then the form and its issues are read again; changes not saved are asked about first. The banner of a document that does not load says the error in the same plain words. A save from the configurator keeps the keys the loader ignores as written, under the setting the form wrote (a stage's misspelled timout_s, feedback: human), so they stay for you to fix.
    • Direct edit: the YAML as written, saved with its diff. A document that does not load is said before it is saved.
    • Several problems. A loop's problems are its problem.yaml and each NAME.problem.yaml in its folder (not in a subfolder, not another name: foo.yaml is an input file, not a problem). With more than one, a menu beside the ways picks the one the configurator, Direct edit and Check show ("problem.yaml · selected" is the one the next start runs by default); one that does not load is listed as such, in red, and opens in Direct edit to be fixed (the configurator says what it could read of it). Edits not saved are asked about before another one opens. The address keeps the one open (settings/problem/edit?doc=fast.problem.yaml). Opening or saving a problem here does not select it: the problem a run takes is picked in the Start dialog, as before.
    • Agent: say what should change; an agent revises a copy of the loop's files and shows its diff (not while the loop runs).
    • Check runs flux task check on the document as it stands: whether it is ready to run, what it refused or found missing, then its checks, stages, objectives, tools and model. The whole output is under Details.
