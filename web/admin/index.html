    Server and admin¶

    Run a server¶

    flux user add ada --admin       # the first account, on the server's machine
flux serve                      # http://127.0.0.1:8765/
    Option Effect
    --host HOST, --port PORT Where it listens (default 127.0.0.1:8765); put a TLS proxy in front for others
    --secure-cookie Send the session cookie over HTTPS only, behind a TLS proxy
    --data DIR The server's data (default $XDG_DATA_HOME/flux/web): accounts, keys, every user's loops
    --max-running N Runs at once per user
    --no-sandbox Runs on the host, not sandboxed: for a single trusted user only

    flux user add and flux serve must name the same data folder; both print it. Run them as the user who should own the loops' files.

    • Data: the data folder holds flux-web.db, secret.key (which encrypts keys and secrets) and every user's loops under users/<name>/apps/. Back up flux-web.db and secret.key together (Admin › Maintenance can) and the loop folders separately.
    • Limits: a loop holds up to 100,000 files and 8 GB; one upload, 900 files and 256 MB.
    • Restarts: a restarted server finds its running loops again; their containers keep running while it is down. scripts/install-service.py (from flux/) installs it as a user service that restarts only the server on updates, or as a system service (User or system service).
    • What changed, told to the pages: one server-sent stream per browser (/api/changes, shared by its tabs) says which things changed -- a loop's state, results, notes, files, problem, settings, answers, agents' turns; one's chats and logins; Admin's resources, maintenance and version -- and the pages read those again. Writes through the server say so at once; a running loop's log writer tells the server over its control socket that the log grew (the run itself never sees the socket); a loop someone is looking at is watched on disk (Linux inotify), so an agent's or a hand's change shows in under a second; elsewhere a look every 5 s, and a sweep of the running loops every 30 s for anything missed. The stream sends a keep-alive line every 25 s (proxies drop silent connections) and is never compressed or buffered (X-Accel-Buffering: no for nginx). A page reconnecting is told what changed meanwhile; after a restart it reads everything again.
    • Slow requests (over 0.5 s; FLUX_SLOW_S sets it) are logged as flux serve: slow: ..., with where their time went (sampled while they ran), and the latest 50 are listed in Admin › Resources under Slow requests. FLUX_SLOW_SAMPLE=0 turns the sampling off.
    • Before a login the server serves only the sign-in page (/login: the login, and the invitation and reset links, /#/invite/...) and the few files it loads; / sends a browser there, and every other page, script and stylesheet of the app answers 404 until there is a session, checked on each request (a logout ends it at once; the page's files keep a session they saw 5 s). The app's files are sent Cache-Control: private, so a shared cache or proxy keeps none of them. The docs' Preview is not covered: it runs the whole app in the browser, by design (minified, and sealed behind its passphrase on the published site).
    • The pages' files are kept by the browser: the page points at /static/v/<version>/..., the version a hash of every file of the web app, and a browser keeps each file a year without asking again. After an update the page names a new version, so a browser loads the new files once and never mixes them with the old; a page left open goes on with its own version (the last three stay served). The first load asks for every module at once (preloaded, not one import after another) and gets the stylesheet in one file; the next ones ask for the page and its data only. Answers sent whole (the API's JSON, the pages, the files) are gzipped for a browser that asks; live streams, downloads and ranges are sent as they are. Through a link of 100 ms round trips the loops page took 5.1 s every time; now about 4 s the first time after an update (the browser's six connections at once: about 220 files) and 0.3-0.7 s after. The server learns that a web file changed from the kernel (inotify): a file saved and the page reloaded shows the change at once, and a page load costs no look at the files. A file changed by another machine sharing the folder is not told, so restart the server after one; on a system without inotify the server looks at the files at most once a second.

    Loops from the server's machine¶

    flux web-loop lists, starts, stops and reads the web's loops from a shell on the server's machine. It never runs a loop itself: it asks the running server, which starts and stops the run as its Start and Stop buttons do, with the same limits, pause, checks, audit and live pages.

    flux web-loop ls                          # every loop: owner/loop, state, last start, the agents its problem names
flux web-loop ls --user cedric
flux web-loop start cedric/nlu            # as the Start dialog: the last start's passes, else 1
flux web-loop start cedric/nlu --forever  # until stopped; --passes N, --screen-only, --document F, --rerun-baseline
flux web-loop status cedric/nlu           # running pass N or idle, the last start, the log's last lines (--lines N)
flux web-loop stop cedric/nlu             # at the end of the pass; --now abandons it

    A loop is USER/LOOP, its owner first. Each request acts as the loop's owner: the run is theirs, on their running limit, and each audit line it writes ends "(by host)". The agents and models are the loop's problem's (its flow, Settings › Problem); a start takes only what the Start dialog takes. --json prints the server's answer; --data names the data folder, as for flux user.

    The server listens for it on a unix socket in the account's runtime folder, $XDG_RUNTIME_DIR/flux/control-<hash>.sock (one per data folder; <data>/.server/control.sock when there is no runtime folder), mode 0600, owned by the server's account; it is made each time flux serve starts (a socket left by a server that ended is replaced) and removed when it stops. With no server answering there, flux web-loop says the server is not running. The trust boundary is the data folder: whoever can open the socket can already read and change every account and loop in that folder, so is the server's admin; run flux web-loop as the account that runs flux serve.

    Agents' Tests from the server's machine¶

    A start waits for each agent its problem names to have passed its Test for the loop's owner, of the configuration as it is now ("Codex not set up for cedric yet (its configuration changed since its Test)"). A new program for an agent (a Codex update) is a new configuration: every user who uses it needs a new Test. flux web-agent runs that Test for them, through the running server, as flux web-loop does:

    flux web-agent ls                         # each user's agents: ready, or needs Test and why; the last Test
flux web-agent ls codex --user cedric
flux web-agent test                       # every user, each agent they set up: one line each, ok or failed, its seconds
flux web-agent test codex --needed        # only those whose gate is not ready; --jobs 2 for two at once
flux web-agent test codex --user cedric   # one user (an agent named: tested even if never set up)
flux web-agent test codex --loop cedric/nlu   # in that loop's context, its variables

    It is the same Test as Account › Agents' button: the server runs it in the user's own home with their own settings, variables and sandbox, and keeps the result as theirs; flux web-agent sees no credential. "Set up" is logged in, a key, endpoint, model or variable of their own for the agent, or tested before (the admin's Test of the server's configuration counts too); a disabled user is skipped unless named. The loops whose own variables run an agent otherwise, and that were tested in their context, are tested again in it. A Test ends by itself after 420 s and says why; a failed one says what the page says and makes the exit 1. Each Test is on the audit as the user's "agent test", ending "(by host)".

    A Test is not a loop's turn. It takes none of the agent's turns at once on its endpoint and waits for none, so it answers while loops hold every one. It does not count against the user's running limit, and it is not held by paused starts. It is not in the usage either (no loop's turn); a failed Test is listed on its own in Admin › Insights. flux web-agent test keeps its own two guards: it refuses a Test of an agent already being tested for that user ("Codex is being tested for cedric: wait for it"), and it runs at most two at once (--jobs 2).

    Admin › Maintenance › Test agents runs the same Tests on a schedule (below).

    Accounts¶

    flux user manages accounts from the server's machine:

    flux user add bob --invite --url https://flux.example   # a link for bob to choose a password
flux user list
flux user role bob admin
flux user link bob                                      # a password reset link
flux user rename bob robert                             # everything of bob's, re-keyed
flux user delete robert --transfer-to cy                # robert gone, his loops cy's (or --delete-loops)

    A link works once, for a week; there is no mail. In the app, Admin › Users does the same: a row per user with the Admin, Create and Run boxes, a Limits cell (how many of their loops run at once, empty for the server's default, and an Active switch: off disables the account, after asking), their groups as pills (× leaves one, + searches the others), Last active, their usage behind Show usage, and a ⋯ menu with View as (the app as they see it, read-only), a reset or invitation link, Rename… and Delete… (Deletes). Headers sort, and the order is remembered. flux user role bob admin makes bob an admin; user takes the flag away.

    A new password logs the user out everywhere: one set from a link, by flux user passwd or by an admin in the app ends all their sessions (for the last two, a notice tells the user at their next login); one changed on their own Account ends all but the session that changed it.

    • Admin is the user's own. An admin administers the server and may do anything with every loop. An admin cannot clear their own Admin box; an admin has Create and Run.
    • Credentials are a group's. Each group is set to Server settings (runs use the server's model, agent and variable settings beneath the user's own) or Own settings (members bring their own settings and agent logins). A user gets the server's settings when any of their groups gives them; in no such group, or in no group at all, they use their own. Admins follow the same rule. A new group starts with own settings. Your Account names the group that gives you the server's settings; Groups in the top bar shows it per group (Groups).
    • Groups: a user is in no group, one or several. Admin › Users › Groups lists each group with its member count, its Credentials, their Effect (who gets the server's settings through it, or through another group), Open projects give (the level its open projects give its members unless a project says another; Asker by default), Rename… and Delete…. A group unrolls to the member grid under its name: a row per member with a Level (see the words), the Member column every member has, a box per word (hover a column's name for its meaning) and × to remove them. The All members row on top gives a word to everyone or takes it from everyone (a dash: some have it). + Add people is under the table; a new member starts as Member. On a phone a member is a block: the name and ×, the level, then the words three to a line. A project's members and a loop's Sharing are the same grid.
    • Permissions of the account, whatever the groups: Create loops and Run loops and agents. A user in no group still creates and runs their own loops.
    • A membership's words -- curate, manage, create (Member, Maintainer, Lead) -- act on the group's projects, never on a loop: being in a group gives nothing on any loop (see the words).
    • Archive, reset, delete, rename and transfer stay with the owner and the admins. A loop is reached in two ways only: its owner (or one with share on it) shares it with a user or a group, or links it into a project. What someone may do with it is the union of their row, their groups' rows and what the projects it is linked into give them. Ask and Run also need Run loops and agents.

    The words¶

    One vocabulary for loops, groups and projects (GET /api/words serves it): the loop words view, ask, edit, run act on loops -- one shared loop, or the loops linked into a project; share is a loop's own (whoever holds it chooses who else gets the loop, giving at most what they hold). The place words act on a group or a project: link (link one's own loops into a project), curate (review a project's knowledge, keep its library), manage (members, levels, access, title; rename, archive, delete) and, on a group only, create (make projects; the maker is the project's Lead).

    A loop is reached in two ways only: a share (to the person, or to a group of theirs), or being in a project it is linked into -- one of its members, with their level there, or a member of its group when the project opens to the group. A group membership carries no loop word: being in a group gives nothing on any loop by itself.

    Place Words
    Loop share view · ask · edit · run · share
    Group membership curate · manage · create
    Project level view · ask · edit · run · link · curate · manage
    Global project level curate · manage

    Levels are one ladder in every place, cut to each place's words; a mix that matches no level reads Custom:

    Level Words Loop Project Group Global project
    Member none -- yes yes yes
    Viewer view yes yes -- --
    Asker view · ask yes yes -- --
    Contributor view · ask · edit · run · link yes (no link) yes -- --
    Maintainer Contributor and curate, create (on a loop: view · ask · edit · run · share) yes yes curate · create curate
    Lead every word -- yes curate · manage · create curate · manage

    A loop's levels stop at Maintainer; its Owner row is shown, never given. A word that acts on a loop brings view with it.

    Why a place has no box for a word (the grids leave these out):

    Place Word Why not
    Loop share link covered by share: linking needs share on the loop (its owner has it) and link on the project
    Loop share curate a loop's record is not curated: what it teaches reaches a project's curators
    Loop share manage its owner's only (rename, transfer, archive, delete): the Owner row, never given
    Loop share create loops are made on the account (Create loops)
    Group membership view, ask, edit, run a loop is reached through a share or a project one is in, never a membership
    Group membership link linking is a project's word: its members' level, or its open level
    Group membership share a loop's own: a group never shares its members' loops onward
    Project level share a loop's own: a link is consent to the project only
    Project level create projects do not nest
    Global project level view its visibility gives it: everyone a public one, its members a private one
    Global project level ask, edit, run, link a global project gives nobody a word on its loops; who links is its join rule

    Who manages a group or a project gives anyone a level or words up to their own there; admins any. The open levels are set by the group's managers (a membership has no loop word to bound them) and by a project's own managers within their words.

    What a group gives. On the loops linked into its projects, only what each project's group access says: invite (the default for a new project) gives nothing on its loops and is private: hidden from the group's members until they are added (its managers and curators see it); view gives every member view on it and its loops; open gives every member the project's open level (the group's default, Asker unless set, or the project's own) -- that level, nothing more. Its words reach every project of the group, whatever its access: curate curates them, manage manages them and the group's members, create makes projects.

    Global projects. A global project is public (everyone sees it, its library and its knowledge) or private (only the members an admin or its managers add, and admins, see it; elsewhere it is not found). Its members hold only curate or manage (Member, Maintainer, Lead). Nobody sees another person's loops linked into it but admins and its managers; in a private one its members do not see the other members either. Who links loops into it is its join rule (everyone, or admins), and in a private one only its members. There is no curator group: a curator is a member with curate.

    Renames¶

    Only an admin renames a user: Admin › Users, the row's ⋯ › Rename… (or flux user rename). Everything that holds the name moves with it -- the user's folder (loops, chats, home), their sandbox caches, their loops' settings, variables, shares and result columns, the shares other owners gave them, their runs' paths, scheduled changes naming them, chats that focus on their loops, the questions they asked, their usage. It is refused while anything of theirs works: a run of their loops, an agent writing or answering about one, a chat answer, a login or an agent test. There are no redirects: links to the old name stop working, so everyone their loops are shared with is told once, with the new link, and so is the user. Their sessions stay; they log in with the new name from then on. The audit keeps the old name where it was written, with one "rename user" entry.

    Admin › Users › Groups › Rename… renames a group; its members, their permissions and its shares stay (they are kept by the group's id), and its members are told. Names are one whatever their case; _ is reserved and / is not allowed (a project is addressed <group>/<name>).

    Deletes¶

    Active off (in Limits) disables a user: logged out, unable to log in, everything kept. ⋯ › Delete… is the hard one, for admins only. Its dialog says what the user holds -- their loops (and whom each is shared with), the projects only they manage, the loops shared with them, their groups and sessions -- and asks where their loops go: transferred to another user (each moves as a transfer does, with its files, record, runs and projects; its shares cleared; a name the other user already has becomes <loop>-<user>, shown before you confirm) or deleted (as the loop's own Delete). Then their account goes with everything kept for them: sessions, invites, notifications, memberships, project levels, the shares to them, their own model settings, variables and agents' keys, their Overview layout, scheduled changes for them, their folder (chats, home, agents' logins) and sandbox caches. The audit keeps their name where it was written, with one "delete user" entry; the usage log, transcripts and others' chats stay as history. It is refused while a loop of theirs runs or anything of theirs works (as a rename), for yourself and for the last enabled admin; you type their name to confirm. Whom their loops were shared with is told, and so is the user who got them. flux user delete NAME --transfer-to USER (or --delete-loops) does the same from the server's machine.

    Groups › Delete… is refused while the group has a project, archived ones too: the dialog lists them, each a link to its page to delete it. Otherwise it says the members, the loops shared with the group and, first, the members who get the server's settings through this group alone: they change to their own. You type its name to confirm; its memberships, the loop shares made to it and its settings go, and its members are told. Its members keep their accounts and loops.

    Projects¶

    Think of a group as an organisation and a project as one of its repositories: the project has its own members, and loops are linked into it. A project belongs to one group, addressed <group>/<name>, or is global, addressed _/<name> and shown "global / …". Names are letters, digits, - and _, one per group whatever their case; titles are free. The Groups page lists a group's projects and makes new ones, and each project has a page of its own: its loops and its members. The API (/api/projects, /api/groups/mine) and flux project on the server's machine manage them:

    flux project create hw/nlu --title "NLU operators"                    # --access invite|view|open (invite)
flux project create _/techniques --visibility private --join admins  # global: admins only (public by default)
flux project member _/techniques cy maintainer                        # a global project's: member, maintainer (curate) or lead (curate, manage)
flux project access _/techniques public                               # a global project's visibility: public or private
flux project member hw/nlu bob contributor                            # a level, or view,ask,link ... or none (a Member)
flux project member hw/nlu bob remove
flux project access hw/nlu open viewer                                # what the group's members get: open, at Viewer (group: the group's)
flux project rename hw/nlu nlu-ops                                    # the old address stops working
flux project archive hw/nlu-ops                                       # --undo unarchives
flux project list --all
flux project delete hw/nlu-ops --yes

    Levels are the words' ladder cut to a project's words (view, ask, edit, run, link, curate, manage); the one who makes a project is its Lead. A Member (no words) sees the project and its members, nothing more. Group access, per project, says what the group's members get without being its members: invite (private: hidden from them until they are added, but for the members whose group membership curates or manages; the default for a new project), view (they view it and its loops; every project made before reads so) or open (each gets its open level, nothing more). There is no joining: a project's own members are added by those who manage it; anyone may leave a project.

    What someone may do with a project is the union of: what its group access gives, their membership of its group (curate and manage on every project of the group), their own level as its member, and a global project's view (everyone a public one, its members a private one). Rights only add up: nobody loses a right because of a project. Admins may do everything. Members with create make the group's projects; only admins make global ones and choose whether each is public or private and who may link loops into them; a global project's members (curate or manage) are added by admins and its managers. Archiving hides a project from the lists and freezes it until it is unarchived. Every change is in the audit.

    Admin › Users › Projects lists every project, the groups' and the global ones, archived ones too: its title (a link to its page) and address, its group, how many loops are linked into it, how many members it has and the size of its library. A global project's Visibility (Public or Private) and Who links loops (everyone, admins only) are set in its row; each row's ⋯ opens it, renames it, archives or unarchives it, deletes it. New global project is under the list. GET /api/admin/projects answers the list.

    A project's library (<data>/projects/<group-id>/<name>/library/, written only by the server) is browsed and changed from its page as a loop's files are, through /api/projects/<group>/<name>/library (what it holds, what one may do), .../library/files, .../file (GET, PUT, DELETE), .../item, .../item/size, .../move, POST .../files, PUT/DELETE .../part and .../hidden. View browses; edit, curate or manage changes; manage hides paths from the agents (kept on the project, in the database and its project.json). Paths stay inside it, links are never followed or made, a zip holding a link is refused; it holds what a loop may (100,000 files, 8 GB). No loop reads it yet.

    Loops in projects¶

    A loop is in no project, one or several, in an order its owner sets. Linking a loop is its owner's consent; the project's roles then decide. Only its owner (or an admin) links it: into a group's project where they hold link, or into a global project (anyone -- a private one's members only -- unless its join rule is admins); an archived project takes none.

    • On every loop linked into a group's project, each of its members gets their roles' loop words -- view, ask, edit, run -- and the group's members what its access gives (view, or the open level). This adds to what shares give, never takes away (a group membership gives no loop word); ask and run still need the account's Run loops and agents; curate, link and manage stay the project's. An archived project gives none until unarchived.
    • A global project gives nobody any right on a loop. A user sees only their own loops in it; admins and its managers see every one.
    • Each link keeps an extraction consent: whether what its runs teach may be extracted for the project's knowledge (kept for when extraction comes). On by default for a group's project, the owner's to switch; off for a global one, where only an admin or one of its managers turns it on and the owner may turn it off.

    A loop renamed or transferred keeps its projects; a loop deleted leaves them; a project deleted lets its loops go and tells their owners. The API is GET /api/apps/<loop>/projects?owner=<owner> and PUT the same path with the whole ordered list, [{"project": "hw/nlu", "extract": true}] (left out, extract keeps what it was, or the default); POST /api/projects/<group>/<name>/loops links one of one's loops, PUT and DELETE on .../loops/<owner>/<loop> change its learning or take it out; each project in /api/projects lists its loops, and each loop in the loop lists its projects. On the server's machine:

    flux project loop bob/adder                          # its projects, in order
flux project loop bob/adder set hw/nlu _/techniques  # exactly these, in this order (none: no project)
flux project loop bob/adder add hw/dsp               # one more, last
flux project loop bob/adder extract hw/nlu off
flux project loop bob/adder remove hw/dsp
flux project loops hw/nlu                            # the project's loops

    Your account¶

    Account holds your Agents (each agent's login, Test, model and variables), your usage, your password, desktop notifications, and the Overview layout used on every loop; a line names your groups and links to the Groups page. Changing the password asks for the current one (wrong ones count and lock as a login's do) and logs out your other sessions.

    An agent is used only once its Test passed for whoever starts the loop. A Test runs at once, whatever your loops hold: it waits for no turns at once and no running limit (Agents' Tests). A login runs the agent's own login command in the sandbox, in a small terminal; Claude Code's token is stored encrypted and never shown again. An agent never runs on FluxAgent: without settings of its own, it uses its own configuration and login (Models and agents).

    Admin¶

    Tab What it holds
    Loops Every user's loops (a loop is archived from its own settings); pause new starts, stop or restart them all after their pass; documents of an earlier form, with Migrate all
    Insights Failed starts and agent Tests, usage and cost by user and agent (the knowledge collector's calls as their loop's), endpoints, refused hosts, the audit trail
    Resources CPUs, memory and disks over time, the sandbox containers, each loop's disk and caches
    Maintenance Scheduled clean-up tasks, each on or off, with Run now; scheduled changes of a setting
    Sandbox Limits (CPUs, memory, processes, scratch: a default and a maximum), the network (open, or an allowlist), the PATH directories mounted, what every user's home starts with
    Agents FluxAgent and each agent: program, login, model and key, seconds per turn, token prices, turns at once on its endpoint (every loop's turns; an agent's Test takes none), whether Ask may use it, thinking by default; + Add agent
    Chat What users may use in Chat (the tab, network beyond the base allowlist, the workbench, loop access), the hosts a chat may also reach, overrides per group and user (Chat)
    Users Users, groups and permissions, invitations, View as; Projects: every project
    Version The commit the server runs, updates waiting on origin/main, Update and Roll back (Version)

    Keys are stored encrypted and never shown again. With nothing set, runs use the machine's own configuration (~/.config/flux/flux.env, and each agent's own).

    An agent's panel says its program as runs find it, with its version, or what was looked for ("claude is not on the runs' PATH"); users are offered only agents whose program is found -- in the chat, Ask, New loop › Agent and the configurator's agent menus, where one a document names that is not found shows (not available). An agent added under a name of its own runs its kind's program unless its Program (or FLUX_<NAME>_BIN) names another -- what the built-in agent of its kind runs, said as "/…/claude (claude's)" -- and its login, Test and runs use that program too.

    Thinking by default¶

    Each agent's panel in Admin › Agents, and FluxAgent's, says whether it Thinks by default: where a loop's box does not say (think: beside by: flux or an agent, an agent's effort:, Thinking) and as the Think switch of a chat's composer starts for it (Chat). An agent also has the effort it works at when thinking and when not, from the levels its kind takes (Claude Code --effort, Codex model_reasoning_effort, OpenCode --variant); its own adds no flag. FluxAgent has its own four efforts -- low, medium, high, max: thinking, tool rounds and answer length at once (Chat); built in is high thinking and medium not.

    Thinks by default Effort when thinking when not
    Each agent on its own (no flag) its kind's lowest (low, or minimal)
    FluxAgent off built in (high) built in (medium)

    Untouched, loops run exactly as they did: agents with no effort flag, FluxAgent answering straight. A loop's box worked by FluxAgent takes an effort only when one is said: its effort:, or one picked here -- the built-in levels leave its requests (its tool turns, its output) as they were. What wins, first to last: a chat's Think, the loop's box, this default. Saved at once and audited (thinking by default); a run, a chat or an ask started afterwards takes it.

    Resources¶

    The tab is read again when what it shows changes (a loop starts or ends, a container is stopped, the minute's sample of the machine), at most every 5 s. Sandbox containers lists every container the sandbox runs, with its CPU, memory and processes; the page shows the list as last read and the engine is asked again in the background, so a busy engine never holds the page. Each loop's disk is measured in the background too: after a start-up, and again when a size is ten minutes old (until then the size measured before is shown). Whose says what each one is: a loop's (its link; Stop ends the loop after its pass, View opens the loop whose author or Talk uses it), Chat · user (a user's chat sandbox; kept when it stays between answers, each answer running in it named under it), Login · user or Agent test · user. Its state says answering or kept, idle for a chat's. Stop on a chat's stops the answers running in it, each saying it was stopped, and removes it: the user's next message starts a fresh one. A container no process runs any more is left behind, with Kill; the scheduled clean-up removes those itself, never one a loop, a login, a test or a chat still uses.

    Slow requests lists the latest 50 answers that took longer than FLUX_SLOW_S (0.5 s) since the server started, the newest first: the request (its method and path, without the query), how long it took and when, and the status when it failed. These are the same lines as the server's log (flux serve: slow: ...), so you can find the slow page without the log. The list is empty after a restart.

    Under each request, folded, is where its time went: while a request runs past the limit, the server looks at what every thread is doing every 10 ms. The fold names the place most of those looks found the request at (a file, line and function: the innermost first, then Flux's own code outward) and how many of the looks it took, the next places after it, and Also busy meanwhile: other threads that were working at the same time (a background job, another request), which slow a request down without being part of it. When the request had not reached its own code yet, the fold says what held it: before its handler and where (its sign-in being checked), the event loop busy and where, waiting for a worker thread: all N taken (every worker serving other requests), else waiting: not in its handler (its body, a guard). The log line says the same in short: ... 0.93 s; at <place> (94% of 63 samples); also busy: <thread> at <place>. Nothing is looked at while no request is past the limit, so this costs nothing the rest of the time.

    Maintenance¶

    The scheduled tasks clean scratch and leftover containers, compact the databases, condense run logs, prune old records and agent folders, alert when a disk fills, and back up the server's database. Bring task journals up to date converts journals written by an older Flux, so Live can read them. Two tasks act on a loop's record, off the schedule by default: Re-Evaluate asks one loop's next start to measure the pending designs again (its boxes add pass 0, the failed designs, or every design), and Show hidden evaluations shows again what an older Flux's invalidation hid, on one loop or every loop at rest (see Results). Running loops are never touched, archived loops only by the checks, compaction and journal updates, and every run is audited.

    Invalidate all (every design of a loop set aside) is not a maintenance task: it cannot be run over the loops, on one loop from here, or on a schedule. It is the loop's own, in its Settings › Maintenance, and asks first. A server that had it scheduled forgets that schedule when it starts; its past runs stay in History.

    Test agents (off until turned on; e.g. daily at a time) runs the Tests flux web-agent test runs by default, through the same code: each user's agents they set up (logged in, a key of their own, or tested before; disabled users left out), and their loops' Tests in their context. Ticked (the server's shared configurations too, on by default), it also runs Admin › Agents' Test of the server's own configuration of each agent that has a shared endpoint or credential, as the admin who asked (a schedule's: the first admin). Each result is kept as that Test's, so a start's gate reads it, and is on the audit as the user's "agent test", ending "(by maintenance)". Tests at once is 1 or 2 (2 by default). A Test takes no turn at once on its endpoint and no running-loop limit, as above. A Test already running (a button's, the daily retest) is left and said "being tested already". The task's result says each Test, failed first: whose, which agent, ok or why not, its seconds; its Edit dialog lists the last run's Tests one per row. One failed Test makes the run failed. A user whose Test passed before and fails now is told, as the daily retest tells them. Nothing of a configuration's values is shown or kept.

    Maintenance has three tabs, each with a filter box and chips that narrow its rows:

    Tab What it lists
    Tasks The built-in tasks: running first, then queued, failed, done and off. Chips: Running, Queued, Failed, Off
    Scheduled changes Your scheduled changes (below), soonest next run first. A chip per setting or kind
    History Every run of a task or a change, newest first: what, when, by whom (the schedule, the server's start-up, or an admin's Run now), how long it took and its result. Chips: Failed, Scheduled changes, Run now. The last 1000 runs are kept

    On a phone each row is two or three lines: its name with its buttons, then its schedule and last run, then its result.

    One task runs at a time. Run now (the ▶ button on each row; on every loop, or on one) runs the task at once when nothing else runs; otherwise it joins a queue, first come first run, and the row says queued · 2nd with Cancel. Asking again for a task already queued or running adds nothing. Scheduled runs join the same queue. A running task shows a spinner and how long it has run. The queue lives in the server's memory: a restart drops it, and the schedule asks again. Resetting, renaming, transferring or archiving a loop is still refused while a task runs, never between two.

    A task runs every so many minutes, hours or days, or daily at a time on the days picked, or on a cron expression (the same form as a scheduled change's, below). A task at a time of day runs once when its time comes; a time already past when it is set waits for its next day.

    Scheduled changes¶

    A scheduled change does one thing at a time of day. + Scheduled change asks first for its kind, then that kind's fields, then when:

    Kind What it does
    Turns at once Sets one endpoint limit: turns at once of an agent's endpoint, or requests at once of FluxAgent (the limits under Admin › Agents), checked as that form checks it: a whole number, 0 for no limit. An agent's Test takes no turn
    Pause starts Pauses new starts with a reason (up to 200 characters), or resumes them. Running loops go on. While paused, starts, owners' restarts, Restart all and a pending restart after a pass are refused with the reason
    Running limit A user's running-loops limit (0–64, or default), or the server's default (0–64, or default: the --max-running flag). New starts only
    Stop loops Stops the running loops after their pass: every loop, one user's, or one loop. Now (off by default) stops them at once, the current pass abandoned
    Start a loop Starts one loop as its owner, with the options of its last start, for 1–1000 passes or until stopped. Refused, and shown as a failed run, when the loop is gone or archived, its owner is disabled or may not run loops, starts are paused, the owner is at their limit, or it already runs

    When is daily at a time on the days picked, or, under Advanced: cron expression, five cron fields: minute, hour, day of the month, month, day of the week. */15 9-17 * * 1-5 means every 15 minutes from 09:00 to 17:59 on weekdays. The form says the schedule in words and its next times. Times are the server's own, and its time zone is shown beside the field.

    For example, to leave the shared endpoint to people by day and give it to the loops by night, add two changes to Claude Code's turns at once:

    Change When
    Claude Code turns at once → 1 daily at 08:00, Mon–Fri
    Claude Code turns at once → 4 daily at 20:00, every day

    A night of runs, for example, takes three changes, every day: Start a loop at 20:00 until stopped, Pause starts at 20:05 with the reason nightly runs (no one else starts one), and Stop loops at 07:00, every loop after its pass, with Pause starts set to Resume starts at 07:30.

    Each change is a row with its schedule, next run, last run and result, Run now (▶, queued like any task), and Edit…, Turn off/Turn on and Delete… in its menu. A change takes effect at the next turn of every loop, running loops too. Lowering the limit stops no running turn: running turns finish, and new turns wait until fewer than the new limit run.

    A stop or a start happens at its time only: one missed while the server was down is not done when it starts. The pause, each user's limit and the default limit are settings. When the server starts, each setting gets the value of whichever of its changes came last (at or before now), so a server that was down at 20:00 still has the night's value. If two changes of one setting were both missed, only the later one is applied. Adding, editing and deleting changes is audited, and so is every change made. A run that found the value already set is not recorded. The audit reads, for example, scheduled: Claude Code turns at once → 4 (was 1).

    Sandbox¶

    Every run is sandboxed unless a loop's Settings › Preferences › Advanced (admins) says otherwise. The network is open, or an allowlist of hosts, domains and address ranges; HTTP(S) goes through the server's proxy, and raw TCP/UDP is a per-loop choice. The command line's equivalents are FLUX_SANDBOX_NET=allowlist, FLUX_SANDBOX_ALLOW and FLUX_SANDBOX_RAW_NETWORK=1 (Sandbox).

    Allowlists¶

    Every allowlist (the sandbox's, Chat's, a loop's extra hosts, an agent's hosts and FLUX_SANDBOX_ALLOW) reads the same way:

    Entry Allows
    dl.acm.org that host only
    *.acm.org or .acm.org acm.org and every subdomain (dl.acm.org, www.acm.org, a.b.acm.org)
    10.0.0.0/8, 192.168.1.20, ::1 the addresses in the range, or that address
    localhost this machine (127.0.0.1, ::1)
    • Separate entries by new lines, commas, semicolons or spaces. # starts a comment to the end of the line.
    • Case, a trailing dot and a port do not count (DL.ACM.org.:443 is dl.acm.org); a pasted URL keeps its host.
    • * alone is refused: choose open (or Chat's Open) instead.
    • Saved, the list is kept one entry per line, and the page says how it reads, for example Understood as: acm.org and its subdomains · arxiv.org only.
    • A page that redirects to another domain (a sign-in or a CDN host) is refused by that host's name. Recently blocked under the list names the hosts refused lately; a click adds one. The agent's error says the same: flux sandbox: refused www.acm.org (not on the network allowlist -- add www.acm.org or *.acm.org).
    • Lists kept before this rule, when a name also allowed its subdomains, were rewritten once as *.name, so they reach what they reached.

    Limits restrict every sandbox the server starts: a loop's runs and checks, a loop's Chat, Chat answers, the author agent, agent Tests and logins. For CPUs, memory, processes and scratch /tmp:

    • Default is what a sandbox gets when its loop sets none.
    • Maximum is the most a loop may ask for. A higher ask is clamped to it, never refused, and a loop that sets nothing is held to it too. The run's log says memory 8g clamped to 1g by the server.
    • Empty is no limit (processes: 4096).

    CPUs are a positive number such as 2 or 0.5, at most this machine's count. Memory and scratch are sizes with a unit, such as 512m or 4g; memory is at most this machine's RAM. The page shows both. A change is audited (sandbox limits). It applies to sandboxes started after it; running ones keep their limits. A loop's Advanced (admins) shows the server's default and maximum under each field, and clamped to 1g by the server when its value is above the maximum. On a server started with --no-sandbox, the limits are shown read only.

    Proxy¶

    Proxy is what runs, agents, Chat, logins and the author agent reach the network through, and Flux's own calls to the model endpoints. It applies with or without the sandbox.

    • From the host (the default) takes the first place that names one: the server's environment, /etc/environment, /etc/environment.d/*.conf and ~/.config/environment.d/*.conf, then what the server user's login shell exports (a systemd service often has none of a profile's). The page says which, for example From /etc/environment: HTTP http://proxy:3128 · not for .corp.example.org.
    • Set here takes an HTTP proxy, an HTTPS proxy (each http://host:port, with user:password@ if it asks) and a not through it list, read like an allowlist (new lines, commas, semicolons or spaces; # comments): a host, .domain or *.domain (it and its subdomains), an IP or a CIDR. Empty fields are no proxy. Switching to set here starts from the host's values.
    • Credentials are stored encrypted and shown as http://***@proxy:3128; a URL left as shown keeps them. They never appear on a command line: a sandbox gets them in its variables file.
    • The server and an open sandbox get HTTP_PROXY, HTTPS_PROXY and NO_PROXY in both cases, localhost, 127.0.0.1 and ::1 always added to NO_PROXY. An allowlisted sandbox keeps its own proxy (localhost only in its NO_PROXY), which reaches allowed hosts through this one, directly for those its not through it list names.
    • In effect says the proxy and where it came from. A change is audited (sandbox proxy, the credentials masked) and applies to what starts after it: running loops keep theirs.

    Chat¶

    Admin › Chat says what users may use in Chat. The admin allows features; each user then switches them on or off per chat, within what is allowed.

    Feature Allowed Default
    Chat tab The user has Chat in the top bar. Off, every other feature is off too. on
    Network beyond the base allowlist A chat may also reach the hosts listed under Network beyond the base allowlist, or any host when it is Open. off
    Workbench A chat may read and write the user's workbench. on
    Loop access A chat may read the user's loops, their own and those shared with them, read-only. on
    • For everyone sets the server's value. Overrides sets a value per group and per user: as above, on or off. A user's value beats their groups', which beat the server's; of a user's groups, one that turns a feature off wins. Add a user adds a user's row.
    • A chat always has the sandbox's base allowlist (Sandbox): the hosts listed there, the agents' hosts and the model endpoints. Agents need it, so there is no "off". Allowed with no hosts listed and not Open, the feature stays off, and users see why. On a server whose sandbox network is open, chats have the open network.
    • The hosts beyond the base are an allowlist (Allowlists): *.acm.org lets a chat reach acm.org and all its subdomains. Recently blocked names the hosts chats were refused lately.
    • A feature that is off is greyed in the user's chat, with the reason: turned off by the admin on this server, for the group …, or for you.
    • Changes apply from each chat's next message. They are audited (chat permissions), as are chats made and deleted (chat created, chat deleted).

    Limits per answer bound a coding agent's answer: Minutes (default 8, 1 to 60) and Tool calls (default 40, 5 to 400). An answer ends sooner when it is done: once the agent has written its answer (or its question) and then goes quiet, repeats itself, or only updates its plan. An answer stopped at a limit keeps what the agent wrote; with nothing written it fails, saying which limit it reached. FluxAgent has no such limit: it reads with its tools (at most 20 rounds of calls) and then answers.

    Attached files bound the files a user attaches to a message, in Chat and in a loop's Chat: MB a file (default 50, 1 to 2048) and Files a message (default 10, 1 to 50). Any type is kept as it is: in the user's workbench (uploads/) or with the answer (Chat › Attached files).

    How Think starts in each composer is each agent's and FluxAgent's own: thinking by default, in Admin › Agents. (A server where Chat's earlier Think on by default was ticked has FluxAgent thinking by default.)

    Each answer runs as a loop's Chat answers do: in the sandbox, under the server's limits, with the user's model and agent settings, and the agents offered for Ask (Admin › Agents).

    Sandbox sets how long a user's chat sandbox is kept idle (minutes, default 30, 0 to 240). A user's answers run in one sandbox, started by their first message and kept between messages, so the next answer starts sooner (about a second instead of two on an idle server); it ends once no answer has run in it for this long. Several chats of the user share it, and so do answers written at the same time, under one set of limits. What an agent keeps between answers is in the user's home and workbench, as before, never only in the sandbox. 0 gives each answer a sandbox of its own.

    A sandbox is started again when what it is started with changes: these settings (the network beyond the base, its hosts), the sandbox's (limits, network, PATH, the proxy), the agents' and the model's settings, and, when the server restarts, Flux's code or the server's environment. An answer running at that moment is stopped and written again on the new ones, its message kept and one answer kept, saying restarted: the admin changed the chat settings (or the sandbox settings, the proxy, the agents' settings) or restarted: Flux was updated. One the user may no longer have answered ends stopped, saying why. A finished answer is never touched; the next one simply starts on the new settings. The limits per answer and this time apply from the next answer and start nothing again.

    Environment variables¶

    Variables apply in order: the server's (Admin › Agents › All agents), the user's (Account), the loop's (Settings › Preferences). Secrets are stored encrypted. The sandbox's own variables, PATH, HOME and the model settings cannot be set this way.

    Version¶

    Admin › Version says which code the server runs and updates it. Updates follow main and are fast-forward only.

    • Running: the commit the server started on (its short hash and the D-number in its subject), the branch, whether the checkout has changes, the Nix lock's inputs (flake.lock), the Environment (the prepared dev shell the server started on, its key and the previous one; whether one is building or failed, or the checkout's flake.nix/flake.lock want another), how long the server has run and the clone's path. When the checkout has moved since the server started, it says so, with the restart command.
    • Check for updates runs git fetch origin main in the server's clone and lists the commits behind origin/main, with their D-numbers. A main that has commits of its own has diverged and cannot be updated.
    • Documents: a dry run of flux task migrate over every loop's documents, by origin/main's code (its tree in a temporary folder) when it can run here, else by the running code. It lists which documents would change and which need a hand. Nothing is written. A document that names an agent an admin added (Admin › Agents) loads as it does for its runs: the dry run, the migration after an update and Admin › Loops › Migrate all know the server's added agents.
    • Update is refused off main, with changes in the checkout, or when main has diverged. Running loops do not hold it: each start runs on its own copy of the code it started on, in the Nix environment it started in (Running loops keep their code), so no loop is stopped or waited for. After the fast-forward the server restarts. When it starts on the new code it first migrates every idle loop's documents: a document is written only when it loads, and the original is kept as <file>.orig. A running loop's documents are never rewritten under it: the tab lists them as waiting, and they are migrated when its run ends (or just before its next start), on the History with the update they follow. Only a loop running on the checkout itself (one started while the checkout had changes, or before each start had its own code) still holds an update, until it ends; the tab names it. There is no "after the running passes" any more: nothing an update changes reaches a running loop.
    • The environment first: under the service units, when origin/main's flake.nix or flake.lock differ from every environment already built, Update builds that environment first, in the background, as the service's account. The checkout and the server are not touched meanwhile. The update is queued: the tab says "Building the environment for …" and follows the build, and the History lists it. Once the environment is built, the update is applied (fast-forward, the environment made current, the restart). A failed build moves nothing: the queued update is dropped, and the tab shows the end of Nix's output. A queued update builds its environment ahead in the same way, so the switch is quick. A code-only update needs no build and goes at once, as before. A rollback reuses the previous environment that is kept, or builds it first in the same way.
    • Roll back returns to the commit the last update came from, as long as the checkout is still where that update left it. It is refused with changes in the checkout, or while a loop runs on the checkout itself. Documents that update migrated and nobody changed since are put back from their .orig; a renamed one is listed for a hand. A running loop's are put back when its run ends, as above; when the code rolled back to cannot do that (it predates each start having its own code), a rollback with such a loop running is refused until it ends. Then the server restarts.
    • History: who, when, from and to, and the result of each update, queued update, migration (at the start, or "after its run"), document put back, and rollback. It is kept in <data>/version/log.jsonl and in the audit trail.

    How the server restarts depends on how it runs. The system service with its own account (FLUX_SERVICE=system, below) ends itself and systemd's Restart=always starts the new code; no polkit or sudo is involved. The user service and the owner's system service (FLUX_SERVICE=watched) are restarted by flux-update.path when HEAD moves (its flux-update.service builds the environment first, then restarts); there, Update fast-forwards the owner's checkout only when it is clean and on main. A server started by hand says the command to run, and it has no prepared environment: an update moves the checkout at once, as before.
