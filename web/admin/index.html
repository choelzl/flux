    Server and admin¶

    Run a Flux server, manage accounts, groups and projects, and set the server's agents, sandbox, chat and maintenance.

    The server¶

    Installing and starting one: Install; for a team, the system service. Everything else is on these pages.

    • Data: the database, secret.key (encrypts keys and secrets) and every loop. Back up the database and secret.key together (Admin › Server › Maintenance), loop folders separately. Never copy the database alone while the server runs (Backups and restore).
    • Limits: a loop holds up to 100,000 files and 8 GB; one upload 900 files and 256 MB. Runs at once per user: each user's Limits cell (Accounts).
    • Restarts: running loops are found again; their containers keep running meanwhile.
    • TLS proxy: for others to reach the server, put one in front; it must not buffer the live connection (nginx: the server sends X-Accel-Buffering: no).
    • Slow requests (over 0.5 s) are logged; the latest 50 are in Admin › Activity › Resources.
    • Worker processes: heavy pages are made in 2 to 4 worker processes (40-130 MB each).
    • Before login, only the sign-in page is served. Logging in or out in one tab updates the others.
    • After an update, open pages load the new version once.

    Agents' Tests¶

    A start waits until each agent its problem names passed its Test for the loop's owner, with the current configuration ("Codex not set up for cedric yet (its configuration changed since its Test)"). A new agent version needs new Tests.

    • Each user tests their own in Account › Agents: run in their home with their settings; no credential is seen.
    • Admin › Server › Maintenance › Test agents runs them for every user on a schedule (or Run now): each user's set-up agents ("set up": logged in, own key, endpoint, model or variable, or tested before), in their loops' contexts. Disabled users are skipped.
    • A Test times out after 420 s. A failure is listed in Admin › Loops › Failures.
    • Audited as the user's "agent test". Not counted in usage.

    Accounts¶

    Admin › People › Users makes an account: a name, a password (empty: an invitation link to send the user) and a group, then Add. Links work once, for a week; there is no mail.

    Admin › People › Users: a row per user with Admin, Create, Run, Internals, a Limits cell (loops at once; Active off disables the account), groups (×, +), Last active, Show usage, and ⋯: View as (read-only), a reset or invitation link, Rename, Delete.

    Permission Gives
    Admin Administers the server and every loop. Implies Create, Run, Internals. You cannot clear your own
    Create loops Makes loops
    Run loops and agents Runs loops, Ask and agents
    Internals ("See how Flux works") Agents' prompts, thinking and commands; Flux's skills; diagram source; workbenches; the full log and record; search reasoning. Without it, turns show only replies and counts (Live); a Chat proposal is accepted by someone who has it. No group or project role gives it; audited
    • A new password logs the user out everywhere (from a link or an admin). Changed on their own Account, it keeps the current session.
    • Settings layer field by field: the server's, then each group's (by group name; later wins), then the user's. An empty field inherits. Keys and models never pair with a lower layer's endpoint; token prices are the endpoint's layer's (A group's agents).
    • Groups: a user is in none, one or several. Admin › People › Groups lists each group with members, Open projects level (Asker by default), Rename and Delete. Unrolled: the member grid (Level, a box per word, ×; All members; People adds as Member). The same grid serves projects and loop Sharing.
    • Group membership gives nothing on any loop (the words).
    • A loop is reached only by a share or by a project it is linked into. Your rights are your row, your groups' rows and your projects', together. Ask and Run also need Run loops and agents.
    • Archive, reset, delete, rename and transfer belong to the owner and admins.

    The words¶

    One vocabulary everywhere.

    • Loop words: view, ask, edit, run (on a shared loop or a project's loops); share (a loop's own: give the loop to others, at most what you hold).
    • Place words: link (link your loops into a project), curate (review knowledge, keep the library), manage (members, levels, access, title; rename, archive, delete), create (groups only: make projects; the maker is Lead).
    Place Words
    Loop share view · ask · edit · run · share
    Group membership curate · manage · create
    Project level view · ask · edit · run · link · curate · manage
    Global project level curate · manage

    Levels (a mix is Custom):

    Level Words Loop Project Group Global project
    Member none -- yes yes yes
    Viewer view yes yes -- --
    Asker view · ask yes yes -- --
    Contributor view · ask · edit · run · link yes (no link) yes -- --
    Maintainer Contributor and curate, create (on a loop: view · ask · edit · run · share) yes yes curate · create curate
    Lead every word -- yes curate · manage · create curate · manage
    • A loop's levels stop at Maintainer; Owner is shown, never given.
    • Words acting on a loop imply view.
    • Managers give levels up to their own; admins any.
    • Why some boxes are missing: linking needs share on the loop and link on the project; a loop is not curated; managing a loop is the owner's; groups never carry loop words or share; projects do not nest; a global project's visibility gives view and it gives no loop words.

    What a group gives on its projects' loops: only the project's group access: invite (default; nothing, hidden), view, or open (the project's open level, Asker by default). Its curate, manage and create reach every project of the group.

    Global projects are public (everyone sees them) or private (members and admins only). Members hold only curate or manage. Only admins and managers see others' loops in one. Who links: everyone or admins (a private one: members only).

    Renames¶

    • User (admins: ⋯ › Rename): everything moves (folder, caches, settings, shares, runs, schedules, chats, usage). Refused while anything of theirs runs. No redirects: people their loops are shared with, and the user, are told the new link. Sessions stay. One "rename user" audit entry.
    • Group (pencil in Admin › People › Groups): members, permissions and shares stay; members are told. Names ignore case; _ reserved, / refused. Refused while a linked loop runs.

    Deletes¶

    • Active off disables a user: logged out, everything kept.
    • ⋯ › Delete (admins): the dialog lists their loops, sole-managed projects, shares and groups, and asks whether their loops are transferred to a user (a clashing name becomes <loop>-<user>) or deleted. Everything else of theirs goes; the audit and history stay. Refused while anything of theirs runs, for yourself, and for the last admin. Type their name to confirm.
    • Groups › Delete: refused while it has projects (archived too; listed with links). It lists members, shared loops, its agents and settings (loops naming its agents will not start) and its machines (revoked). Type its name. Members keep their accounts and loops.

    A group's agents¶

    A group's Agents tab (#/groups/<id>/agents, admins and managers) is the layer between the server's settings and each member's.

    • FluxAgent and a tab per agent: endpoint, model, key, seconds per turn, prices (turns at once stay the server's, except for the group's own agents). A set field shows "over server"; an empty one "from server"; ↺ resets. Keys are encrypted and shown only as "set".
    • Per agent: variables, instructions (after the server's, before each member's), thinking by default, and Test (counts for each member who inherits exactly that configuration).
    • All agents: variables for every agent.
    • + Add: a group's own agent (name, kind OpenCode/Claude Code/Codex, label, extra arguments). Documents name it <group>/<name> (group name lower-cased, other characters _: Team A/foo is team_a/foo), or by name alone if unambiguous (by: foo is refused if two groups have one). It shows program not found until its program is found here.
    • Audited (group settings, group agent added, changed, removed), never values. Members see the result in Account › Agents.
    • A renamed group's agents become <new>/<name>; <old>/<name> still works until reused.
    • A member removed from a group loses its layer from their next run.

    A group's schedule¶

    The Schedule card schedules the group's own agents' turns at once, as Scheduled changes do (+ Schedule, Run now, Edit, Turn off/Turn on, Delete). Never above the admin's limits:

    • the stricter of the group's and the admin's value applies;
    • an agent on the same endpoint as a server agent shares its slots;
    • the server's pause and running limits still apply.

    The card says when the admin's limit is stricter ("The admin's limit is stricter: at most 2 at once (shared with OpenCode on box.example:8080)"). Audited (group schedule). Admin › Maintenance › Schedule lists them read-only.

    Projects¶

    A project belongs to one group (<group>/<name>) or is global (_/<name>, shown "global / …"). Names: letters, digits, -, _, unique per group regardless of case. See Groups and a project's page.

    A group's project is made on the group's page (New project: name, title, group access), a global one by admins (New global project in Admin › People › Projects). Members, levels, access, rename, archive and delete are on the project's page (Groups).

    • Levels: the words on a project. The maker is Lead. A Member sees the project and its members only.
    • Group access: invite (default; hidden), view, open (the open level).
    • Rights only add up: group access, group membership's curate/manage, project level, a global project's visibility.
    • A project's contents (files, knowledge, chats) are its own members' and admins' only (Groups).
    • Members with create make a group's projects; only admins make global ones.
    • Archiving hides and freezes a project. Everything is audited.

    Admin › People › Projects lists every project: title, address, group, loops, members, library use ("6 B of 2 KB", over when above). Per global project: Visibility, Who links loops. Row tools: open, rename, archive/unarchive, delete. New global project is below.

    Library limits: Library limit for every project (GB), or a row's Limit; empty inherits (finally a loop's 8 GB). Audited ("library limit"). An over-limit library cannot grow.

    Loops in projects¶

    A loop is in none, one or several projects, in an order its owner sets. Only its owner (or an admin) links it: into a group's project where they hold link, or a global one per its join rule. Archived projects take none.

    • In a group's project, members get their loop words on it; the group's members what its access gives. Never takes rights away. Ask and run still need Run loops and agents.
    • A global project gives no rights; users see only their own loops there.
    • Each link has learning (the collector): on by default in a group's project; in a global one off until an admin or manager turns it on.
    • Renamed or transferred loops keep their projects; a deleted project unlinks its loops and tells the owners.

    The owner sets them in the loop's Settings › Preferences › Projects (Files and settings): Add to a project…, the order, Learns, ✕. A project's page lists its loops.

    Your account¶

    Account has four tabs (#/account/agents; #/account opens Profile):

    • Profile: your groups, usage, password (asks the current one; logs out other sessions), desktop notifications, Overview layout.
    • Agents: a tab per agent: login, Test, model, variables, your own instructions; All agents for shared variables. Fields show "from server", "from group", or "over group" with ↺. Your groups' own agents have tabs too.
    • Machines: your machines (Add my machine) and the others your loops may use (Machines).
    • Shared links: every link you made (Share), with opens, Copy, Revoke; stopped when you lost the right.

    An agent is used only once its Test passed for whoever starts the loop. Tests run at once, outside any limit (Agents' Tests). Logins run in the sandbox in a small terminal; Claude Code's token is stored encrypted. Without its own settings an agent uses its own configuration (Models and agents).

    • Keys are encrypted and never shown again. With nothing set, runs use the machine's configuration (~/.config/flux/flux.env, each agent's own).
    • Model of an agent without an endpoint: From the agent lists the agent's own models (as each user's login sees them); Default (the agent's own) leaves it to the agent; with the box off, type any name.
    • Which model wins: a document's model:, then the loop's variable, then Account › Agents, then Admin › Runtime › Agents.
    • An agent's panel shows: installed (path on hover) or missing ("claude is not on the runs' PATH"), kind, version, document name; Connection and Verification pills with Test; Program, Name shown; Enabled, Offered for Ask, Thinks by default and efforts.

    • An added agent runs its own Program (or FLUX_<NAME>_BIN), else its kind's.

    Enabled¶

    Untick Enabled to switch an agent off. It is offered nowhere (a document naming it shows (disabled by an admin)), and starts, chats, asks and Tests naming it are refused: claude is disabled on this server by an admin. Running loops keep it until they stop. Audited (agent disabled, agent enabled).

    Other agents of the same kind are unaffected: an added aide of kind claude still runs its own Program, else the built-in's, else FLUX_CLAUDE_BIN, else claude on PATH. Use Enabled, not a bogus Program, to disable.

    Thinking by default¶

    Each agent's panel sets whether it Thinks by default (where a loop's box does not say: Thinking; and how Chat's Think starts: Chat), with its effort when thinking and when not (its own leaves it to the agent). FluxAgent's efforts: low, medium, high, max; built in is high thinking, medium not.

    Thinks by default Effort when thinking when not
    Each agent on its own its kind's lowest (low, or minimal)
    FluxAgent off built in (high) built in (medium)

    Precedence: a chat's Think, then the loop's box, then this default. Audited (thinking by default); applies to runs started afterwards.

    Structured answers (FluxAgent, on by default): asks the model for answers in a fixed shape; a design answer not in that shape is asked for once more, never read from the text. Turn it off for a model server that cannot: designs are then read from the reply's text, and the run's log says so.

    Instructions¶

    Instructions: text given to the agent with every task (loops, Chat, New loop › Agent, its Test). Not FluxAgent. OpenCode ships with a default (Default restores it). At most 4,000 characters; audited (agent instructions). Groups and users add their own after the server's (Account › Agents); a loop's turns use its owner's.

    Resources¶

    • Over time: CPU, memory, disks (30 days), beside every loop's tokens per second.
    • Sandbox containers: CPU, memory, processes. Whose: a loop's (Stop after its pass), Chat · user (Stop), Login · user, Agent test · user. left behind containers have Kill (the clean-up removes them too).
    • Compiler caches: each user's ccache size.
    • Disk per loop.
    • Machine picker: this server or a joined machine (its CPU, load, memory, disks, steps; a storage machine's bytes served). Figures arrive with each heartbeat (~15 s), kept 30 days.
    • Orphan caches: sandbox caches no loop owns (a deleted loop's, or not the web's). Each says whether Clean disk removes it next (goes at the next clean) or why not (in use, used in the last 14 days). Clean now runs that part; Delete removes one. A cache owned by another account shows the command to run (podman unshare rm -rf <cache> or sudo -u <owner> rm -rf <cache>).
    • Slow requests: the latest 50 over 0.5 s, and where heavy pages are made (in 4 worker processes, 60 MB each).

    The memory guard¶

    When the machine runs short of memory (RAM above Stop above, 95%, with swap over the Swap mark, 80%, or filling), the server stops the loop using the most memory, then the next, until RAM is under Until under (90%). A chat sandbox can be stopped too.

    • The loop ends failed; earlier passes are kept. Why it stopped says e.g. Stopped to free memory: the machine was at 96% (30.7 GB of 32.0 GB); this loop used 11.4 GB, the most of any.
    • Logged, audited (memory guard), and the owner is notified. It is not restarted.
    • The Server card shows memory and swap use and the last stop. Edit sets on/off and the marks (50% to 99%); audited (memory guard settings).

    The sandbox scratch cap¶

    A loop's sandbox scratch (pass working files) is capped by its Scratch /tmp size: the loop's own (Settings › Advanced), else the server's default (Admin › Runtime › Sandbox › Limits), held to the maximum. None set: no cap.

    Clean disk trims each scratch every five minutes, oldest first; never recent files, a running loop's current work, or the baseline's and decision's files. Reported in the loop's log, Maintenance history and Disk per loop (trimmed 4.2 GiB today). Trimmed files show no longer kept.

    Commands¶

    Admin › Activity › Commands summarises what the loops' agents ran over 1, 7 or 30 days (UTC), per loop, agent and mode: commands and flags that do not exist, each flux command's uses and failures, shell programs and tools, commands repeated across turns, turns and failures. No output beyond known error lines. Export saves JSON. Up to a minute behind.

    Maintenance¶

    Task What it does Its setting

    Condense history Logs over 50 MB and journals over 20 MB keep their recent part (older gzipped); old transcript turns keep only usage. Never results, ideas or decisions older than (days), 14
    Compact and check Compacts and checks the database and every record; loads each stopped loop's document; with backups kept over 0, saves the database and secret.key to backups/ backups kept, 0 (no backup)
    Prune server tables Expired sessions and invitations; old login failures, notifications, refused-host log; old audit lines older than (days), 30; audit (days), 365 (0: all kept)
    Prune run history Keeps each loop's latest starts in the run list keep, 200
    Test agents Off by default: the agents' Tests, below none
    Clean leftovers Off by default: what updates leave behind, below. Never a record none

    • Running loops are touched only where the table says; archived loops only by checks and compaction.
    • Record edits are the loop's own (Settings › Record, never scheduled): Prune stale records, Prune empty starts, Prune failed designs (pick a stage, or Any stage; e.g. Deletes 143 failed designs (stage gate) in bob/x: their rows, their designs' text and the pass files only they have ... Cannot be undone.), Invalidate all, Re-Evaluate (Results).
    • Test agents: each user's set-up agents, in their loops' contexts, and the server's shared configurations as the first admin (Agents' Tests). Two at once; outside limits; audited "(by maintenance)". One failure fails the run; a user whose Test newly fails is told.
    • Clean leftovers (after an update, or weekly), on every loop at rest or one:
    Left behind By Removed when
    problem.yaml.orig, NAME.problem.yaml.orig beside a loop's document an earlier Flux's document migration kept the original the document is there and loads
    files in the data folder's kept/ the server, to start sooner after a restart, named for its code made by other code than the server runs now (never read again), or half-written by a process gone over an hour ago

    It never removes records: out/.NAME.db.before-vN copies and stray -wal, -shm, -journal files are listed as kept for you to delete. It skips running loops. Each removal is audited. Old prepared environments are removed by updates themselves.

    Tabs: Tasks (running, queued, failed, done, off), Schedule (scheduled changes), History (every run, the last 1000; chips Failed, Schedule, Run now).

    • Each task has Run now and Edit. One task runs at a time; others queue (queued · 2nd, Cancel). A restart drops the queue.
    • Run now asks first when it deletes or rewrites data (Deletes pass folders older than 3 days in 12 loops (3 running) ... Cannot be undone.), and says nothing when there is nothing to do. Also from Edit › One loop › Run and a loop's own Settings.
    • On one loop: Clean disk trims scratch, removes old pass folders and its sandbox cache; Condense history condenses its log, journal and transcript; Compact and check compacts, checks and loads its document.
    • Schedules: every N minutes, hours or days; daily at a time on picked days; or cron. A time already past waits for the next day.

    Backups and restore¶

    Back up server database saves the database and secret.key to backups/server-<time>/ while the server runs.

    To restore:

    1. Stop the server.
    2. Move flux-web.db and any flux-web.db-wal and flux-web.db-shm aside (keep them).
    3. Put the backup's flux-web.db and secret.key in the data folder.

    4. Start the server.

    5. Never copy a database in while the server runs.

    6. A start that finds mismatched files is refused, naming them; nothing is deleted. Copy all three together before moving any: the -wal holds committed changes.

    Scheduled changes¶

    + Schedule: pick a kind, its fields, then when.

    Kind What it does
    Turns at once Sets an agent endpoint's turns at once or FluxAgent's requests at once (whole number; 0 no limit). Group agents are scheduled by the group (A group's schedule)
    Pause starts Pauses new starts with a reason (up to 200 characters), or resumes. Running loops go on; starts and restarts are refused with the reason
    Running limit A user's running-loops limit (0–64, or default), or the server's default (0–64, or default). New starts only
    Stop loops Stops running loops after their pass: all, one user's, or one. Now stops at once
    Start a loop Starts one loop as its owner, with its last start's options, for 1–1000 passes or until stopped. Refused (a failed run) if gone, archived, owner disabled or at limit, starts paused, or already running
    • When: daily at a time on picked days, or Advanced: cron expression (*/15 9-17 * * 1-5: every 15 minutes, 09:00-17:59, weekdays). Server time zone, shown.
    • Each row: schedule, next and last run, result, Run now, Edit, Turn off/Turn on, Delete.
    • Changes apply at every loop's next turn. Lowering a limit stops no running turn.
    • A missed stop or start is not done later. Settings (pause, limits) take their latest past value when the server starts.
    • Audited, e.g. scheduled: Claude Code turns at once → 4 (was 1).

    Example: people by day, loops by night:

    Change When
    Claude Code turns at once → 1 daily at 08:00, Mon–Fri
    Claude Code turns at once → 4 daily at 20:00, every day

    A nightly run: Start a loop at 20:00 until stopped; Pause starts at 20:05 (nightly runs); Stop loops at 07:00 after their pass; Pause starts → Resume starts at 07:30.

    Parallel work¶

    A loop runs one agent turn and one tool step at a time unless an admin ticks Allow parallel work in its Settings › Preferences › Advanced; then its document says how much.

    • One agent turn at a time counts every agent and model turn of the run (designs, repairs, a trunk's agents, the passes' knowledge steps and buds). Knowledge steps (papers, workbench, ideas cleanup) go after the designs' turns; a FluxAgent cleanup lets a design in between two of its requests.
    • One tool step at a time: one design's check and measurements at a time.
    • pipeline: true still pipelines: the next design's agent turn runs while the previous design is checked and measured. Live says parallel work is off.
    • This holds on the server and on server machines. On its owner's own machine a run may always work in parallel; on a group's machine, per the group's Allow parallel work on our machines (Machines).
    • Running limits, turns at once and pauses still apply.

    Execution¶

    Admin › Loops › Controls › Execution says how loops run from their next start: Shared (the default) or Old loops (fallback), the way loops ran before, kept while the shared way is new. A loop that is running keeps its way until it ends. Each change is in Audit.

    Sandbox¶

    Every run is sandboxed unless a loop's Settings › Preferences › Advanced (admins) says otherwise. Network: open, or an allowlist; HTTP(S) goes through the proxy; raw TCP/UDP is per loop (Sandbox).

    Allowlists¶

    Every allowlist (sandbox, Chat, a loop's extra hosts, an agent's hosts):

    Entry Allows
    dl.acm.org that host only
    *.acm.org or .acm.org acm.org and every subdomain (dl.acm.org, www.acm.org, a.b.acm.org)
    10.0.0.0/8, 192.168.1.20, ::1 the addresses in the range, or that address
    localhost this machine (127.0.0.1, ::1)
    • Separate by new lines, commas, semicolons or spaces; # comments.
    • Case, a trailing dot and a port are ignored (DL.ACM.org.:443 is dl.acm.org); a pasted URL keeps its host.
    • * alone is refused: choose open.
    • The page shows how it reads (Understood as: acm.org and its subdomains · arxiv.org only).
    • A redirect to another domain is refused by that host. Recently blocked lists refused hosts; click to add. The agent sees: flux sandbox: refused www.acm.org (not on the network allowlist -- add www.acm.org or *.acm.org).

    Limits apply to every sandbox (runs, checks, chats, the author, Tests, logins). For CPUs, memory, processes and scratch /tmp:

    • Default: when the loop sets none.
    • Maximum: higher asks are clamped (memory 8 GB clamped to 1 GB by the server).
    • Empty: no limit (processes: 4096).

    CPUs: e.g. 2 or 0.5, up to the machine's count. Memory and scratch in GB (128, 0.5), memory up to the machine's RAM. Scratch also caps disk use (the sandbox scratch cap). Audited (sandbox limits); new sandboxes only. Read-only on a server started without the sandbox.

    Proxy¶

    The proxy for runs, agents, Chat, logins, the author, and Flux's model calls, sandboxed or not.

    • From the host (default): the server's environment, /etc/environment, /etc/environment.d/*.conf, ~/.config/environment.d/*.conf, then the login shell's exports. Shown as e.g. From /etc/environment: HTTP http://proxy:3128 · not for .corp.example.org.
    • Set here: HTTP and HTTPS proxies (http://host:port, optionally user:password@) and a not through it list (hosts, .domain, *.domain, IPs, CIDRs). Credentials are encrypted and shown as http://***@proxy:3128.
    • Sandboxes get HTTP_PROXY, HTTPS_PROXY, NO_PROXY (localhost always added).
    • In effect shows the result. Audited (sandbox proxy); applies to what starts afterwards.

    Chat¶

    Admin › Runtime › Chat sets what users may use in Chat; users switch allowed features per chat.

    Feature Allowed Default
    Chat tab The user has Chat in the top bar. Off, every other feature is off too. on
    Network beyond the base allowlist A chat may also reach the hosts listed under Network beyond the base (These hosts), or any host when it is Open. off
    Workbench A chat may read and write the user's workbench. on
    Loop access A chat may read the user's loops, their own and those shared with them, read-only. on
    • Everyone is the server's value; Overrides per group and user (default, on, off). User beats group beats server; among groups, off wins. Add user adds a row.
    • Chats always have the sandbox's base allowlist (Sandbox). With nothing listed and not Open, the network feature stays off.
    • A disabled feature is greyed with why (turned off by the admin on this server, for the group …, for you).
    • Applies from each chat's next message. Audited (chat permissions, chat created, chat deleted).

    FluxAgent on the web (web tools; only with the chat's Network on; never private addresses):

    Setting Default
    MB each 50 1 to 500. A larger download is refused.
    Seconds a fetch 60 5 to 300.
    Ports beyond 80 and 443 none For example 8080. Other ports are refused.
    Web search None SearXNG (its address, for example https://searx.example.org), or Brave Search (its subscription token).
    • Paper search needs export.arxiv.org and api.openalex.org allowed.
    • The search provider is reached as set, regardless of the host list.
    • The Brave key is encrypted; replace or Clear it. Fetches are audited (chat web).

    Other limits:

    Setting Default Range
    Minutes per coding-agent answer 8 1 to 60
    Tool calls per coding-agent answer 40 5 to 400
    Diagram tries (Chat) 5 0 to 10
    Attached MB each (Attached files) 50 1 to 2048
    Attached Files a message 10 1 to 50
    Sandbox kept idle (minutes; 0: one sandbox per answer) 30 0 to 240
    • An answer stopped at a limit keeps what was written; with nothing written it fails, naming the limit.
    • How Think starts: thinking by default.
    • Answers run sandboxed under the server's limits with the user's agent settings.
    • A user's chats share one sandbox. It restarts when chat, sandbox, proxy, agent or model settings change, or Flux is updated; an answer in progress is rewritten (restarted: the admin changed the chat settings, restarted: Flux was updated).

    Sharing¶

    Sharing governs read-only links (Share):

    • Links for anyone (on): off stops making and opening them (signed-in links unaffected).
    • The longest a link for anyone lasts: 1, 7, 30 or 90 days (default 90).
    • Per user: link count and Revoke (all of theirs).

    Links are rate-limited and built with the maker's current rights. View as cannot make links. Audited under Shared links.

    Environment variables¶

    Applied in order, later wins: the server's (Admin › Runtime › Agents › All agents), the user's (Account), each linked project (the first project wins; Groups › Variables), the loop's (Settings › Preferences). Secrets are encrypted. Sandbox variables, PATH, HOME and model settings cannot be set.

    Version¶

    Admin › Server › Version shows the running code and updates it, fast-forward on main only.

    Tile Shows
    Running The commit's short hash and subject
    Update "Up to date" or "3 commits behind origin/main" with Update to; "origin/main · checked 2 min ago"; Check now; queued or building updates (Cancel)
    Up Uptime ("57 min")
    Checkout Branch (amber off main), clean or changed files, path
    Nix The toolchain's locked revisions; the prepared environment (a toolchain change is built before the restart)
    • Checks: opening the tab fetches origin/main when due (daily; hourly after a failure), in the background. A failed check keeps the last good result. Check now checks at once.
    • Update: refused off main, with local changes, or when main diverged. Running loops finish on their version. A loop started on a dirty checkout holds updates until it ends.
    • Toolchain changes build the new environment first, in the background (the tab follows the build); then fast-forward and restart. A failed build changes nothing. Code-only updates go at once.
    • Roll back: to the commit the last update came from, while the checkout is unchanged. Refused with local changes or while a loop runs on the checkout itself.
    • Records: a newer Flux upgrades a loop's record once (next start, or Compact and check), keeping a copy. A running loop's record waits.
    • Old data: this Flux reads records from version 7 and loop files from Nov 12, 2026. Older ones are refused naming Flux 9957e3728 (open, start or import there, export again). A loop file with old box names (generate:, orchestrate:, ...) or params:: convert in Flux fdfd1faf0 (Server › Old data › Migrate). A document with an old key names the Flux that explains it. Nothing is converted here.
    • History: who, when, from, to, result; also audited.

    The system service restarts itself after an update. A server started by hand says to restart it.
