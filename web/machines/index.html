    Machines¶

    Run some steps on another machine: one with an FPGA board, a licensed tool, or more cores or memory. Add it once from the Machines page and one line run on it; then a check or stage whose needs matches its labels runs there, and its numbers come back as if run on the server (Resource hints).

    Whose machine it is¶

    A server machine A group's machine Your own machine
    Added by an admin an admin or one of the group's managers any user
    Used by every user's loops the loops of the group's members only the loops you own: never a loop shared with you, never anyone else's
    Added in Admin › Runtime › Machines the group's Machines tab, or Admin › Runtime › Machines (Role: A group's) Account › Machines
    • A loop uses its owner's machines, whoever starts it. A step goes to any machine its needs match; no kind is preferred.
    • A member who leaves a group (or is disabled) stops using its machines within seconds; running steps finish.
    • Deleting a group revokes its machines and cancels unused codes.
    • Machine names are unique across the server.

    What the machine needs¶

    • Linux with systemd and Podman 4.9+ (cgroup v2): Ubuntu 24.04, Debian 13, Fedora, RHEL 9.4+. The line delegates cgroup controllers to the flux account as the server installer does (System service).
    • Nix, multi-user. The line lets flux use it and adds the binary caches (cache.nixos.org, nixchip0.cachix.org), as the server installer does.
    • Network to the Flux server and the public Nix caches. No Git, repository access or credentials.

    Run the line with sudo. It installs the runner as the system service flux-worker under the flux account. If something is missing it says what and stops; run it again after.

    The Machines page¶

    • Admin › Runtime › Machines: every machine (server, group, user).
    • A group's Machines tab (#/groups/<id>/machines): that group's.
    • Account › Machines: yours, and below them the other machines your loops may use (read-only), so you know which labels to ask for.

    Each shows:

    • Totals: cores, memory, devices (fpga=1), and use. "1 unhealthy" flags a machine taking no steps.
    • A row per machine: labels (× removes, + adds: lab, fpga=1, board=zcu104), use (2/16 cores, 8/56 GB), health (healthy, unhealthy with why, setting up or updating with progress, draining or drained, away after five silent minutes), running steps, Flux version (old when behind), last heard. Menu: Rename, Drain/Resume, Rotate keys, Revoke.
    • This server: the first row (accent dot), where unlabelled steps run. Admins give it labels and Rename it.
    • Waiting: steps no machine has taken, and why.
    • Codes not used yet, with Cancel.

    + Add machine (admins pick the Role) or + Add my machine: a name and labels, then the line to run, with Copy (and a hash-checked form for plain HTTP).

    Labels set on the page replace earlier ones. A user's machine's labels are set only by that user; admins can still drain or revoke it. Group machine changes are audited (group machine).

    The line¶

    + Add machine (or + Add my machine) makes a one-time code and shows the line to run on the new machine, with Copy:

    curl -fsSL http://flux.example.org:8765/worker/install.sh | sudo sh -s -- 'fx1-…@…'
    • The code works once, for one hour.
    • The line checks Podman and Nix, makes the flux account, joins, gets Flux from the server, prepares tools (~2 GB the first time), tests a container, and starts the flux-worker service. The machine's row shows its progress (setting up).
    • Files: /var/lib/flux-worker; cache: /var/cache/flux-worker.
    • Run it again (no code needed) to repair or change options; it keeps the machine's identity.
    • Over plain HTTP, use the page's hash-checked form.
    • Options after the code: --label KEY=VALUE (repeat), --jobs N (steps at once, default 2).

    A machine added before the system service¶

    A machine whose runner was a user service takes no steps. Revoke it, remove its user service on the machine, and add it again with a new code.

    Labels and needs¶

    flow:
  measure:
    board:
      run: "{python} {home}/on_board.py {artifact}"
      metrics: [latency]
      needs: {fpga: true, board: zcu104}
    needs Matches
    key: true The machine has the label
    A number (fpga: 1) Takes one of a counted resource; fpga=2 runs two such steps at once
    A word (board: zcu104) Exactly that value
    cores, memory, disk, arch, os What the machine measures itself (not settable by label)
    • Design's run, the baseline's, a search's run and the scope's commands take needs too. Agent work always runs on the server.
    • A whole loop on a machine: needs in its mode block (flow: {needs: {bigmem: true}} or trunk: {needs: ...}). Requires the server's admin to allow whole-loop runs, and a machine joined as a full machine. The log's start line says where it runs.
    • Parallel work for a whole-loop run: on the server or a server machine, the loop's Allow parallel work; on your own machine, always; on a group's, the group's Allow parallel work on our machines.
    • Set labels in the machine's row (+, ×), or with --label on the line. A label only your machine has (alice-board: true) keeps your steps there.
    • This server's labels: its row (admins).

    Limits¶

    Each step runs in its own Podman sandbox with the loop's sandbox settings (never above the machine's size) and the server's network policy. A step without memory in needs reserves none.

    Which machine a step goes to¶

    • A free machine holding most of the step's inputs (earlier stages, input files) is preferred. A step never waits for "its" machine.
    • The user who waited longest since their last step goes first.
    • If this server matches too, whichever is free first runs it.
    • Runner cache: a quarter of the disk, at most 50 GB, least recently used evicted.

    Proxies¶

    The line and the runner honour HTTP_PROXY, HTTPS_PROXY, NO_PROXY (set them in your shell before the line; it reads them despite sudo). Give nix-daemon the proxy too when caches need it.

    When a machine cannot run a step¶

    A full disk, a failed sandbox or missing tools are the machine's fault: the step returns to the queue for another machine, and this one is unhealthy until it checks itself again. A step killed for lack of memory runs once more. The machine's row shows its labels, steps and health.

    Updates¶

    A machine updates itself when the server's Flux changes: it stops taking steps, gets the new Flux, prepares tools, checks itself, and restarts in seconds with the same identity. Running steps carry on (one that cannot is measured again). It shows "updating" meanwhile.

    A failed update keeps the old Flux and takes no steps (unhealthy, with why); it retries after ten minutes or at the server's next update. A runner started by hand, or added before the system service, cannot update: run the line again (or re-add it).

    Drain a machine¶

    Drain in its row: it finishes running steps and takes no new ones. Resume puts it back. Owners can drain their own machines.

    A storage machine¶

    A storage machine caches loop files for the runners: each file comes from the server once. It runs no steps.

    Admins: + Add machine, Role Storage. Its line ends in --role storage.

    • Needs Nix and the network, no Podman.
    • Runners reach it on port 8766. Options: --listen HOST:PORT (default 0.0.0.0:8766), --url URL (default http://<its name>:8766).
    • Keeps files unused for a week at most, within half its disk.
    • While it is down, runners fetch from the server.
    • Shown with a Storage tag.

    Rotate a machine's keys¶

    Rotate keys in its row (admins for any, you for yours). New keys at the next heartbeat; the old ones stop working. No new join code. The row says "new keys asked" until done.

    Rename a machine¶

    Rename in its row (admins for any, this server included; you for yours). Names: lower-case letters, digits, ., _, -; unique (revoked machines and pending codes included). Same machine: keys, labels and steps stay. Past results keep the old name.

    Remove a machine¶

    Revoke in its row: its key is refused from now on, and the steps it holds go back to the queue. On the machine, disable the flux-worker service and remove its unit, /var/lib/flux-worker and /var/cache/flux-worker.
