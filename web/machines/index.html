    Machines¶

    A loop can measure some of its steps on another machine: one with an FPGA board, a licensed tool, more cores or more memory than the server has. You add the machine once with one line; from then on, a check or a stage whose needs names one of its labels runs there, and its numbers come back to the loop as if it had run on the server (Resource hints).

    Whose machine it is¶

    A server machine Your own machine
    Added by an admin any user
    Used by the loops of users whose group's Credentials is Server settings (as the server's agents) only the loops you own: never a loop shared with you, never anyone else's
    Code made with Admin › Runtime › Machines, or flux machines join-code on the server Account › Machines, or flux machines join-code --mine --user NAME on the server

    A loop always uses its owner's machines, whoever starts it.

    What the machine needs¶

    • Linux with systemd and Podman 4.9 or later from the distribution (cgroup v2): Ubuntu 24.04, Debian 13, Fedora, RHEL 9.4 and later have it. The line lets Podman limit the flux account's jobs itself. When the account's user manager does not have the cpu, memory and pids controllers yet, it writes /etc/systemd/system/user@.service.d/delegate.conf, runs systemctl daemon-reload and restarts that manager. It restarts only flux's manager, and only when nothing of flux's runs under it; otherwise it asks you to restart it later or reboot. A drop-in of yours that already delegates them is left alone. A host still on cgroup v1 stops the line (details).
    • Nix, multi-user (the official installer). The line sets it up for the flux account itself: it adds flux to allowed-users when Nix does not let it in yet, and adds Flux's binary caches and their keys (cache.nixos.org and nixchip0.cachix.org) when they are missing, then restarts nix-daemon. It writes them to /etc/nix/nix.custom.conf when your nix.conf includes that file (the Determinate installer's), else to the end of /etc/nix/nix.conf, in a block marked # Flux, keeping your own settings and a copy of the file as it was (nix.conf.before-flux). It never makes flux a trusted user. On NixOS it prints the nix.settings to add instead. FLUX_INSTALL_BUILD=1 leaves the caches alone (the tools then build on the machine, for hours).
    • The network to the Flux server and to the public Nix caches. Nothing else: no Git, no access to any repository, no credentials.

    Run the line with sudo. The runner is a system service, flux-worker, running as the account flux (the line makes it when it is missing; on the server's own machine it is the server's account). When something is missing, the line says exactly what to install and stops; run it again afterwards.

    The Machines page¶

    Admin › Runtime › Machines shows every machine, the server's and every user's (a user's carries its owner's name); Account › Machines shows your own and, below them, the server machines your loops may use (when your group's Credentials is Server settings): each one's name, labels, size and health, read-only, so you know which labels a step's needs can ask for. Both show:

    • At the top: how many cores, how much memory and how many of each device (a label with a number, such as fpga=1) the machines have, and how many are in use (on the admin's page, this server's own machine included). A device in use on every machine is simply busy, not a fault; "1 unhealthy" beside a total says a machine with it takes no step now.
    • A row per machine: its labels (× takes one away, + adds one: lab, fpga=1, board=zcu104), its use (2/16 cores and 8/56 GB: what its steps count of its size, each with a bar), its health (healthy, unhealthy with the reason, setting up or updating with what it is doing and for how long -- fetching its code, building its environment (with the paths fetched so far), checking itself --, draining or drained, away when it has not been heard from for five minutes, even while it was setting up), its running steps, its Flux version (old while it is behind the server's) and when it was last heard from. Point at a row for Rename, Drain/Resume, Rotate keys and Revoke (asked first).
    • This server is the first row on Admin › Runtime › Machines, tagged this server: the machine the server runs on, where every step without a label runs. Its use is what the steps running on it count. An admin gives it labels in its row (× and +, as any server machine's); nothing to drain or revoke, and Rename (its name is its host name until an admin renames it). On Account › Machines it is the first of the server machines, for everyone, its labels read-only.
    • Waiting: the steps no machine has taken yet, whose they are, what they need and why they wait.
    • Codes not used yet: each join code still good, with Cancel.

    + Add machine (an admin's: a server machine, or one of a user's own, chosen under Role) or + Add my machine asks for a name and labels, then shows the line to run on the new machine once, with Copy and, folded under it, the checked form for plain HTTP.

    Labels set on the page replace the ones the machine was given before (on the code, on the line or in its capabilities.yaml): a label taken away here stays away. A user's own machine's labels are set by that user alone, on Account › Machines; on Admin › Runtime › Machines they show read-only, and an admin can still Drain, Resume or Revoke the machine.

    Add a machine from the server's console¶

    On the server, make a join code (an admin's makes a server machine; --mine makes one of a user's own):

    flux machines join-code --machine fpga-1 --label fpga=1 --label board=zcu104 --url http://flux.example.org:8765

    It prints the code and the line to run on the new machine:

    curl -fsSL http://flux.example.org:8765/worker/install.sh | sudo sh -s -- 'fx1-…@…'
    • The code works once and for one hour (--minutes for less). A second run of the same line, or a run after the hour, joins nothing: make a new code.
    • The line checks Podman and Nix, makes the flux account and its folders, joins the server, gets Flux from the server itself, prepares its tools from the public Nix caches (about 2 GB the first time), checks that a container starts, and starts the runner as the system service flux-worker (systemctl status flux-worker, journalctl -u flux-worker -f). It says each step as it goes.
    • The runner keeps its files in /var/lib/flux-worker and its cache in /var/cache/flux-worker.
    • Run the same line again (no code needed once the machine has joined) to repair the machine or change its options: it does only what is missing, keeps the machine's identity and restarts the runner.
    • Over plain HTTP, the server also prints a second form of the line that checks the installer's hash before running it; prefer it when the network between you and the server is not trusted.

    Options after the code: --label KEY=VALUE (repeat) and --jobs N (steps at once, default 2; a run again keeps the number it had).

    A machine added before the system service¶

    A machine added with an earlier form of the line (its runner a user service of your account) is no longer moved over by the line, and takes no step: the Machines page says it runs code older than the server's. Stop and remove its user service, then add it again with a new code:

    systemctl --user disable --now flux-worker.service
rm -rf ~/.config/systemd/user/flux-worker.service ~/.local/share/flux-worker
systemctl --user daemon-reload

    Labels and needs¶

    A machine's labels are what a step can ask for:

    flow:
  measure:
    board:
      run: "{python} {home}/on_board.py {artifact}"
      metrics: [latency]
      needs: {fpga: true, board: zcu104}
    • key: true: the machine has the label; a number (fpga: 2) counts boards, GPUs or seats.
    • key: "2025.2": exactly that value; key: ">=2025.1": that version or newer.
    • cores, memory, disk, arch and os are what the machine measures itself; a label cannot set them.

    A command that writes designs can ask for a machine the same way: Design's run, the baseline's, a search's run and the scope's commands take needs too (Resource hints). An agent's work always runs on the server.

    Give labels on the code (--label), on the line (--label after the code), or in capabilities.yaml in the runner's folder (/var/lib/flux-worker). A label only your machine has (alice-board: true) sends your steps there and nobody else's.

    This server's own machine takes labels too: in its row on Admin › Runtime › Machines, or on the server with flux machines label NAME --label fpga=1 --label board=zcu104 (all of its labels at once; none clears them; the same command sets a joined server machine's). A step whose labels it has runs on it like any other step, for users who may use the server machines.

    Limits¶

    Each step runs in its own Podman sandbox with the loop's sandbox settings (CPUs, memory, processes, /tmp), never above the machine's own size, and the server's network policy. A step whose needs says no memory sets none aside on the machine: it goes to any machine with its labels, and the sandbox's memory is its only limit.

    Which machine a step goes to¶

    When several machines have a step's labels, a free one that already holds most of what the step needs gets it: the design's earlier stages (a runner keeps a design's intermediate files between its steps) and its input files. A step never waits for "its" machine: if that one is busy, another free machine with the labels runs it at once, with the same numbers. When several users' steps wait, the user who has waited longest since their last step started goes first. When this server has a step's labels too, the step runs here as soon as this server has room for it, and on a joined machine as soon as that one does: whichever is free first.

    What a runner keeps counts toward its cache limit (FLUX_WORKER_CACHE_GB on the machine, default a quarter of its disk, at most 50 GB); the least recently used goes first.

    Proxies¶

    The line and the runner honour HTTP_PROXY, HTTPS_PROXY and NO_PROXY. Set them in your shell before the line (it reads them even though sudo does not pass them on); the runner keeps the ones set then. Nix fetches through its own daemon: give the daemon the proxy too (its service's environment) when the caches are only reachable through it.

    When a machine cannot run a step¶

    A full disk, a sandbox that does not start, or tools that are no longer there are the machine's problem, never the design's: the step goes back to the queue and runs on another machine that has its labels (or waits for one), and the machine is marked unhealthy until it checks itself again. flux machines list on the server shows each machine, its labels, its jobs and its health.

    A step killed because the machine ran out of memory runs once more, on another machine when one has its labels.

    Updates¶

    A machine added with the line updates itself when the server's Flux changes: it takes no new step, gets the new Flux from the server, prepares its tools again (only what changed, from the public Nix caches) and checks itself while its running steps go on, then restarts on the new Flux with the same identity in a few seconds. The steps it was running carry on through the restart and their results come back as usual; one that cannot (its container stopped meanwhile) is measured again, on this machine or another. Nothing to do on the machine, and no new join code. The machine shows "updating" only while it prepares and restarts; its steps stay in its jobs.

    If an update fails (its tools do not build, its check fails), the machine stays on the Flux it had and takes no step until an update succeeds: flux machines list shows it as unhealthy with the reason, and it tries again after ten minutes or at the server's next update. A runner started by hand from a Flux checkout cannot update itself: run the install line on it once more (it keeps its identity). A machine added before the system service cannot either: add it again (above).

    Drain a machine¶

    To take a machine out of use for a while (maintenance, a board to swap), drain it on the server:

    flux machines drain fpga-1

    It finishes the steps it is running and takes no new one; other machines with the same labels take them meanwhile. flux machines resume fpga-1 puts it back. Its owner can drain their own machine too.

    A storage machine¶

    With many runners, each one fetching a loop's files from the server adds up. A storage machine holds those files for them: each file comes from the server once, and the runners fetch it from the storage machine. It runs no step itself.

    Add one as an admin: + Add machine, Role Storage, or on the server flux machines join-code --role storage --machine store-1. Run the line it gives on the storage machine; it ends in --role storage:

    curl -fsSL http://flux.example.org:8765/worker/install.sh | sudo sh -s -- 'fx1-…@…' --role storage
    • It needs Nix and the network to the server, but no Podman.
    • The runners must reach it on its port, 8766 by default. Options after --role storage: --listen HOST:PORT (where it listens, default 0.0.0.0:8766) and --url URL (the address the runners use, default http://<its name>:8766).
    • It keeps files unused for a week at most, and at most half of its disk (FLUX_STORAGE_GB on the machine for another limit); a file it no longer has is fetched from the server again.
    • While it is down, drained or unreachable, the runners fetch from the server as before. Nothing else changes.

    It shows on the Machines page with a Storage tag.

    Rotate a machine's keys¶

    Each machine has its own keys, made when it joined. To replace them (a machine that changed hands, a disk that was copied), choose Rotate keys in its row's menu (an admin for any machine, you for your own), or on the server:

    flux machines rotate fpga-1

    The machine makes new keys at its next heartbeat, within seconds, and carries on as the same machine with no new join code; its old keys stop working. Steps it is running finish as usual. The row says "new keys asked" until it has done so.

    Rename a machine¶

    Point at its row and choose Rename (an admin for any machine, this server's own included; you for your own), or on the server:

    flux machines rename fpga-1 lab-east

    A name is lower-case letters, digits, ., _ and -, and no two machines share one: a name another machine has (a revoked one's too, or one a join code not used yet gives) is refused, and the refusal says whose it is. It is the same machine under a new name: no new join code, its keys, labels and steps stay its own, a step it is running finishes there and shows the new name at once, and the machine keeps its new name from its next heartbeat. Results measured before keep the name the machine had then.

    Remove a machine¶

    flux machines revoke NAME on the server (or, for your own machine, its Revoke): the machine is refused from then on. On the machine, sudo systemctl disable --now flux-worker, then remove /etc/systemd/system/flux-worker.service, /var/lib/flux-worker and /var/cache/flux-worker.
