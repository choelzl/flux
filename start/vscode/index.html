    VS Code¶

    Run a loop on the folder you have open in VS Code, on your own machine, and keep it on the Flux server: Live, Results, notes and Stop work from the web as for any loop. The loop's agents use your machine's own logins (Claude Code, Codex, OpenCode as you have them).

    Install¶

    The extension brings no Flux of its own: once you sign in, it downloads the Flux that runs your loops, and the Python it runs on, from your Flux server. The machine where the folder is needs only:

    • your coding agent (Claude Code, Codex or OpenCode), installed and logged in -- its VS Code extension may be enough (below);
    • the tools your loop's checks run (compilers, simulators): its steps run on this machine, with your own PATH -- a step's python3 is yours; Flux adds only its own flux and fluxpreset.

    No Python, no Nix, no Podman, no containers: the machine is the loop's boundary. It runs Linux on x86_64 (x64) or aarch64 (Arm64) with glibc 2.27 or later -- most distributions, WSL, dev containers, a Remote-SSH host from VS Code on Windows or macOS; not Alpine (musl).

    1. On the Flux web, Account › Machines › VS Code extension: Download.
    2. In VS Code: Extensions › ⋯ › Install from VSIX… and pick that file.
    3. Sign in. The first time, a notification shows Flux downloading from the server (some 45 MB).

    On a machine it does not run on, the Flux view says what it runs on.

    After the server is updated, the extension fetches the server's new Flux by itself and moves to it once no loop is running here (a window's folder or another's): a run in progress finishes on the one it started with. The move is one handover: the old worker ends, the new one starts and has 90 seconds to connect and stand; a new Flux that does not start, connect or stand gives way to the one before, which runs again, and the bottom line says why until Refresh tries it again. A worker that ended before the move is moved all the same: an update never leaves this machine without one. A run here never holds the server's update: while the server restarts the run goes on, and the run reaches the new server once it is back (its journal, its record, its end). Live says which Flux it runs: "runtime 3581a0c2". Without the server, the Flux it has keeps working. The line at the bottom of the Flux view says which code runs here: code 3581a0c ✓ when it is the server's, updating to … while it moves to a new one.

    The extension updates itself too: install it by hand once, and after a server update it installs the server's new one and says Flux updated: Restart Flux to use it.

    To update now, use Refresh in the Flux view's ⋯ menu: it fetches the server's new Flux and extension at once and says Flux is up to date when there is nothing new.

    Your agents¶

    Flux finds each agent's program on this machine, first found first:

    1. a program the loop's problem.yaml names for it (bin, or an agent of its own);
    2. the agent's VS Code extension, when it carries the agent's program: Flux uses that program;
    3. the program on the machine's PATH.

    Their sign-in is the agent's own: logging in from the Claude Code or Codex panel logs in the agent your loop runs. When neither is found, the graph's head and the agent's row in its box's section of problem.yaml's form say so (hover it for how to install it). The row says where each agent was found ("Claude Code (VS Code extension)", PATH, this document's).

    FluxAgent is the server's: its steps ask the endpoint set on the server (Admin or Account › Agents › FluxAgent) through the server, so nothing has to run on your machine for it.

    Sign in¶

    1. On the Flux web, Account › Machines › New VS Code code: give it a name (this VS Code's, such as laptop) and copy the code. It is shown once.
    2. In VS Code, open the Flux view: its Setup section says what is next. Set the server opens Flux: Server (flux.server) in Settings: the server's address, such as http://flux.example:8080 (Settings marks an address that is not one).
    3. Sign in with a VS Code code (in Setup, or from the Command Palette) and paste it.

    A code signs in one VS Code, once, and with it every folder you open in that VS Code: you sign in once. The code is used up (pasted again, it is refused); a code nobody used expires after a day.

    Once signed in, VS Code stays signed in -- across reloads, restarts, and in VS Code in a browser from any browser -- until you revoke it or sign out. It only attaches, creates, starts, stops and notes your own loops, and downloads the server's Flux; everything else stays on the web.

    Account › Machines lists the codes not used yet (Revoke one you no longer need), and each signed-in VS Code as one machine under the code's name, tagged VS Code, its Loops column naming the loops attached there -- running, idle, or folder not open (Machines). Revoke on it signs that VS Code out and refuses its machine's key; its loops stay yours. Sign out in VS Code signs it out from there, for every folder; the machine stays.

    A machine revoked (or removed on the server) stops, and VS Code says so; revoked, VS Code is signed out there too. Sign in again and Attach (or the notice's Attach): it joins anew under the same name. Nothing to delete by hand.

    Attach¶

    Open your project's folder and choose Attach this folder in Setup (or on the status bar). Its loop lives in the folder's .flux/: problem.yaml, the loop's scripts, its results and what its runs write. Its commands reach your project's files as {project}/... (Document). Flux:

    • sends the .flux folder once to the server as a loop of yours, named after your folder;
    • adds /.flux/ to your folder's .gitignore: the loop stays out of your repository;
    • adds this VS Code to Account › Machines as one machine named after your code (the first folder attached joins it; the next ones use it), and makes it the loop's home: the loop runs there from now on. The machine runs the loops of the folders open in your VS Code windows, several at once (one run a loop); a window closed stops its loop's run, and the last window closed ends the worker.

    Until the loop is attached, Setup offers Attach this folder; a folder with no loop yet offers New loop… (below); the status bar names the same step. The Loop view shows once Flux is on this machine (after you sign in), and once the loop is attached Setup goes. A folder whose problem.yaml is at its root offers to move it into .flux/ (its commands then say {project}/... where they said {home}/...), or to attach it as it is.

    A loop that hides files from its agents which someone else may have hidden cannot be attached: on your machine they would not be hidden from you.

    The loop keeps its name in .flux/: rename your project's folder and it is still the same loop. To rename the loop itself, stop it and change its Name at the top of problem.yaml's form (or choose Rename loop in the Flux view's menu): it is renamed on the server and in your folder, its results with it.

    The loop in the sidebar¶

    The Flux view draws your folder's loop as one graph, top to bottom: Setup, Search, Design, Check, Measure, Choose, the Run strip and the Knowledge chips. AI marks a box an agent or FluxAgent works. Check and Measure are folded, as Live's graph draws them: one box with how many checks (or measurements) it holds and a thin bar for each -- in the box's colour when it passed in its latest run, red when it failed, amber when it passed after failing earlier in the pass, pulsing while it runs, grey while it waits or has not run yet, outlined when the checks stopped before it. Point at a bar for its check and its command; click it for its section of the form, or the box for the group's. The chevron (›) opens the group into its checks in order (or its stages, a stage's cutoff on the arrow after it), each with its own buttons and +; Flux remembers which groups you opened for each loop. A box's corner says how its last work went: a ✓ or ✗, or a turning ring while it works. Its head says where the loop stands in one word, the same as the status bar -- Running, Stopping, Stopped, Ended or Failed (hover it for why) -- its pass (re-measure pass for an R pass, which is not counted among the passes), for how long, its lanes, and the best design so far against your first goal, with Results to open the loop's Results in your browser (every design, compare, star, accept). When designs were measured before a change to how a stage measures them -- you edited its script, say -- a line says how many and what changed, as the web's Overview does, with Re-measure…: it asks, then measures them again (by the running loop before its next pass, else by a run of its own). Under it, a line for each agent that is not ready here, every agent Design takes turns with included -- "codex · not logged in here · Log in… · Test again" (hover it for the boxes that wait) -- Log in… opens a terminal running the agent's own login; it is tested again when the terminal closes. An agent is asked about its login by its own program -- the one your agents: names with bin:, so a build of OpenCode or Codex under another name counts once its own login works -- and the line says what is wrong in a few words: not installed, not logged in, or not answering; hover it for the agent's own words. The loop runs here as you, with your own logins, so Start waits only for a program that is missing or does not run: an agent whose own program says it is not logged in is said with Log in… and Start runs it anyway, and one whose login Flux cannot see is ready.

    problem.yaml has two faces in one tab, as VS Code's Settings have: its text, and a form with every box as a section and their names down the side. Open as form (✎) and Open as text ({ }) in the editor's title bar switch between them, each landing where you were: on the box your cursor is in, or with the cursor at the lines of the section you were in. Click a box in the graph: the form opens at its section. The form writes problem.yaml in place -- your comments and the order of your keys stay -- and says saved to problem.yaml beside each change; what it does not edit it names under its fields, folded, with a link to its line. What you type or pick shows at once and stays while it is written; a change that cannot be written keeps your value and says why, beside the field. Undo, redo and the tab's unsaved dot are the editor's own; when the text has changes you have not saved, the form says so and shows them once you save. The text stays the default when you open problem.yaml; to open it as a form every time, set it in VS Code's Workbench › Editor Associations (problem.yaml → Flux form).

    • The Problem, at the top: the loop's Name (renames it), the Statement, the Artifact file, the Contract and the Environment: variables every process of the loop gets, its steps and its agents (env:), a row each; one Flux will not set says why at its row.
    • Agents: the agents problem.yaml defines for itself (agents:), each a section under it -- its Program (typed, or picked with the folder button; a program of your own its Command) with its state here beside it, and its Model. Under Fine-tune (folded): Interface (how the program is driven -- Default is what it says to --help, the words beside it say which, or why none; Claude Code, Codex, OpenCode an override; A program of my own turns it into a run: command), Arguments, Effort and Thinking (think), Timeout (seconds a turn), List command (models: {run: ...}, the command printing what Model offers; a list of names stays in problem.yaml) and Instructions (instructions:, text added to every brief the agent gets, after its kind's from Admin › Agents). + add an agent adds one; the boxes then name it.

    • Setup › Baseline: what is measured before pass 1 -- Off, The project as it is, A design file (picked with the folder button, relative to the loop's folder), A command and its timeout, or Known values (a metric, its value, its stage) -- and how its last run went: measured, failed and why, or standing unchanged.

    • A check or a stage: its name, its command -- a line of your own, a Preset (Flux's own checks and measurements that read the design's language and whose programs are on this machine, each written with its defaults: no Verilator here, no RTL preset offered; the one the step runs stays listed, and flux task check names a missing program), or one of your folder's VS Code tasks or launch configurations -- and its timeout. A check's Failures: Count (count_re: one capture group, the number of failures its output prints) or Each (fail_re: one match a failure) and the pattern of the one chosen; switching drops the other's. A stage's metrics and its Cutoffs, a row each (a metric, at least, at most or within a share of the best, its value): each must pass, else the design stops there; + cutoff adds one. + in Check or Measure (in the graph or the form) adds one (between two, with the + between them).

    • Each box shows its own buttons when you point at it or reach it with Tab: edit, go to its lines in problem.yaml, and remove (a check or a stage). Enter opens a box's section, Delete removes a check or a stage; both ask first.
    • Search, Design, Choose: who works it -- the rules, FluxAgent or an agent -- and, on the agent's row, its state on this machine with Log in… and Test again; its Model. Under Fine-tune (folded): Effort and Thinking; Timeout (seconds a turn, 1800 unsaid) -- on Design with Continues (times the agent's work goes on past it) and Grace (seconds of one last turn, a quarter of Timeout unsaid; budget's) beside it --; its Session (Setup's Plan, Search, Design, Choose): None (a new one each pass, on Design each design), Keep (kept pass after pass), and on Design Seed with every (passes). Design's Probe: whether its agent may try its file against the gate and the stages before handing it in (hover it for how often).
    • Design listing agents (by: [...]: a trunk's, or a passes' agents in turn) is a table, a row an entry of the list -- t1, t2 in trunk mode --: its Agent, Model (as any agent's: Default, its list, Other…, ⟳), Effort, Thinking, a dot for its state on this machine (hover it for the words), Test (⚗) and ×. The same agent twice is two rows (two trunks). A change writes that entry alone; what else the entry says (timeout_s, session, provider, …) stays as written and is counted on its row (+1, hover it for the keys -- a provider with its name). + agent lists the document's own agents, then the kinds installed here, each with its dot; the one picked is added at the end by its name (never FluxAgent: a list is coding agents'). The Fine-tune under the table is the box's own, every entry's default: Timeout, Continues, Grace, and in passes mode Session.
    • A Critic on Search, Check, Measure and Choose: Off, FluxAgent or an agent (picked as a box's); Search's and Choose's Rounds (1 to 5: how often the box answers its objections).
    • Choose's objectives: each metric higher or lower is better, or Tracked (not ranked) (no direction: shown, never ranked; the graph's Choose says it without an arrow); its goal and unit. A change rewrites that entry alone, its other keys (aggregate, tie, ...) kept.
    • A Model lists the models the agent offers on this machine, as its turns would run it -- for an agent of problem.yaml's own, its models: names or what its List command prints; one with its own Program and no models: lists none of its kind's, only (Claude Code's kind) its own service's when its settings name one (ANTHROPIC_BASE_URL in its environment, the project's .claude/settings.local.json or .claude/settings.json, or its CLAUDE_CONFIG_DIR's). Beside it, ⟳ asks again and a few words say how the listing went: 14 · 12:04 (how many, when), or no list · ANTHROPIC_BASE_URL unset (hover it for the whole: where Flux looked, or what the command said). Default writes none: the agent's definition's model, else your setting for its kind (Account › Agents), else the agent's own choice. A model set on a box wins over the definition's. Other… takes any name -- the agent answers for it at its first turn. A model the list says is one provider's reads GLM-V5.1 · wireless: picking it writes model: and provider: together (the agent's definition says the flag its CLI takes it by, provider_flag: --provider; Your own agents); picking a model listed with none removes provider:; Other… keeps whatever provider: is written; Default clears both.
    • Run: passes or trunk, Tools at once (the designs evaluated at once; unsaid, the agents + 1), passes, repairs, Pipeline (on by default: the next design drafted while the ones before are checked and measured; off writes pipeline: false, each session then waiting for its design's decision). Designs drafted at once is Design's table: an agent listed twice is two sessions. Knowledge: each part on or off, the paths hidden from the agents (hover a field for what it is).
    • In trunk mode the form shows only what a trunk runs: no Plan, no Prototype, no Repairs per design; Run says Designs for the hand-ins, and Pipeline as under Passes.

    In problem.yaml's text, the box your cursor is in is selected in the graph -- in a folded group, the group and that check's bar -- and the editor's breadcrumb and Outline name it (Measure › synth).

    problem.yaml stays yours: edit it by hand and the graph follows. Its mistakes show in Problems as you save. A part with a mistake is drawn in red with what is wrong; click it to go to its line. The head says how many problems there are, and Start waits until they are fixed. A new loop's graph is drawn before it is filled in: the head says what is left ("Add the statement first", "Add a check first", each with Open it to its place in the form), and Start waits for it. With Red Hat's YAML extension installed, problem.yaml also completes its keys and explains them as you type.

    Create¶

    A folder with no loop shows New loop… in Setup: pick where it starts -- the skeleton, your folder's VS Code tasks (pick which become checks and which stages), or describe it to an agent (say what the loop should make and how a design is checked and measured; the agent writes problem.yaml as New loop › Agent does). The server's New loop makes it, then it is brought into .flux/ and attached, and problem.yaml opens as a form at its Problem, the statement to write. Each AI box's agent and its state on this machine are on that box's row of the form and under the graph's head: log in to each before you start. A loop of yours with your folder's name on the server already is offered to bring here instead.

    Start¶

    Start in the Flux view's title bar (or the loop's Start on the web) runs it here; it is greyed while an agent is not ready on this machine, and the view's head says which. It asks how: Until stopped, A number of passes… (a trunk's: designs), Re-measure what is asked first (the R pass alone), Rerun the baseline first (pass 0 measured again, then until stopped), or Re-evaluate…, which opens the loop's Settings on the web to tick which designs. While it runs, the same graph lights up: the box at work, the designs in it (hover Design for the drafts at work), each check's and stage's bar, the checks' runs passed and failed after Check and the stages' after Measure, the best so far on Choose, the pass and its lanes on the Run strip. When it ends a notification says so -- how many passes and the best, or why it failed with Journal. A check or a stage whose command did not run at all (not a design failing it) shows in Problems at its line of problem.yaml until it runs again. Click a design to see its change in VS Code's diff editor; the Flux journal panel lists the steps at work and those that ended, offline too -- a failed one with why (hover it for the whole message); click a row whose words are cut to read them whole, and again to close it. A seed on a machine without Landlock says so beside its time. Until the run's first step -- this machine taking it, the sandbox and tools getting ready -- the head says Starting with the run's latest words, and the journal its log so far; the view's … menu opens the loop's Overview, Results or Live in your browser. Stop and Note are in the view's title bar while it runs, Stop now in its … menu; they work from the web too.

    Chat¶

    The loop's Chat is a Flux tab in VS Code's agent panel, beside Claude Code or Codex. Chat about this loop in the Flux view's title bar opens it (the panel too, when it is closed); Ask Flux about this… among a box's or a step's buttons opens it on a new conversation about that box -- after a failed run, with how it failed. Ask, and the answer comes as on the web: the same agents, the same conversations (Open on the web in the tab's title bar), claude is looking · 23 s · 12 commands with Stop while it works.

    When the agent proposes a change to problem.yaml, its settings or a document under library/, its card has Show diff -- VS Code's own diff of your file and the proposal, with Accept and Reject in its title bar -- and Accept, which writes the change in your folder (your other edits and undo kept), then tells the server: the web shows it Done · applied on your machine. A proposal made on a text your file no longer has (you edited it since) is refused with problem.yaml changed since this was proposed: nothing written -- ask for it again. Other proposals -- a note, an idea, a design note -- are made by the server, as on the web. New chat and Earlier chats are in the tab's title bar.

    A loop living on your machine is answered here on your machine, its only place: the agents your problem.yaml defines (agents:), the agents installed here, and FluxAgent (its model is the server's). The agent works in your folder, as your loop's own agents do: your files as they are now, your .venv, your logins. Who answers lists them, with Default (the first) chosen until you pick one. Beside Think, Effort offers the agent's kind's levels (Default: its own). The answer says where it ran: codeagent · 1 min 12 s · here on fern. A reply asks the same agent. While your machine is offline (VS Code closed, the laptop asleep), or online with the loop's folder not open in any window, a question is refused at once -- wordline lives on fern, which is offline … or … which is online, but the loop's folder is not open in VS Code there; nothing waits to run later. A machine lost while it answers ends that answer, said in the conversation.

    While a loop lives on your machine:

    • the web shows it on your machine, as any loop running on another machine;
    • its files are changed in VS Code: the web's file edits say so. What the web and the agents read follows your folder as you save -- a hand edit, a form, an accepted proposal, a file added or removed -- not only when a run ends (never what the runs write: out/, runs/, workbench/);
    • a run goes on when your machine loses the server, and catches up once it is back;
    • a Start waits for your machine to be online with the loop's folder open there (the Overview says which: open in VS Code now, online, its folder not open in VS Code, not heard for 3 h). Settings › Name & ownership › Take back makes the loop the server's again (a run still on your machine is stopped and what it sends late is set aside).
