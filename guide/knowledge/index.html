    Knowledge, skills, hidden paths¶

    What the model and the agents can look up besides the document, and what they may not read. The fields are in the Document reference.

    Files, notes and papers¶

    flow:
  knowledge:
    library: [spec.md, reference.py, notes/]
    by: claude
    insights: {by: rules}
    • The library: the loop's library/ folder, the files and folders library lists beside the document (a spec, reference code, a method note; a folder counts as each of its files), and each project's library the loop is linked into, read-only, at library/<project>@<group>/. Nothing of it is pasted into a prompt or a brief (D1494): a coding agent's brief carries one line naming flux knowledge -- flux knowledge lists the library one line each (a paper's digest, the workbench's description, else the file's first line), flux knowledge search "<words>" gives the nearest files with their best passages, flux knowledge show NAME reads one -- and a model step looks it up with its knowledge(query) tool and the excerpts retrieved for the task. Hidden paths never appear. by says who summarises the papers (flux, FluxAgent, the default, or an agent); agents read papers in pieces with flux library (below).
    • insights: {by: rules} draws facts from the loop's record, no AI; {by: <agent>} has that agent draw conclusions, each citing its rows; unsaid or {by: off}, none. They are not pasted into a coding agent's brief either (D1505): the loop keeps them beside its record as it makes them, the brief carries one line -- Insights: flux knowledge insights reads what this run has concluded from its record so far (computed by rules); none of it is pasted here. -- and flux knowledge insights prints them (--json for data; with {by: off}, "No insights"). A model step, which runs no command, still has them in its prompt.

    • by: off turns all reading off (the library, its digest and the hint).

    • A project's knowledge (web app, a project's Knowledge tab): entries its people keep, each one insight under one of the project's topics, proven by designs of its loops -- added by hand, or proposed by Flux's collector once a linked loop's top designs have mostly changed (one call to the loop's own model, outside the loop; curators accept or reject each proposal; see the collector). A loop linked into the project reads its accepted entries (never a proposal) with flux knowledge: flux knowledge lists each project's topics with their questions and its entries' headlines, flux knowledge search "<words>" [--topic t] [--project p] gives the matching entries whole (headline, analysis, designs: loop · design · rank), flux knowledge show <id> one; --json for data. The same command lists and searches the loop's library first (above). A coding agent's brief carries one line per project that has an accepted entry -- Project knowledge: silicon@hw-lab — pipelining 2 · timing 1. Query it before choosing a design direction, as your first command, e.g. flux knowledge search "<words>" … --; a plain model step, which runs no command, is not told. The entries are those of the loop's start (a change reaches the next start; the run's log says the version it read). A loop in no project, whose projects have no accepted entry or whose knowledge is {by: off} is told nothing; see Groups › Knowledge.

    A model that keeps getting a design wrong usually lacks a fact, not effort: a method note with the method and the facts (not a design) helps more than more passes.

    Reading the library: flux library¶

    A coding agent reads the library -- the loop's own and every project library it reads -- in pieces, never a whole PDF at once:

    flux library                               # every document, one line each: name · pages or lines · what it is
flux library "QUERY" [--n 5]               # the nearest documents, each with its digest and its 3 best passages
flux library digest  PAPER                 # its digest
flux library outline PAPER                 # its sections, each with its pages and lines
flux library read    PAPER --section 3.2   # one section
flux library read    PAPER --around "QUERY"  # the passages that match best, with a little context
flux library read    PAPER --lines 120-220 # or --pages 3-4 for a PDF; --from 221 goes on from a line
    • Names. A document is named by its place in library/: booth.md, papers/x.pdf, silicon@hw-lab/x.pdf for a project's (library/silicon@hw-lab/x.pdf and a file name or stem one document has are accepted too).
    • Outline. From its headings: Markdown #, LaTeX \section, a PDF's numbered headings (3.2 Method) and the usual unnumbered ones (Abstract, References ...). A document with none is cut by its pages (a PDF) or in chunks of 120 lines.
    • Capped. Every answer prints about 3000 tokens at most; a cut one ends with the exact command that continues (… continue: flux library read x.pdf --from 221). Every passage says where it is: section, page, lines.
    • Search. The library's own BM25 ranking, offline and the same every time. A PDF's text (pdftotext) is cached by its content ($XDG_CACHE_HOME/flux/text), so its line numbers stay the same.
    • Hidden. A path the loop or a project hides from its agents is refused.
    • Inside an agent's turn it reads that turn's loop (in the sandbox too); elsewhere --loop or the current folder. Plain text; --json for data. A coding agent's LIBRARY section names these commands and asks for a first step (flux library "<your method or bottleneck>", then flux library read PAPER --around "QUERY": a digest is a summary, not the method); a loop with no library and no project library is told of no papers. The old flux loop library and flux loop digest answer as they did.

    Skills¶

    A skill is a folder with a SKILL.md: front matter with name and description, then the instructions, and any files they use. Put skills in the loop's skills/ folder and they are read without a word in the document. The model gets an index and a skill tool; every coding agent of the loop finds them in its work folder. The built-in flux-loop-commands skill (how to read the loop's record with flux loop ...) comes with them.

    skills: [skills, ../shared-skills]           # these folders instead of skills/
skills: {"off": [flux-loop-commands]}        # skills/ and the built-in one, this one off
skills: "off"                                # none at all

    --skill DIR on flux task run or flux ask adds a folder for one run.

    Hidden from AI¶

    A gate is only as good as the agent's ignorance of it. An agent that can read the tests can write a design that passes them and nothing else. knowledge.hidden names paths no agent and no prompt may read:

    flow:
  knowledge:
    hidden: [tests/, golden.py, "params/*.json"]

    The loop's own checks, measurements and scripts read these paths as ever, and a check's failure text still reaches the agent. Paths are relative to the loop's folder; sub-loops hide their parent's paths too. An agent's own hidden: option adds paths for that agent alone.

    Each agent's brief names them as off limits, and its permission settings refuse reading and editing them where the agent has per-path rules (Claude Code and OpenCode; Codex has only the brief). Nothing more is taken away: the agent keeps its search tools and its shell, and a command that names a hidden path (pytest tests) is not refused. Hidden is trust plus each agent's own deny rules, no sandbox: a search or a script the agent writes could still read a file, so for secrets, rely on the sandbox. Parameters lists each agent's rules.

    In the web app, hide a path:

    • in Files, from a file's or folder's Actions › Hide from AI;
    • in the configurator's Graph, on the Knowledge box;
    • when adding files to New loop › Agent, with Hide from AI on the file;
    • with flux ask --hidden PATH on the command line.

    Ideas cleanup¶

    The loop keeps an ideas notebook: each hypothesis a model or agent proposed, with the designs that tested it. Over many passes it fills with the same idea in other words. knowledge.ideas has it cleaned up in a pass's Setup, once it has grown. Unsaid, FluxAgent does it at the default thresholds; say who else, other thresholds, or off:

    flow:
  knowledge:
    insights: {by: rules}
    ideas: claude                        # an agent; or {by: flux, open: 30, new: 15}; or off
    • When: before a pass, if the notebook holds at least open open ideas (20 by default) and new of them came since the last cleanup (10). Otherwise the step is a note in Live (Setup · tidy ideas, "14 open ideas, 3 new since the last cleanup") and no model is asked.
    • What: one short call (or one turn of the agent) reads each open idea's title, hypothesis and evidence and answers which ideas are the same. Each group becomes one idea: the others are merged into it, keep their text and evaluations, and their evidence counts under the kept idea. Nothing is deleted. A design that names a merged idea, and a queued one, tests the kept idea. The same call ranks the open ideas, the most promising first, each with a reason: Results › Ideas lists them in that order. The ranking is only for you to read: the loop's own choice of ideas never reads it.
    • Undo: flux loop ideas --unmerge 7 makes idea 7 its own idea again (idea 7, #7 and the idea's id say it too); naming a kept idea undoes every merge into it. flux loop ideas shows each idea's number and its merges. An idea is said by its number as "idea 7", never "#7", which is a design's.

    Unsaid, the cleanup is FluxAgent's ({by: flux, open: 20, new: 10}): each cleanup costs one model call, and only once the notebook reached 20 open ideas. In a loop no step of which asks the model (a sweep, a script or a coding agent writing the designs, with the rules orchestrating) it is off instead, and flux task check says so in a NOTE line; ideas: claude has an agent do it there. ideas: off (or {by: off}) turns it off. Before D1525 an unsaid cleanup was off, so a loop that never said it now cleans up its notebook too. In the web app it is Ideas cleanup in the Graph's Knowledge box, beside the insights: FluxAgent unless you choose otherwise, and choosing Off writes ideas: off.

    Workbench¶

    workbench/ beside the document is the agents' own folder: tools they build and notes they keep, shared by the loop's agents and kept across runs. knowledge.workbench says who sums it up for the next prompt when it changed (off, flux, or an agent); by default, whoever digests the papers. In the web app it is Files › Workbench; the library and its digests are Files › Library.
