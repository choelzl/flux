    Document¶

    Everything a loop's document, problem.yaml, can say, and the contract every command it names must follow: arguments, placeholders, what to print, exit codes.

    Use Configure for why you would choose each setting, flux task check FOLDER to validate a document, and flux task migrate FOLDER --write to upgrade an older one.

    The document at a glance¶

    Only statement is required. A complete document; the numbered marks say where each part is described:

    statement: Count the primes below n, as fast as possible.  # (1)!
contract: >-  # (2)!
  A Python module defining count_primes(n) that returns
  exactly how many primes are below n.
language: python

flow:  # (3)!
  orchestrate:
    search: sweep
    space: {method: [trial_division, sieve, slice_sieve]}
  generate:
    command: "{python} {home}/render.py {artifact} {method}"
  test:  # (4)!
    build: "{python} -m py_compile {artifact}"
    correctness:
      run: "{python} {home}/check.py {artifact}"
      timeout_s: 60
  measure:  # (5)!
    quick:
      run: "{python} {home}/bench.py {artifact} 50000"
      metrics: [time_ms]
      cutoff: {metric: time_ms, below: 20}
    full:
      run: "{python} {home}/bench.py {artifact} 1000000"
      metrics: [time_ms]

objectives:  # (6)!
  - {metric: time_ms, direction: minimize, goal: 20}

budget: {passes: 5, tools_at_once: 1}  # (7)!
params: {n_max: 1000000}  # (8)!
    1. What to make. The only required field.
    2. Rules every design must follow: names, ports, what is forbidden.
    3. Who does each box of the loop: here a search over three methods, and a script that writes each design (flow settings).
    4. The checks, in order; the first that fails refuses the design (check settings).
    5. The measurements, cheapest first. cutoff decides which designs go on to the next stage (measurement settings).
    6. What decides. A goal makes an objective a limit: here at most 20 ms (objectives).
    7. How much to spend (budget).
    8. Your own settings, handed to every command as the {params} file.

    Files and loading¶

    • The folder is the loop. Its name is the loop's id: 1 to 60 letters, digits, _ and -. There is no id key; saying one is refused.
    • The document is problem.yaml (or problem.yml, problem.json). Alternates beside it are NAME.problem.yaml; each keeps its own results.
    • Beside it: your scripts, library/ (papers and notes the model reads), workbench/ (the agents' own tools and notes, kept across runs), skills/ (read unless skills: says otherwise), and out/ (the results, written by Flux).
    • Parsing: a YAML or JSON error reports its line and column; a document that is not a mapping is refused. Unknown keys are refused with a "did you mean" hint.
    • Older documents are never upgraded silently: flux task migrate FOLDER shows what changes and --write saves it.
    • Normal form: equivalent spellings (plan: flux and plan: {by: flux}) load to the same document and share one record -- model, FluxAgent's old name, too.

    Document fields¶

    Field Values / default Purpose
    statement Required non-empty string What to build or optimize
    contract String; empty Interface and rules every design must follow (names, ports, what is forbidden)
    language String; inferred, else text The design's file type (table below)
    flow Map; defaults below Who does each step: search, generation, checks, measurements, and the supporting boxes
    trunk Map; unset Trunk mode, in place of flow with the same contents: Design's by may list agents
    objectives List; empty Limits and ordered preferences (objectives)
    budget Map; defaults below Run length, repairs, concurrency, prototypes (budget)
    params Map; empty Your own settings, handed to any command as the {params} JSON file
    skills off, a folder or list of folders, or {from, off}; skills/ Skills (a folder with SKILL.md) the model and agents can load (skills)
    baseline true, false, or a map; absent A reference measured before pass 1 (baseline)

    language sets the design file's extension, matched without case:

    Language Extension Language Extension
    systemverilog .sv cpp, c++ .cpp
    verilog .v c .c
    vhdl .vhd cuda .cu
    python .py opencl .cl
    text .txt rust .rs
    yaml .yaml markdown .md
    json .json shell, bash .sh
    chisel, scala .scala anything else . + the name, lower case, no spaces

    When language is absent it is inferred only from a check or stage that starts with a built-in tool's full command (in practice the Verilator lint line, which gives systemverilog); otherwise it is text. Say it explicitly.

    Flow settings¶

    flow says who does each box of the loop's drawing. A box takes a word, an agent's name, or {by: <word or agent>, ...settings, ...agent options}:

    flow:
  generate: claude                              # an agent, no options
  select: {by: claude, session: pass}           # an agent with options
  plan: flux                                    # FluxAgent
  feedback: off                                 # a word

    flux is FluxAgent, Flux's own model working a box (its endpoint and model are set in Models and agents). model, its old name, means the same everywhere and is still read; the configurator keeps it in a document that says it and writes flux in a new one. claude, codex and opencode are built in; a server can add agents of its own (named by FLUX_AGENTS). The old form {agent: X} is refused: write {by: X}.

    Box Values (first is the default) Purpose
    flow.orchestrate.by unset (the rules, no AI), given, flux, tools, agent Who decides what to try next
    flow.orchestrate.policy adaptive (default), explore, improve, tune, finetune, variations Sets the search's emphasis
    flow.orchestrate.search unset, sweep, montecarlo, anneal, gradient, genetic, pareto, {gradient: {...}}, module:Class, a list of phases How the points of space are picked (search settings)
    flow.orchestrate.scope {list: ..., brief: ..., check: ..., timeout_s: 120} The scopes of one whole design a pass may work on (scope)
    flow.plan off, flux, agent Write the pass's plan, checked before use
    flow.generate flux, agent, {command: ...}, {catalog: [paths]} Write each design
    flow.test A command, or an ordered map of named checks; never an agent Decide correctness (checks)
    flow.measure An ordered map of named stages; never an agent Put numbers on passing designs (measurements)
    flow.select unset (the objectives choose), agent Make the decision; an agent only breaks ties
    flow.feedback unset (your notes are read), off Take your notes from the loop's Chat into the next prompt
    flow.knowledge A map (knowledge): library, by (who digests, or off), insights, ... What the model and agents can look up

    The configurator's Graph names the boxes by what they do: orchestrate is Search, generate Design, test Check, measure Measure, select Choose.

    • orchestrate: {by, policy, search, space}. by unset is the rules (they pick the work, no AI); given a fixed order ({given: [part_a, part_b]}); flux (FluxAgent picks); tools (FluxAgent with tools: standings, history, decisions, knowledge); or an agent. policy sets the search's emphasis -- adaptive (default), explore, improve, tune, finetune, variations. search is the algorithm that picks the points of space (sweep, montecarlo, anneal, gradient, genetic, pareto, phases) and decides alone. A space with by: flux or an agent and no search: that one proposes the points. A search word under policy:, or a policy name under search:, is refused naming the right key (flux task migrate moves an older document's). The bare word is shorthand: orchestrate: explore is {policy: explore}, orchestrate: sweep {search: sweep}, orchestrate: claude {by: claude}.
    • orchestrate.scope, for a loop of one whole design (no knobs): each pass works on one scope of it. list is a command printing the scopes, one a line, its name first; brief, given {scope}, prints what the design agent is told of it; check, given {scope} and {artifact}, checks the scope on a design that passed the gate (N failing of M, or its exit). Each pass the orchestrator picks its direction and a scope in one decision, seeing which scopes the latest passes took and how their checks ended (the rules: each in turn). While the scope's check fails, the design goes back to the same agent with the failures, until it is clean or the pass's tries_per_pass are spent; every design that passes the gate is kept and measured as usual. For a spec kept in the loop's folder: list: fluxpreset ndf list --spec {home}/spec, brief: fluxpreset ndf clauses {scope} --spec {home}/spec (it names the units that depend on it), and fluxpreset ndf scope {scope} --spec {home}/spec lists the unit and its dependents for a check of your own.
    • generate takes exactly one form. {command: ...} is your script (generator contract); {catalog: [a.py, b.py]} reads the listed files (relative to the folder) in turn; flux (FluxAgent) and agents write the design. session takes only keep here. A generator command has no timeout_s of its own: it uses the largest check timeout.
    • session: keep (with turns: K, 8 unsaid, or turns: forever) on any box an agent works, or a critic: the agent's conversation is kept across passes, one session per design at once, a new one after K turns or when the document, the agent, its model or Flux changes; forever never renews it for its turns. Off unless said; refused on the papers' digester. {by: codex, session: keep, turns: 4}, {by: claude, session: keep, turns: forever}.
    • test and measure are never an agent's. by: on them is refused: they establish facts.
    • select: {by: claude} adds an agent that breaks ties among designs the objectives cannot separate; the objectives' choice stands otherwise.
    • plan is checked before use; a plan that fails the check falls back to the document's order.
    • Thinking. One switch, think: true or false, beside whoever works a box. Where FluxAgent works it -- orchestrate, plan, generate, the critic of test, measure or select, and knowledge with its workbench and ideas -- {by: flux, think: true} lets it reason before it answers (slower, often better; its thinking shows in the task's live view); think: false, it answers straight. Beside an agent -- any box, critic or Knowledge section an agent works, an agent added under a name of its own too -- {by: claude, think: false} runs it at its effort for not thinking, true at its effort for thinking (both the admin's, below); refused for an agent of your own command. An agent's effort (agent options) is the finer level and wins over its think. Unsaid, the server's thinking by default decides: untouched, FluxAgent answers straight and each agent works at its own effort (no flag), as before. The configurator shows Thinking under the agent wherever one is chosen -- a box, a critic, a Knowledge section -- default, on, off, its help line saying the admin's default, with its effort beside it (FluxAgent's levels or the agent's kind's); a box nothing thinks on shows none, nor does an agent with a command of its own. Search with tools says it as {by: tools, think: true}. FluxAgent proposing the points of a search over parameters (Search's AI search) has its own, written beside it: orchestrate: {by: flux, think: true, effort: high, space: {...}}.
    • Effort (FluxAgent). Beside by: flux (or model) wherever think goes, effort: low | medium | high | max sets how hard FluxAgent works -- whether it thinks, how long it works and how long its answer may be -- at once; max also checks its own answer. It comes before the box's think. Unsaid, the admin's choice holds (thinking by default). The configurator shows effort beside FluxAgent's Thinking.
    flow:
  orchestrate: {by: flux, think: true}        # FluxAgent reasons over what to try next
  plan: {by: flux, effort: max}                # works hardest and checks its own plan
  generate: {by: codex, think: false}         # the design agent at its effort for not thinking
  select: {by: claude, effort: high}          # the finer level, as it is
  test: {check: "true", critic: {by: flux, think: true}}          # the critic reasons before it judges
  knowledge: {by: flux, effort: high, ideas: {by: flux, think: false}}   # papers, and the ideas cleanup

    Critics¶

    A critic is a second opinion on one box, said as critic: inside it. Only four boxes take one:

    Box What the critic judges A rejection rounds
    orchestrate The direction picked for a pass, before any design work is spent on it The direction is picked again with the objection yes
    test A design the checks passed The design fails; the objection is its note on the record no
    measure A stage's numbers The result is marked rejected and never chosen; it is not measured again no
    select The pick The decision is made again without it; the critic says whether it rejects the design or the pick yes 
    flow:
  orchestrate: {by: claude, critic: flux}
  test:
    correctness: "{python} {home}/check.py {artifact}"
    critic: claude
  select: {critic: {by: claude, rounds: 2, timeout_s: 600}}

    A critic is flux (FluxAgent), an agent, your own agent ({by: {command: [...]}}), or {by: ..., rounds: N, ...agent options}. rounds (1 to 5, default 1) is how many times the box answers an objection, on orchestrate and select only. A rejected design or pick stays rejected in later passes; a rejected direction is about its own pass. A box without critic: has none.

    An orchestrate critic needs someone who picks: by: flux, by: tools or an agent. With the rules, a search over a space, or under trunk:, nobody picks a direction, so there is nothing to judge and the loader warns. An idea queued by hand is not judged. When the rounds run out the last pick goes ahead, and a critic that fails or runs out of time has no opinion: it never stops the loop.

    A critic runs wherever its box runs: in every pass, in pass 0 (the baseline), in an R pass (Measure again, a hand rejection that asks for a measurement), in Re-Evaluate and in the re-evaluation of an invalidation. Numbers it already judged are not judged again.

    The select critic says in its verdict what it rejects, with rejects:

    • design: the design itself. It is final, like a rejection by hand: it never lapses, and only Restore in Results counts it again.
    • pick (also when the critic says nothing, as every verdict before): only this pick. It lapses once the numbers it judged change (the design measured again, measured on a new stage, or measured under other inputs), and the design can be chosen again.

    The metrics a critic names in wrong are cleared: struck through in Results, their values kept. Results names each rejection's critic and links its critique in Live. The older flow.critique and budget.critique_rounds are refused; flux task migrate turns the first into critics and takes the critics off for a 0 of the second.

    Check settings¶

    flow.test is one command (a check named test) or an ordered map. Checks run in the order written; the first that reports failures refuses the design and the rest do not run.

    test:
  build: "{python} -m py_compile {artifact}"                  # a bare command
  correctness:                                                # or a map
    run: "{python} {home}/check.py {artifact}"
    timeout_s: 60
    Field Default Purpose
    run Required Command string or argument list
    count_re (\d+) failing One capture group holding the number of failures
    fail_re Absent One match per failure; used instead of the default count pattern
    timeout_s 120 Seconds before the check is stopped

    Check names are a letter, then letters, digits, _ and -. A check named build uses no default pattern: any non-zero exit means the design did not build. count_re or fail_re at the level of flow.test (not inside a check) is refused. How a check's output becomes a verdict is in the check contract.

    Measurement settings¶

    flow.measure is an ordered map of stages, cheapest first. A stage is a command or a map:

    Field Default Purpose
    run Required Command string or argument list (as a check's; command: is refused, flux task migrate renames it); {metrics} in it is the stage's metrics, comma-separated (fluxpreset rtl measure {artifact} --metrics {metrics} ...)
    metrics Required unless metrics_re The names printed as name=value -- a number, or a dictionary (below)
    metrics_re Derived from metrics Map of metric name to a regex with one capture group
    needs Inferred for fluxpreset prog count/size; else empty Programs required on PATH; a missing one skips the stage ("NOT RUN")
    timeout_s 600 Seconds before the stage is stopped
    cutoff None A gate before the next stage, or a list of gates that must all pass
    estimate Off Predict first, and skip designs the estimate already rules out

    A stage names its metrics only. A metric printed as a dictionary, name={"a": 1, "b": 2} (or inside a JSON object of metrics), is read as one: each finite value becomes name.a, name.b, a test each, and name is their mean: nothing declares it a dictionary. The dictionary may say its own aggregate with the key _a -- name={"a": 1, "b": 2, "_a": "sum"} -- which is no test; any value but mean, median, min, max or sum refuses the measurement. Missing, null and non-finite values stay unmeasured, never zero. An objective ranks the dictionary by name (its _a, else its mean), by another aggregate it says -- {metric: name, aggregate: sum, direction: minimize, unit: us}: mean, median, min, max or sum; said, it wins over _a -- or by one test, {metric: name.a}. An objective needs no type:; flux task migrate drops an old type: dict (alone, it becomes aggregate: mean, what it ranked by). A dictionary no objective names is an extra measurement: recorded, shown folded under its name in Results and Settings › Preferences (its mean, its entries a click away), never ranked. Metric names are unique per stage; evaluator: stages are gone and refused.

    Cutoffs gate the next stage: {metric: M, at: N} keeps designs at least N, {metric: M, below: N} at most N, {metric: M, within: F} within the fraction F (0 < F <= 1) of this run's best on that stage. Exactly one rule per condition. M is any number the design has at that stage: measured there or carried from an earlier stage (below).

    Estimates: {kind: surrogate|command|model, margin: 0.05}; command only with kind: command (estimate contract). A design whose estimate misses a cutoff or a limit by more than the margin is skipped and never measured.

    Stages measure different things. One stage may time a design and the next measure its area; a stage need not repeat what an earlier one measured. A design's numbers at a stage are, for each metric, the deepest measurement at or before it: a later stage replaces an earlier one's number for the same metric, and a metric only an earlier stage measured is carried forward. Results, flux loop results, show and the report say where a carried number came from ("fmax_mhz=500 (from timing)").

    flow:
  measure:
    timing: {run: "{python} {home}/sta.py {artifact}", metrics: [fmax_mhz], cutoff: {metric: fmax_mhz, at: 250}}
    area:   {run: "{python} {home}/area.py {artifact}", metrics: [area_um2]}
objectives:
  - {metric: fmax_mhz, goal: ">= 300"}   # judged on area, with timing's number carried
  - {metric: area_um2, direction: minimize}

    Every objective must be measured by at least one stage. A limit pinned with stage: must name a stage that has its metric (measured there or before), and a cutoff may name only a metric its stage has; otherwise the run says the question cannot be answered as posed. task check and the run's first step note an objective only the last stage measures: the stages before rank without it.

    Between stages: every design past a stage's cutoffs climbs to the next one (one already measured there, in an earlier pass, is not measured there again), so every design gets every objective's number. Only a cutoff, or an estimate, saves a costly stage: with neither, the cheap stage saves no measurement, and task check says so. A pass carrying many designs (a sweep's) then pays the costly stage for each of them, at most budget.tools_at_once at a time. The decision is made on the deepest stage reached, over the designs measured there, each with every objective by then; a design that never reached the stage where an objective is first measured is not chosen: Results lists it as Rejected, "stopped at" its stage (or Pending while its pass may still climb it).

    Knowledge settings¶

    Field Default Purpose
    library Empty Files and folders (specs, sources, notes, PDFs), relative to the folder, that join library/ as the loop's library; the AI looks it up when it needs it (flux knowledge, flux library)
    by flux Who summarises the library's papers: flux (FluxAgent) or an agent (its options beside); off turns the library off
    insights {by: off} Conclusions drawn from the loop's results: {by: rules} (computed, no AI), {by: <agent>}, or {by: off}; flux knowledge insights prints them
    workbench who digests Who sums up the agents' workbench/ when it changed: off, flux, or an agent ({by: claude, timeout_s: 600} with its options); unsaid, whoever digests the papers
    ideas flux Who cleans up the ideas notebook before a pass, once it grew: flux (FluxAgent, the default; off in a loop that asks the model nothing), off, or an agent; {by: flux, open: 20, new: 10} runs it at 20 open ideas with 10 new since the last cleanup (the defaults). It merges repeated ideas (undoable); see Ideas cleanup
    hidden Empty Files, folders or globs (relative to the folder) the AI agents may not read: tests, checks, a gate's files and their parameters; see Hidden from AI

    by: off may have insights, ideas, workbench and hidden beside it, not library. The old sheet, files, text, digest, lessons and off keys are refused; flux task migrate moves them (a text needs a file). While knowledge is on, the loop's library/ is read. Each project the loop is linked into has its library inside it, read-only, at library/<project>@<group>/ (<project>@_ for a global project), in the loop's project order, with the project's hidden paths hidden under it: a name with @ at the top of library/ is reserved for them.

    Hidden from AI¶

    knowledge.hidden lists paths the loop's agents may not read, so no agent games the gate by reading it: the loop's own checks, stages and scripts read these paths as ever, and a check's failure text still reaches the agent.

    flow:
  knowledge:
    hidden: [tests/, golden.py, "params/*.json"]

    Each path is relative to the loop folder, inside it, and never the document itself. An agent's own hidden: option adds paths for that agent alone. Hidden paths are left out of the library, the knowledge files and the skills. Hiding is no sandbox: for secrets, use the run's sandbox. In the web app, a file or folder is hidden from the Files tab (Actions, Hide from AI), when it is added, or in the configurator's Knowledge box. Chat can read hidden files to answer you; the loop's own agents cannot.

    Skills¶

    A skill is a folder with a SKILL.md (front matter name and description, then the instructions). The loop's skills/ folder is used without a word in the document, by the model and every coding agent of the loop, together with the built-in flux-loop-commands (how the loop's results are read with flux loop ...). skills: chooses other folders or turns them off:

    skills: off                                  # none, not the built-in one either
skills: [skills, ../shared-skills]           # these folders instead of skills/
skills: {off: [flux-loop-commands, rtl-style]}   # skills/ and the built-in one, these two off
skills: {from: [../shared-skills], off: [old-style]}

    Objective settings¶

    Each entry is a metric name or a map:

    Field Default Purpose
    metric Required A metric a stage reports (name or name.test for a dictionary metric)
    direction maximize, or the stage metric's minimize or maximize
    goal None A limit: at most N when minimizing, at least N when maximizing; also ">= 1000", "< 80"
    stage The deepest stage for a goal Where the goal is judged (a stage that has the metric: measured there or carried from an earlier one)
    unit Known for common metrics Display unit
    type dict when aggregate is said, else number dict: the metric is a dictionary of tests, ranked by aggregate; unsaid, a metric printed as a dictionary is one all the same (its mean)
    aggregate mean How a dictionary's tests make its number: mean, median, min, max, sum
    tie 0 Relative band within which two designs tie and the next objective decides
    margin 0 Extra headroom required when a goal is judged on a shallower stage
    balance false Decide by the best trade-off (the knee) of the goal-less objectives
    keep None A relative limit: keep this fraction (0..1] of the best gain over above
    above 0 The reference for keep

    How the decision is made: a design that meets every limit beats one that misses any. Among those that meet them, the goal-less objectives decide in the order written (within tie, the next one decides). If none meets every limit, the one missing fewest, then by the smallest shortfall, is reported as the closest, not as a decision. An unmeasured limit counts as missed. With balance, the best trade-off of the goal-less objectives decides. An exact tie goes to the next objective in the order written, limits included (of two designs alike on area, the faster), then to the design made first. goal cannot be combined with keep or balance. A dictionary metric needs no type:: an objective naming it ranks its mean unless its aggregate (or else the dictionary's own _a) says another, or names one of its tests (d.test).

    Budget¶

    Run length, repairs, and concurrency¶

    Field Default Purpose
    passes 0 A limit on the passes of flux task run without --passes; 0 runs until stopped. Not in the configurator, and a start from the web never reads it: the Start dialog sets each start's passes, and "until I stop it" means just that
    tries_per_pass 3 What one pass may work through. A loop builds one design a pass, so this caps its tries that give none and a critic's send-backs; for a search, its rounds: a pass carries one proposal, and a round that gives no design takes the next. Leave it out unless a search needs more; only a search's Tries row sets it in the configurator
    repairs_per_design 3 Repairs of one design before it is given up
    designs_at_once 1 Designs at once, wherever: passes at once, trunk branches (twice that may wait), a search pass's designs, a Re-Evaluate pass's designs. A server limit also applies. Passes of a search run one at a time: the designs at once are inside each pass (what a pass carries)
    tools_at_once auto Tool runs at once across the whole loop: checks, measurements and an agent's flux probe. Unsaid: half the cores, at most 4, or designs_at_once when more. Use 1 for anything timed, or for a tool that breaks when two of its runs share the machine. It never holds designs at once, only their tool runs. A server limit also applies
    agent_continues 3 Times a design agent's work is continued past its time limit before its design is handed in as it stands
    agent_grace_s a quarter of the agent's time limit, 300–600 s A final short turn to get the design past the gate; 0 turns it off

    prototype as a budget key is refused: it is generate's (below). These values are not type-checked; check them with care.

    Prototypes¶

    A prototype is the algorithm in Python (or SystemC) checked against the golden model before the target design is written. It applies to problems with a golden model, and is said on the box that writes the designs: generate: {prototype: false}, generate: {by: claude, prototype: systemc} (true, the default, false, python or systemc). Beside a command or a catalog no prototype is written: it is a warning there. Setting it does not create a golden model. Its limits are budget knobs:

    Field Default Purpose
    prototype_attempts 30 First model attempts
    prototype_patience 8 Attempts earned per new best
    prototype_attempts_max 90 Most model attempts
    prototype_agent_attempts 8 First coding-agent attempts
    prototype_agent_patience 2 Coding-agent attempts earned per new best
    prototype_agent_attempts_max 20 Most coding-agent attempts
    prototype_table_max 64 Largest module-level table allowed
    prototype_cost_max 0 (effective 2000) Cost ceiling before spelling; negative turns it off
    prototype_shrink_attempts 8 Attempts to make a verified prototype cheaper
    prototype_unmeasured_stop 4 Unmeasurable attempts in a row before the pass ends

    Direct-model tools and context¶

    For FluxAgent turns, not a coding agent's.

    Field Default Purpose
    tools true Tools inside model turns
    compute_timeout_s 10.0 Seconds for the model's compute tool
    tool_hops 6 Tool rounds before the model must answer
    tool_result_chars 40000 Most characters of a tool's output given to the model

    explore, hop_share, knowledge_share, compact and compact_share are tuning knobs the loop manages; leave them at their defaults.

    Baseline / pass 0¶

    baseline runs the checks and the real measurements on a reference before pass 1, so results can be read relative to it. It is off by default; pass 0 uses no AI and repairs nothing, and does not count toward passes.

    baseline: true                                   # the project as it is: your scripts as written
# baseline: {file: baseline.py}                  # an unchanged design file
# baseline: {command: "{python} {home}/baseline.py {artifact}", timeout_s: 600}
# baseline: {metrics: [{metric: area_um2, value: 120}, {metric: fmax_mhz, value: 1000, stage: place}]}
# add only: true to stop after pass 0
    Form What pass 0 measures
    true Your scripts as written; {artifact} is an empty file, so use {home}/... paths
    {file: F} F (relative to the folder) copied to {artifact}; the original is untouched
    {command: C, timeout_s: 600} Whatever C writes to {artifact} (contract); if it writes nothing, the project as it is
    {metrics: [...]} Nothing runs: the values are recorded as the reference
    • metrics entries are {metric, value, stage}: a finite number; stage defaults to the deepest; the metric must be one that stage reports; each stage/metric pair once. Provided values supply no design and are never the decision.
    • only: true ends the run after pass 0 (a tool check without optimization).
    • Reuse: a successful baseline on record stands while the document's baseline: section is unchanged -- whatever else changes (the folder's files, the tools, Flux). To measure it again, the loop's Settings › Maintenance › Re-Evaluate with Rerun baseline ticked (or flux task run ... --rerun-baseline) makes the next start, and only it, run pass 0. A failed one is tried again at the next start. Baselines skip estimates and cutoffs.
    • Baselines are references: drawn as gray lines, the base of relative values, never the decision or a search start.
