    Document¶

    Everything a loop's document, problem.yaml, can say, and the contract every command it names must follow: arguments, placeholders, what to print, exit codes. It is written from the code and checked against it.

    Use Configure for why you would choose each setting, flux task check FOLDER to validate a document, and flux task migrate FOLDER --write to upgrade an older one.

    The document at a glance¶

    Only statement is required. A complete document; the numbered marks say where each part is described:

    statement: Count the primes below n, as fast as possible.  # (1)!
contract: >-  # (2)!
  A Python module defining count_primes(n) that returns
  exactly how many primes are below n.
language: python

flow:  # (3)!
  orchestrate:
    search: sweep
    space: {method: [trial_division, sieve, slice_sieve]}
  generate:
    command: "{python} {home}/render.py {artifact} {method}"
  test:  # (4)!
    build: "{python} -m py_compile {artifact}"
    correctness:
      run: "{python} {home}/check.py {artifact}"
      timeout_s: 60
  measure:  # (5)!
    quick:
      run: "{python} {home}/bench.py {artifact} 50000"
      metrics: [time_ms]
      cutoff: {metric: time_ms, below: 20}
    full:
      run: "{python} {home}/bench.py {artifact} 1000000"
      metrics: [time_ms]
  select: {finalists: 2}

objectives:  # (6)!
  - {metric: time_ms, direction: minimize, goal: 20}

budget: {passes: 5, workers: 1}  # (7)!
params: {n_max: 1000000}  # (8)!
    1. What to make. The only required field.
    2. Rules every design must follow: names, ports, what is forbidden.
    3. Who does each box of the loop: here a search over three methods, and a script that writes each design (flow settings).
    4. The checks, in order; the first that fails refuses the design (check settings).
    5. The measurements, cheapest first. cutoff decides which designs go on to the next stage; select.finalists how many climb (measurement settings).
    6. What decides. A goal makes an objective a limit: here at most 20 ms (objectives).
    7. How much to spend (budget).
    8. Your own settings, handed to every command as the {params} file.

    Files and loading¶

    • The folder is the loop. Its name is the loop's id: 1 to 60 letters, digits, _ and -. There is no id key; saying one is refused.
    • The document is problem.yaml (or problem.yml, problem.json). Alternates beside it are NAME.problem.yaml; each has its own record, out/<id>.NAME.db.
    • Beside it: your scripts, library/ (papers and notes the model reads), workbench/ (the agents' own tools and notes, kept across runs), skills/ (read unless skills: says otherwise), and out/ (the record, the cache and the decided design, written by Flux).
    • Parsing: a YAML or JSON error reports its line and column; a document that is not a mapping is refused. Unknown keys are refused with a "did you mean" hint.
    • Older documents are never upgraded silently: flux task migrate FOLDER shows what changes and --write saves it.
    • Normal form: equivalent spellings (plan: flux and plan: {by: flux}) load to the same document and share one record -- model, FluxAgent's old name, too.

    Document fields¶

    Field Values / default Purpose
    statement Required non-empty string What to build or optimize
    contract String; empty Interface and rules every design must follow (names, ports, what is forbidden)
    language String; inferred, else text The design's file type (table below)
    flow Map; defaults below Who does each step: search, generation, checks, measurements, and the supporting boxes
    objectives List; empty Limits and ordered preferences (objectives)
    budget Map; defaults below Run length, repairs, concurrency, prototypes (budget)
    params Map; empty Your own settings, handed to any command as the {params} JSON file
    parts List of names, map of descriptions, or decompose Pieces of one artifact (parts)
    subtasks List of folders or inline documents, or decompose Child problems, each its own loop (sub-loops)
    max_subtasks Integer; 4 Most children when subtasks: decompose
    skills off, a folder or list of folders, or {from, off}; skills/ Skills (a folder with SKILL.md) the model and agents can load (skills)
    baseline true, false, or a map; absent A reference measured before pass 1 (baseline)

    language sets the design file's extension, matched without case:

    Language Extension Language Extension
    systemverilog .sv cpp, c++ .cpp
    verilog .v c .c
    vhdl .vhd cuda .cu
    python .py opencl .cl
    text .txt rust .rs
    yaml .yaml markdown .md
    json .json shell, bash .sh
    chisel, scala .scala anything else . + the name, lower case, no spaces

    When language is absent it is inferred only from a check or stage that starts with a built-in tool's full command (in practice the Verilator lint line, which gives systemverilog); otherwise it is text. Say it explicitly.

    Flow settings¶

    flow says who does each box of the loop's drawing. A box takes a word, an agent's name, or {by: <word or agent>, ...settings, ...agent options}:

    flow:
  generate: claude                              # an agent, no options
  select: {by: claude, session: pass}           # an agent with options
  plan: flux                                    # FluxAgent
  calibrate: off                                # a word

    flux is FluxAgent, Flux's own model working a box (its endpoint and model are set in Models and agents). model, its old name, means the same everywhere and is still read; the configurator keeps it in a document that says it and writes flux in a new one. claude, codex and opencode are built in; a server can add agents of its own (named by FLUX_AGENTS). The old form {agent: X} is refused: write {by: X}.

    Box Values (first is the default) Purpose
    flow.orchestrate.by unset (the rules, no AI), given, flux, tools, agent Who decides what to try next
    flow.orchestrate.policy an intent: adaptive (default), explore, improve, tune, finetune, variations The emphasis that guides who decides, FluxAgent or an agent proposing points, or a search's prompts
    flow.orchestrate.search unset, sweep, montecarlo, anneal, gradient, genetic, pareto, {gradient: {...}}, module:Class, a list of phases How the points of space are picked (search settings)
    flow.orchestrate.scope {list: ..., brief: ..., check: ..., timeout_s: 120} The scopes of one whole design a pass may work on (scope)
    flow.plan off, flux, agent Write the pass's plan, checked before use
    flow.generate flux, agent, {command: ...}, {catalog: [paths]} Write each design
    flow.test A command, or an ordered map of named checks; never an agent Decide correctness (checks)
    flow.measure An ordered map of named stages; never an agent Put numbers on passing designs (measurements)
    flow.select unset (the objectives choose), agent, {finalists: N} Choose the decision; an agent only breaks ties
    flow.calibrate on, off Compare a costly stage's numbers with the cheap stage's
    flow.feedback unset (your notes are read), off Take your notes from the loop's Chat into the next prompt
    flow.knowledge A map (knowledge): library, by (who digests, or off), insights, ... What the model and agents can look up

    The configurator's Graph names the boxes by what they do: orchestrate is Search, generate Design, test Check, measure Measure, select Choose.

    • orchestrate: {by, policy, search, space} (D1499, D1512). by unset is the rules (they pick the work, no AI); given a fixed order ({given: [part_a, part_b]}); flux (FluxAgent picks); tools (FluxAgent with tools: standings, history, decisions, knowledge); or an agent. policy is the intent that guides it -- adaptive (default), explore, improve, tune, finetune, variations; it guides, it never forbids. search is the algorithm that picks the points of space (sweep, montecarlo, anneal, gradient, genetic, pareto, phases) and decides alone; policy beside it guides its prompts (unsaid, the search's own guidance). A space with by: flux or an agent and no search: that one proposes the points, guided by policy. A search word under policy:, or an intent under search:, is refused naming the right key (flux task migrate moves an older document's). The bare word is shorthand: orchestrate: explore is {policy: explore}, orchestrate: sweep {search: sweep}, orchestrate: claude {by: claude}.
    • orchestrate.scope, for a loop of one whole design (no parts, sub-loops or knobs): each pass works on one scope of it. list is a command printing the scopes, one a line, its name first; brief, given {scope}, prints what the design agent is told of it; check, given {scope} and {artifact}, checks the scope on a design that passed the gate (N failing of M, or its exit). Each pass the orchestrator picks its direction and a scope in one decision, seeing which scopes the latest passes took and how their checks ended (the rules: each in turn). While the scope's check fails, the design goes back to the same agent with the failures, until it is clean or the pass's steps are spent; every design that passes the gate is kept and measured as usual. For a spec kept in the loop's folder: list: fluxpreset ndf list --spec {home}/spec, brief: fluxpreset ndf clauses {scope} --spec {home}/spec (it names the units that depend on it), and fluxpreset ndf scope {scope} --spec {home}/spec lists the unit and its dependents for a check of your own.
    • generate takes exactly one form. {command: ...} is your script (generator contract); {catalog: [a.py, b.py]} reads the listed files (relative to the folder) in turn; flux (FluxAgent) and agents write the design from the brief. A generate agent keeps one session per part through its repairs; session is refused here. A generator command has no timeout_s of its own: it uses the largest check timeout.
    • test and measure are never an agent's. by: on them is refused: they establish facts.
    • select: {finalists: N} is how many designs climb to each costlier stage (default 3). {by: claude, finalists: 2} adds an agent that breaks ties among designs the objectives cannot separate; the objectives' choice stands otherwise.
    • plan is checked before use; a plan that fails the check falls back to the document's order.
    • Thinking. One switch, think: true or false, beside whoever works a box. Where FluxAgent works it -- orchestrate, plan, generate -- {by: flux, think: true} lets it reason before it answers (slower, often better; its thinking shows in the task's live view); think: false, it answers straight. A thinking model's answer that comes back empty is asked again with thinking off. Beside an agent -- any box, critic or Knowledge section an agent works, an agent added under a name of its own too -- {by: claude, think: false} runs it at its effort for not thinking, true at its effort for thinking (both the admin's, below); refused for an agent of your own command. An agent's effort (agent options) is the finer level and wins over its think. Unsaid, the server's thinking by default decides: untouched, FluxAgent answers straight and each agent works at its own effort (no flag), as before. The configurator shows Thinking under the agent wherever one is chosen -- a box, a critic, a Knowledge section -- default, on, off, its help line saying the admin's default, with its effort beside it (FluxAgent's levels or the agent's kind's); a box nothing thinks on shows none. Where FluxAgent works a critic or a Knowledge section, the document cannot say its thinking; Search with tools says it as {by: tools, think: true}, which the configurator does not edit. There the two show read-only, the admin's, and the help line says so. FluxAgent proposing the points of a search over settings (Search's AI search) has its own, written beside it: orchestrate: {by: flux, think: true, effort: high, space: {...}}.
    • Effort (FluxAgent). Beside by: flux (or model) on orchestrate, plan or generate, effort: low | medium | high | max sets FluxAgent's thinking, its tool rounds and its output at once (the table): low 6 rounds, 3000 tokens, no thinking; medium 20 and 6000; high 30 and 10000, thinking; max 50 and 16000, thinking, and a self-check of its answer. It comes before the box's think. Unsaid, the box runs as before (the loop's tool_hops, the run's output cap) unless the admin picked an effort for FluxAgent (thinking by default). The configurator shows effort beside FluxAgent's Thinking.
    flow:
  orchestrate: {by: flux, think: true}        # FluxAgent reasons over what to try next
  plan: {by: flux, effort: max}                # thinks, 50 tool rounds, checks its own plan
  generate: {by: codex, think: false}         # the design agent at its effort for not thinking
  select: {by: claude, effort: high}          # the finer level, as it is

    Critics¶

    A critic is a second opinion on one box, said as critic: inside it. Only four boxes take one:

    Box What the critic judges A rejection rounds
    orchestrate The split into parts, or the pass's direction The work is divided again with the objection yes
    test A design the checks passed The design fails; the objection is its note on the record no
    measure A stage's numbers The result is marked rejected and never chosen; it is not measured again no
    select The pick The decision is made again without it yes 
    flow:
  orchestrate: {by: claude, critic: flux}
  test:
    correctness: "{python} {home}/check.py {artifact}"
    critic: claude
  select: {finalists: 2, critic: {by: claude, rounds: 2, timeout_s: 600}}

    A critic is flux (FluxAgent), an agent, your own agent ({by: {command: [...]}}), or {by: ..., rounds: N, ...agent options}. rounds (1 to 5, default 1) is how many times the box answers an objection, on orchestrate and select only. A rejection holds for later passes. A box without critic: has none. The older flow.critique and budget.critique_rounds are refused; flux task migrate turns the first into critics and takes the critics off for a 0 of the second.

    Check settings¶

    flow.test is one command (a check named test) or an ordered map. Checks run in the order written; the first that reports failures refuses the design and the rest do not run.

    test:
  build: "{python} -m py_compile {artifact}"                  # a bare command
  correctness:                                                # or a map
    run: "{python} {home}/check.py {artifact}"
    timeout_s: 60
    Field Default Purpose
    run Required Command string or argument list
    count_re (\d+) failing One capture group holding the number of failures
    fail_re Absent One match per failure; used instead of the default count pattern
    timeout_s 120 Seconds before the check is stopped

    Check names are a letter, then letters, digits, _ and -. A check named build uses no default pattern: any non-zero exit means the design did not build. count_re or fail_re at the level of flow.test (not inside a check) is refused. How a check's output becomes a verdict is in the check contract.

    Measurement settings¶

    flow.measure is an ordered map of stages, cheapest first. A stage is a command or a map:

    Field Default Purpose
    run Required Command string or argument list (as a check's; command: is refused, flux task migrate renames it)
    metrics Required unless metrics_re The names printed as name=value -- a number, or a dictionary (below)
    metrics_re Derived from metrics Map of metric name to a regex with one capture group
    needs Inferred for fluxpreset prog count/size; else empty Programs required on PATH; a missing one skips the stage ("NOT RUN")
    timeout_s 600 Seconds before the stage is stopped
    cutoff None A gate before the next stage, or a list of gates that must all pass
    estimate Off Predict first, and skip designs the estimate already rules out

    A stage names its metrics only. A metric printed as a dictionary, name={"a": 1, "b": 2} (or inside a JSON object of metrics), is read as one: each finite value becomes name.a, name.b, a test each. Missing, null and non-finite values stay unmeasured, never zero. To rank by the dictionary as a whole, its objective says so: {metric: name, type: dict, aggregate: sum, direction: minimize, unit: us} -- name then holds the aggregate of its tests: mean (default), median, min, max or sum; an objective may instead rank one test, {metric: name.a}. Metric names are unique per stage; evaluator: stages are gone and refused.

    Cutoffs gate the next stage: {metric: M, at: N} keeps designs at least N, {metric: M, below: N} at most N, {metric: M, within: F} within the fraction F (0 < F <= 1) of this run's best on that stage. Exactly one rule per condition. M is any number the design has at that stage: measured there or carried from an earlier stage (below).

    Estimates: {kind: surrogate|command|model, margin: 0.05}; command only with kind: command (estimate contract). The surrogate needs three measured designs first. A design whose estimate misses a cutoff or a limit by more than the margin is skipped and never measured; designs that run keep their estimate in the record.

    Stages measure different things. One stage may time a design and the next measure its area; a stage need not repeat what an earlier one measured. A design's numbers at a stage are, for each metric, the deepest measurement at or before it: a later stage replaces an earlier one's number for the same metric, and a metric only an earlier stage measured is carried forward (the record keeps each stage's own row; the carrying is done when it is read). Results, flux loop results, show and the report say where a carried number came from ("fmax_mhz=500 (from timing)").

    flow:
  measure:
    timing: {run: "{python} {home}/sta.py {artifact}", metrics: [fmax_mhz], cutoff: {metric: fmax_mhz, at: 250}}
    area:   {run: "{python} {home}/area.py {artifact}", metrics: [area_um2]}
objectives:
  - {metric: fmax_mhz, goal: ">= 300"}   # judged on area, with timing's number carried
  - {metric: area_um2, direction: minimize}

    Every objective must be measured by at least one stage. A limit pinned with stage: must name a stage that has its metric (measured there or before), and a cutoff may name only a metric its stage has; otherwise the run says the question cannot be answered as posed. task check and the run's first step note an objective only the last stage measures: the stages before rank without it.

    Between stages: designs that pass a stage's cutoffs join its frontier; the select.finalists best (spread along the frontier with several objectives) climb to the next stage. A stage ranks on the objectives it has numbers for; one not measured yet is left out there, and the log says so ("timing: ranked on fmax_mhz; area_um2 (first on area) not measured yet"). A stage that has no objective at all lets every design through its cutoffs. The decision is made on the deepest stage reached, over the designs measured there, each with every objective by then; a design that never reached the stage where an objective is first measured is not chosen: Results lists it as pending. --screen-only stops after the first stage.

    Knowledge settings¶

    Field Default Purpose
    library Empty Files and folders (specs, sources, notes, PDFs), relative to the folder, that join library/ as the loop's library: read on demand (flux knowledge, a model's knowledge(query)), never pasted into a prompt (D1494)
    by flux Who summarises the library's papers: flux (FluxAgent) or an agent (its options beside); off turns the library, its digest and its hint off
    insights {by: off} Conclusions drawn from the record: {by: rules} (computed, no AI), {by: <agent>}, or {by: off}; an agent reads them with flux knowledge insights, never pasted into its brief (D1505)
    workbench who digests Who sums up the agents' workbench/ when it changed: off, flux, or an agent ({by: claude, timeout_s: 600} with its options); unsaid, whoever digests the papers
    ideas flux Who cleans up the ideas notebook before a pass, once it grew: flux (FluxAgent, the default; off in a loop that asks the model nothing), off, or an agent; {by: flux, open: 20, new: 10} runs it at 20 open ideas with 10 new since the last cleanup (the defaults). It merges repeated ideas (undoable) and ranks the rest; see Ideas cleanup
    hidden Empty Files, folders or globs (relative to the folder) the AI agents may not read: tests, checks, a gate's files and their parameters; see Hidden from AI

    by: off may have insights, ideas, workbench and hidden beside it, not library. The old sheet, files, text, digest, lessons and off keys are refused; flux task migrate moves them (a text needs a file). While knowledge is on, the loop's library/ is read (there is no server-wide library: FLUX_LIBRARY is not read); PDFs go through pdftotext. Each project the loop is linked into has its library inside it, read-only, at library/<project>@<group>/ (<project>@_ for a global project), in the loop's project order, with the project's hidden paths hidden under it: a name with @ at the top of library/ is reserved for them, so the loop's own files and a project's never clash. A project's paper is digested by the loop for its own problem and cited by its place (library/nlu@hw/x.pdf); an exact copy in a later folder is read once.

    Hidden from AI¶

    knowledge.hidden keeps an agent from gaming the gate by reading it: the loop's own tools (its checks, stages, scripts and probes) read these paths as ever, and a check's failure text still reaches the agent; no agent and no prompt reads them.

    flow:
  knowledge:
    hidden: [tests/, golden.py, "params/*.json"]

    Each path is relative to the loop folder, inside it, and never the document itself. Sub-loops hide their parent's paths too, beside their own. An agent's own hidden: option adds paths for that agent alone. Hidden paths are left out of the library, the knowledge files, the skills, the workbench's index and flux loop library; flux library, flux loop diff, gate and measure refuse them. Every agent turn's brief names them as off limits, and the agent's own permission settings refuse them:

    • Claude Code: --settings with permissions.deny: Read(...) and Edit(...) on each path (absolute, //..., and relative to the turn's folder when inside it).
    • OpenCode: permission.read and permission.edit deny patterns in its config (OPENCODE_CONFIG_CONTENT).
    • Codex: no per-path rule a user can set; only the brief says so.

    No tool is taken away and no shell command is refused for naming a path: the agent keeps its search tools (Claude Code's Grep and Glob, OpenCode's grep and glob) and may run pytest tests. OpenCode's grep and glob follow no read rule, and Claude Code's follow it only best-effort, so there the brief is what asks the agent to leave the paths alone.

    This stops an agent from targeting a path; it is no sandbox. A script the agent writes could still open the file, so for secrets use the run's sandbox. In the web app, a file or folder is hidden from the Files tab (Actions, Hide from AI), when it is added, or in the configurator's Knowledge box.

    Skills¶

    A skill is a folder with a SKILL.md (front matter name and description, then the instructions). The loop's skills/ folder is read without a word in the document. The model gets an index of them and a skill tool; every coding agent of the loop (the design agent, a box's, a critic, the insights' and the digests') finds them in its work directory (.claude/skills, .opencode/skills, .agents/skills), together with the built-in flux-loop-commands (how the loop's record is read with flux loop ...).

    skills: off                                  # none, not the built-in one either
skills: [skills, ../shared-skills]           # these folders instead of skills/
skills: {off: [flux-loop-commands, rtl-style]}   # skills/ and the built-in one, these two off
skills: {from: [../shared-skills], off: [old-style]}

    Objective settings¶

    Each entry is a metric name or a map:

    Field Default Purpose
    metric Required A metric a stage reports (name or name.test for a dictionary metric)
    direction maximize, or the stage metric's minimize or maximize
    goal None A limit: at most N when minimizing, at least N when maximizing; also ">= 1000", "< 80"
    stage The deepest stage for a goal Where the goal is judged (a stage that has the metric: measured there or carried from an earlier one)
    unit Known for common metrics Display unit
    type number dict: the metric is a dictionary of tests, ranked by aggregate
    aggregate mean with type: dict How a dictionary's tests make its number: mean, median, min, max, sum
    tie 0 Relative band within which two designs tie and the next objective decides
    margin 0 Extra headroom required when a goal is judged on a shallower stage
    balance false Decide by the best trade-off (the knee) of the goal-less objectives
    keep None A relative limit: keep this fraction (0..1] of the best gain over above
    above 0 The reference for keep

    How the decision is made: a design that meets every limit beats one that misses any. Among those that meet them, the goal-less objectives decide in the order written (within tie, the next one decides). If none meets every limit, the one missing fewest, then by the smallest shortfall, is reported as the closest, not as a decision. An unmeasured limit counts as missed. With balance, the knee is taken among the designs measured on every balance metric that no other design beats on every objective. An exact tie goes to the next objective in the order written, limits included (of two designs alike on area, the faster), then to the design made first (its first measurement), never to the order the record lists them in: the decision is always on the front. goal cannot be combined with keep or balance; a dictionary metric no objective says type: dict for has no number of its own: an objective names one of its tests (d.test).

    Budget¶

    Run length, repairs, and concurrency¶

    Field Default Purpose
    passes 0 Passes to run; 0 runs until stopped
    steps 24 Work items in one pass
    budget_s None Wall-clock seconds for one pass, checked before each step
    repair_attempts 12 Repairs of one draft before it is given up
    batch 1 Search designs one pass carries
    workers 0 Tool runs at once; 0 = half the cores, at most 4. Use 1 for timings
    parallel 1 Passes at once (a server limit also applies)
    parallel_parts 1 Parts drafted at once
    tools_at_once 0 Checks and measurements at once across the whole loop -- passes and parts at once, and an agent's flux probe -- for a tool that breaks when two of its runs share the machine; 0 = no limit
    screen_only false Stop after the first stage
    max_depth 3 Deepest nesting of sub-loops
    regenerate [] Parts to draft again instead of reusing admitted ones
    exploration_quota 0.0 Least share (0..1) of search choices kept for exploring
    explore_every 4 Every Nth draft starts fresh rather than from the best
    explore_after 2 Stalled passes before exploring
    part_patience 3 A loop with parts works on ONE part a pass, picked by its standing; a part whose last N passes gained nothing rests until every part rests (then the whole is at rest and a pass explores). explore_every passes give the least recently visited part its turn
    agent_continues 3 Times a design agent's session is continued past its time limit (the last one is told so). Then the design as it stands is handed in if the gate passes it; else a final short turn (agent_grace_s) whose only job is the gate; else the last file a flux probe gate passed in this design's turns. Only with none of these does the pass give up, without a design, its notes on the record
    agent_grace_s a quarter of the agent's time limit, 300–600 s The final turn after the continues: told the gate's failure on its file, one gate probe, no stages, no experiments; the last file the gate passed is offered to copy back. Its file is handed in when the gate passes it. 0 turns the final turn off (the passing file, if any, is still handed in)
    explore 0 Managed by the loop each pass; a value here has no effect
    cooldown_after 3 Build failures in a row before a part yields
    patching true Repair with edits rather than full rewrites
    patch_context_lines 40 Lines around a fault shown in a repair prompt
    revert_after 3 Failed compile repairs before going back to the last good design
    regress_after 2 Worsening edits in a row tolerated at first
    max_tolerance 4 Most that tolerance grows

    finalists is set with flow.select.finalists and calibration with flow.calibrate; as budget keys they are refused, and so is prototype: it is generate's (below). Only exploration_quota is type-checked; check the others with care.

    Prototypes¶

    A prototype is the algorithm in Python (or SystemC) checked against the golden model before the target design is written. It applies to problems with a golden model, and is said on the box that writes the designs: generate: {prototype: false}, generate: {by: claude, prototype: systemc} (true, the default, false, python or systemc). Beside a command or a catalog no prototype is written: it is a warning there. Setting it does not create a golden model. Its limits are budget knobs:

    Field Default Purpose
    prototype_attempts 30 First model attempts
    prototype_patience 8 Attempts earned per new best
    prototype_attempts_max 90 Most model attempts
    prototype_agent_attempts 8 First coding-agent attempts
    prototype_agent_patience 2 Coding-agent attempts earned per new best
    prototype_agent_attempts_max 20 Most coding-agent attempts
    prototype_table_max 64 Largest module-level table allowed
    prototype_cost_max 0 (effective 2000) Cost ceiling before spelling; negative turns it off
    prototype_shrink_attempts 8 Attempts to make a verified prototype cheaper
    prototype_unmeasured_stop 4 Unmeasurable attempts in a row before the pass ends

    Baseline / pass 0¶

    baseline runs the checks and the real measurements on a reference before pass 1, so results can be read relative to it. It is off by default; pass 0 calls no model or agent, writes no golden model and repairs nothing, and does not count toward passes.

    baseline: true                                   # the project as it is: your scripts as written
# baseline: {file: baseline.py}                  # an unchanged design file
# baseline: {command: "{python} {home}/baseline.py {artifact}", timeout_s: 600}
# baseline: {metrics: [{metric: area_um2, value: 120}, {metric: fmax_mhz, value: 1000, stage: place}]}
# add only: true to stop after pass 0
    Form What pass 0 measures
    true Your scripts as written; {artifact} is an empty file, so use {home}/... paths
    {file: F} F (relative to the folder) copied to {artifact}; the original is untouched
    {command: C, timeout_s: 600} Whatever C writes to {artifact} (contract); if it writes nothing, the project as it is
    {metrics: [...]} Nothing runs: the values are recorded as the reference
    • metrics entries are {metric, value, stage}: a finite number; stage defaults to the deepest; the metric must be one that stage reports; each stage/metric pair once. Provided values supply no design and are never the decision.
    • only: true ends the run after pass 0 (a tool check without optimization).
    • Reuse: a successful baseline on record stands while the document's baseline: section is unchanged -- whatever else changes (the folder's files, the tools, Flux). To measure it again, the loop's Settings › Maintenance › Re-Evaluate with Rerun baseline ticked (or flux task run ... --rerun-baseline) makes the next start, and only it, run pass 0. A failed one is tried again at the next start. Baselines bypass the cache, estimates and cutoffs.
    • Baselines are references: drawn as gray lines, the base of relative values, never the decision or a search start. They are not inherited by sub-loops.

    Parts and sub-loops¶

    parts divides one artifact: parts: [decoder, encoder], a map of descriptions ({decoder: "the 8b10b decoder"}), or decompose (the orchestrator divides it, at most 8). Names are a letter, then letters, digits, _, -. Parts are drafted and checked one by one and joined in order, separated by a blank line.

    subtasks divides a problem into child loops: a list of folders beside the document (subtasks: [ops/recip, ops/exp]), inline documents (maps with an id), or decompose. Do not combine parts and subtasks.

    • A folder child has its own problem.yaml (no id; the folder names it), its record is <parent>/<child>, and it shares the parent's out/ and workbench/.
    • Inheritance: a child takes the parent's contract, language, flow (including checks, measurements and knowledge), objectives, skills, params and budget unless it says them; flow, budget and params merge key by key, the child's winning. Not inherited: statement (each child says its own), parts, subtasks, max_subtasks, baseline, and a parent's generate: {command}. orchestrate is one box (D1514): a child that says none inherits the parent's whole (who decides, policy, search, space, critic, thinking, effort; never seeds or scope), and a child that says its own has exactly that, with nothing of the parent's merged in.
    • Composition: a parent's generate: {command: "... {parts} {artifact}"} composes the children's decided designs into the whole once every child has decided (composition contract). Without it the parent composes nothing.
    • Give inherited skills as paths that resolve from the child too (or absolute ones), and write inline children in the long form ({by: flux}).
