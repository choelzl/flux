    Run, stop, resume¶

    Use this page after creating and configuring a loop. In the web app, the same actions are a loop's Start and Stop (Tour). Replace sums with your loop's folder. Commands use the active Flux environment.

    Check before running¶

    flux task check sums
flux task run sums --passes 1 --json sums/out/answer.json

    task check validates the document, lists the stages and required tools, and reports problems before a run: every file the document names must be in the folder (a missing one is listed with the key that names it and what the folder holds), and the golden model must run. It exits 2 when the document does not load (not a task:) and 1 when something is missing or refused (MISSING:, REFUSED:, or WILL NOT RUN: when a flux/fluxpreset command's words are refused by its own --help). Like a run, it runs in the sandbox; --no-sandbox checks on this machine. It is the same check an agent writing the problem runs before it ends its turn. It does not execute the candidate checks and measurements. A bounded first run checks the actual scripts and their output.

    A folder normally contains problem.yaml. Additional NAME.problem.yaml files describe alternate problems in the same folder and use separate records. When a folder contains several valid documents, specify the file explicitly for unattended runs:

    flux task run sums/small.problem.yaml --passes 1

    Runtime overrides¶

    Values in budget are persistent settings; command-line options override them for one run. Use flux task run --help for the complete command syntax.

    Option Effect
    --passes N Cap passes; default is budget.passes, or unlimited when omitted/zero
    --steps N, --repair N Override work per pass and repair attempts per draft
    --screen-only Stop every design at the first measurement stage
    --db FILE Use a different record
    --out FILE Choose where the feasible decision artifact is written
    --json FILE Write the answer and results as JSON
    --tui Open the terminal task, log, and results view
    --model NAME, --think, --num-predict N Choose a model, request reasoning, and bound output tokens
    --no-structured Disable schema-constrained model output
    --role ROLE=NAME Override a role; task check lists available choices
    --agent orchestrate plan Give the direct model orchestration and planning; all enables both (its tool calls are budget.tools, on by default)
    --plan FILE Follow a saved loop plan
    --tool-hops N, --hop-share F, --patience N Override model tool rounds, context share, and prototype patience
    --regenerate PART... Draft named parts afresh; all starts every part afresh
    --no-prototype, --no-patching Disable prototype work or edit-based repairs
    --skill DIR Add a skill directory; repeatable
    --replies FILE Supply scripted model replies, useful for repeatable experiments
    --rerun-baseline Measure the baseline (pass 0) again, though the document's baseline is unchanged
    --reevaluate At this start, after the baseline: check and measure again every design on the record (those Invalidate set aside, else every one), after a check or measurement changed; then the passes
    --reevaluate-of ID Check and measure again only the designs one invalidation took out (its id is in Results)
    --remeasure Measure again the designs a rejection asked for, then rest
    --no-sandbox Run on this machine, not in the sandbox (also FLUX_SANDBOX=0)

    Stop, resume, and keep experiments separate¶

    An unlimited run continues until you stop it. Limits and timeouts can end individual attempts or passes; a satisfied objective or a stalled search does not automatically end the run. Stop with Ctrl-C, q in the TUI, the browser's Stop action, or another terminal:

    flux stop sums/out/sums.db        # finish the current pass
flux stop sums/out/sums.db --now  # interrupt immediately

    Run the document again to reuse its record. Cached measurements can be reused; stage commands, the scripts they name, and params contribute to the cache identity. Changing the objective can reuse observations; changing the measurement changes what can be reused.

    For a separate experiment, use a fresh --db or a new folder name. Copying a folder's generated out/ and workbench/ also copies its history and agent files; leave them out for a fresh loop. In the browser, a stopped loop's Settings › Preferences › Reset or delete offers Reset, which asks what to keep. Reset removes generated data while retaining the source document and scripts.

    For a process that outlives the terminal:

    flux run -- flux task run sums
flux status sums/out/sums.db
flux attach sums/out/sums.db

    Upgrading older loops¶

    Flux never upgrades a document silently. flux task migrate FOLDER shows what would change in a loop's documents and --write saves them (the original kept as <file>.orig). A loop of sub-loops is migrated as a whole: every sub-loop's document is listed and written with the parent's, once the whole loop loads. A loop's task journal from an earlier version, the file Live reads, is converted once with flux task migrate FOLDER --journal EVENTS (the original kept as events.jsonl.orig.gz); on a server, Admin › Maintenance › Bring task journals up to date does it for every loop.

    Read the result and full output¶

    flux report sums/out/sums.db
flux log sums/out/sums.db

    The report shows measured designs, trade-offs, refusals, and the standing design. The chosen artifact is written under out/ only when a design meets the requirements. An estimated metric or a shallower screening result should not be read as a confirmed measurement.

    task run exit Meaning
    0 A measured design meets every requirement; the decision artifact is written
    3 Correct designs were measured, but none meets every requirement; the report shows the shortfall
    1 No design was measured, or the run could not start
    130 Interrupted

    In the web app, a loop's Live tab shows passes, tools, agent activity, and their output as a tree, a graph, a timeline, and a log. Its Start picker opens an older start; its tasks and conversations belong to that start. Files, logs, and results provide raw or fullscreen views. History is available while its files and records are retained; resetting a loop clears the generated history.

    Sandbox¶

    flux task check, flux task run and flux ask run inside a container, so neither an agent nor the document's own code (its commands, scripts, golden.py) can touch the rest of the machine. The engine is rootless Podman when installed, else Docker (FLUX_SANDBOX_ENGINE=podman|docker). Without either, these commands stop with the sandbox needs Podman or Docker.

    • It sees the host read-only: the system, /nix/store, Flux itself, the programs on PATH, and the loop's folder (inside, at /sandbox/<loop>/).
    • It writes only the loop's out/ and workbench/, the record's folder, and the loop's own cache under ~/.cache/flux/apps/. Scratch in /tmp is gone after the run.
    • Its home holds the agents' configuration and logins for Flux, not your own home: ~/.ssh, other repositories and the Docker socket are not there.
    • Network is the host's by default. FLUX_SANDBOX_ALLOW=host,domain,10.0.0.0/8 limits HTTP(S) to those destinations; add FLUX_SANDBOX_RAW_NETWORK=1 for direct TCP/UDP to them (needs nft on the host). Behind a proxy, HTTP_PROXY/HTTPS_PROXY/NO_PROXY pass in (both cases, with localhost added to NO_PROXY); an allowlist's hosts are reached through it. On a server, its admin sets it (Proxy).
    • Limits: FLUX_SANDBOX_MEMORY (e.g. 16g), FLUX_SANDBOX_CPUS, FLUX_SANDBOX_PIDS (default 4096), FLUX_SANDBOX_TMP_SIZE. On a server, its admin's defaults and maximums apply (Sandbox limits).
    • Off: --no-sandbox or FLUX_SANDBOX=0 runs on this machine as you. Use it only for code you trust, such as the first loop.

    User or system service¶

    scripts/install-service.py (from flux/) writes the units that keep flux serve running and restart it after a commit (flux-update.path).

    • User service (the default): ~/.config/systemd/user/, turned on with systemctl --user daemon-reload && systemctl --user enable --now flux.service flux-update.path. No root needed. It runs only while its user's systemd does: from their login to their last logout, unless root lets it linger (sudo loginctl enable-linger <user>). On Ubuntu, systemd-oomd watches every user@.service and, under memory pressure (50 % for 20 s), kills the user's cgroup that uses the most memory, often the server's with every loop it started; a user unit cannot lower its OOM score, and ManagedOOMPreference=avoid is honoured only on cgroups root owns.
    • System service (--system): run by root's systemd as the owner (User=, Group=; --user NAME), with the same Nix shell, ~/.config/flux/service.env, working folder, KillMode=process, Restart=always, and what only root can set: OOMScoreAdjust=-500 (--oom-score-adjust), ManagedOOMPreference=avoid, OOMPolicy=continue, MemoryLow= with --memory-low 2G. It starts at boot and is outside the user's user@.service. The loop runs it starts are in its cgroup and inherit its OOM score; a sandboxed run's container is Podman's own scope. Rootless Podman keeps its state in /run/user/<uid>: with sandboxed runs, also sudo loginctl enable-linger <user>.

    The script runs no sudo: --system writes the units to a folder (a temporary one, or --output DIR; --dry-run prints them) and prints the commands. To switch:

    python3 scripts/install-service.py --system -- --host 0.0.0.0 --port 8765
systemctl --user disable --now flux.service flux-update.path      # the user service gives up the port
sudo install -m 0644 -o root -g root /tmp/flux-system-units-*/flux* /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now flux.service flux-update.path

    Back: sudo systemctl disable --now flux.service flux-update.path, remove the three files from /etc/systemd/system/, sudo systemctl daemon-reload, then systemctl --user enable --now flux.service flux-update.path. Never both at once: they would fight over the port.

    The environment is built before the restart¶

    Every unit starts flux serve from a prepared environment: scripts/flux-env.sh run sources the dev shell built earlier, so a start runs no Nix evaluation or build and takes seconds. An update that pulls a new nixchip or nixpkgs (a change to flake.nix or flake.lock) builds its environment first, while the old server keeps serving, and the server restarts only once that build has finished. A failed build leaves the server running on the environment it has.

    • Kept where: FLUX_ENV_DIR, which is env/ beside the web data: ~/.local/share/flux/env for the user service and the owner's system service, /var/lib/flux/env for the service account. Each environment is dev-<key>, a Nix profile and so a GC root, with dev-<key>.rc, its nix print-dev-env. The key is the first 16 hex digits of the sha256 of flake.nix and flake.lock, the only two files the dev shell is made of: Flux's own Python is put on PYTHONPATH from the checkout (FLUX_ROOT) and is never part of the environment. current and previous (kept for a rollback) are the two environments kept; older ones are removed. status.json holds the last build's state, and build.log holds Nix's output.
    • A code-only change (same flake.nix and flake.lock) reuses current. Nothing is built, and the restart takes seconds.
    • The user service and the owner's system service: flux-update.path starts flux-update.service, a oneshot with no time limit, as the owner. It runs flux-env.sh prepare (the build, or nothing), and then systemctl try-restart flux.service. When the build fails, the restart never happens. journalctl --user -u flux-update.service shows the build, and Admin › Version shows its state. If the checkout moves again during a build, the newer environment is built too before the restart.
    • The service account: Admin › Version builds the update's environment before it moves the clone (Version).
    • The first start with no environment builds one once, as nix develop used to on every start. To build it ahead of time, run the command the installer prints (FLUX_ROOT=... FLUX_ENV_DIR=... sh scripts/flux-env.sh prepare), as the account the service runs as.

    The downtime that remains is the restart itself: the old server stops, the new one sources its environment and starts serving, a few seconds in all. Loops are not affected: a run outlives the server (KillMode=process) and keeps the code it started on (below).

    Running loops keep their code¶

    A loop's run imports Flux's Python as it goes (most of it only when first needed, passes later), and everything its agents' tools, step commands and sub-loops run is flux ... from the same code. So under the service units (FLUX_SERVICE; FLUX_PIN_CODE=1 for a server started by hand, FLUX_PIN_CODE=0 to turn it off) each start runs from its own copy of the commit the clone is at, not from the clone:

    • The copy: <cache>/code/<commit>/ (/var/cache/flux/code for the service account), a git archive of flux/ and skills/ with the flux wrappers of .nix-bin/, made once per commit (about 13 MB, a second) and shared by the starts on it. The run's PYTHONPATH, PATH, FLUX_ROOT and the sandbox's Nix flake name the copy, and the sandbox mounts it read-only where it mounted the clone. The run's log says it: "on Flux 1a2b3c4d (its own copy)".
    • Its environment: the run keeps the Nix environment the server ran on when it started (dev-<key>). Each start leaves a pin, <cache>/code/pins/<pid>.json and $FLUX_ENV_DIR/pins/<key>.<pid>, while its process lives: flux-env.sh never prunes an environment a running loop is in, and a copy is removed only once no run is on it and the clone has moved past it.
    • The clone with changes (tracked or untracked files under flux/ or skills/, as in the owner's checkout being edited) or no git: the start runs on the clone itself, as before, and says why. Admin › Version then holds an update until that run ends (an update with changes in the clone is refused anyway).

    An update or a rollback therefore goes at once while loops run: the clone moves, the server restarts, the running loops go on with their own code, and their next start uses the new one. A running loop's document is never rewritten under it: it is migrated (or, after a rollback, put back from .orig) when its run ends, by the server's sample each minute or just before its next start.

    To get this on an existing install, bring the checkout to a commit that has scripts/flux-env.sh, run the installer again with the same arguments, build the environment while the old server still serves, and then restart once:

    # user service
python3 scripts/install-service.py -- <serve args>
FLUX_ROOT=$PWD FLUX_ENV_DIR=~/.local/share/flux/env sh scripts/flux-env.sh prepare
systemctl --user daemon-reload && systemctl --user restart flux.service
# the owner's system service: the same prepare, then
python3 scripts/install-service.py --system --user <you> -- <serve args>
sudo install -m 0644 -o root -g root /tmp/flux-system-units-*/flux* /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl restart flux.service
# the service account: Admin › Version updates /opt/flux/src (restarting under the old unit, slowly, one last time), then
python3 scripts/install-service.py --system -- <serve args>
sudo -u flux -H env FLUX_ROOT=/opt/flux/src/flux FLUX_ENV_DIR=/var/lib/flux/env sh /opt/flux/src/flux/scripts/flux-env.sh prepare
sudo install -m 0644 -o root -g root /tmp/flux-system-units-*/flux.service /etc/systemd/system/flux.service
sudo systemctl daemon-reload && sudo systemctl restart flux.service

    If you skip the prepare, the first start under the new unit builds the environment once. Behind a proxy, give the account's prepare the variables in /etc/flux/service.env (below); the units read that file themselves.

    The owner's system service needs --user NAME (the account it runs as, from this checkout). Without it, --system sets up the service with its own account, described next.

    System service with its own account¶

    python3 scripts/install-service.py --system -- --host 0.0.0.0 --port 8765 sets up a service that runs neither as you nor from your checkout:

    What Where
    Account flux, a system user (--account)
    Code its own clone, /opt/flux/src (--src), of main from your checkout's origin (--origin, --branch)
    Web data /var/lib/flux/web (StateDirectory=flux; FLUX_DATA_HOME=/var/lib/flux)
    Sandbox home /var/lib/flux/home, the account's HOME, where its agents log in
    Caches /var/cache/flux (CacheDirectory=flux; FLUX_CACHE_HOME)
    Settings /etc/flux/service.env (EnvironmentFile=)

    Flux's code reads these folders from FLUX_DATA_HOME and FLUX_CACHE_HOME, else from $XDG_DATA_HOME/flux and $XDG_CACHE_HOME/flux; the dev shell's scratch too (FLUX_TMPDIR, unless set: /var/cache/flux/tmp). Only the installer names /var paths. The unit has the same OOM protection, KillMode=process and Restart=always, but no update watcher: updates go through Admin › Version, and the service restarts itself after one.

    The script runs no sudo. It says what is already there and what is missing (the account, its /etc/subuid and /etc/subgid entries, linger, the clone, the settings file). It writes three files to a folder (a temporary one, or --output DIR), and --dry-run prints them instead:

    • flux.service, the unit.
    • root-steps.sh, to run as sudo sh root-steps.sh. It creates the account, gives it sub-ids and linger (rootless Podman needs both), clones the code as the account, creates /etc/flux/service.env and installs the unit. Each step is skipped when it is already done. For an SSH origin it first makes the account a key and stops until that key is a read-only deploy key of the repository. For an HTTPS origin, see A private repository over HTTPS. Git never prompts there (GIT_TERMINAL_PROMPT=0), so a clone that needs a credential fails with git's error instead of waiting.
    • move-data.sh, run once with sudo sh move-data.sh. It copies your server's data (~/.local/share/flux/web) and caches into /var/lib/flux and /var/cache/flux, owned by the account, and then has flux web-move rewrite the old folders' paths in the copied records. It refuses while either server runs or when /var/lib/flux/web already holds data. The source is never changed or deleted. The agents' logins come across too: each web user's (in users/<name>/home) and the server's own sandbox home (~/.local/share/flux/home, merged into /var/lib/flux/home, the account's HOME, without replacing anything there). They are the files each agent keeps its login in (.codex/auth.json, .claude/.credentials.json, OpenCode's auth.json, and those Admin › Agents names for an added agent), owned by the account and still 0600. Your own git and host credentials are never copied: SSH keys (.ssh/), .git-credentials, .netrc, sockets, and any other credential file. Neither are your ~/.config/flux settings. --no-logins leaves the logins behind too.

    The order the script prints:

    systemctl --user disable --now flux.service flux-update.path   # as you: the old server gives up the port
sudo sh /tmp/flux-system-units-*/root-steps.sh
sudo sh /tmp/flux-system-units-*/move-data.sh                  # once
# only if a login didn't come across or has expired:
sudo -u flux -H sh -c 'cd /opt/flux/src/flux && nix develop --accept-flake-config --command codex login'
sudo systemctl enable --now flux.service

    The script says which agents' logins it found for the server and for each web user (by agent name; it never reads the files), and move-data.sh says which are in place after the copy. An agent whose login didn't come across, or has expired, is logged in as the account (codex login, claude setup-token, opencode auth login; the script prints each command), and a web user in that case logs in again in Account › Agents.

    Nix for the flux account¶

    The account runs the daemon's (multi-user) Nix, and the daemon decides two things from /etc/nix/nix.conf. The script reads both without root (nix config show, else nix show-config, else the file and what it includes, never your own ~/.config/nix) and says what they mean for the account:

    • May it use Nix? allowed-users must name it, a group of it, or *. If it lists a group (allowed-users = root @nix-users), root-steps.sh adds the account to the first one listed (usermod -aG nix-users flux), never to a group that gives more than Nix (wheel, sudo, admin, adm, root). If it lists only names, the script stops and prints the line to add:

      extra-allowed-users = flux

    • Does it get the binary cache? The flake's nixConfig names a cache (its substituters and keys are read from flake.nix). Nix uses it for an untrusted account only when the cache is in substituters or trusted-substituters and its key in trusted-public-keys. Otherwise OpenROAD and the other tools build from source, which takes hours. The script prints the lines to add, for example:

      extra-trusted-substituters = https://nixchip0.cachix.org
extra-trusted-public-keys = nixchip0.cachix.org-1:nT5gEHc4661JFHoDukEnF1NFQ0XvS0TE7P370HLm4Ng=

    • Can it reach the daemon's socket? This is decided by the files' modes, not by nix.conf. Debian's and Ubuntu's nix package (/usr/bin/nix) makes /nix/var/nix/daemon-socket root:nix-users 0750, so an account outside nix-users gets "getting status of /nix/var/nix/daemon-socket/socket: Permission denied" even when allowed-users = *. The script reads the folder's and the socket's group and mode. When only their group may reach them, root-steps.sh adds the account to that group (usermod -aG nix-users flux), never to root, wheel, sudo, admin or adm. When only such a group or only the owner may reach them, it stops and says so.

    The report also says which nix the service runs: /nix/var/nix/profiles/default/bin/nix when it is there, else the nix on your PATH (/usr/bin/nix with a distribution's package). It names Nix's version and warns when it is older than the flake needs (Nix 2.4, the first with flakes, for its flake.lock). It also says whether that nix is a client of the daemon. With no daemon socket, Nix is single-user, which cannot serve another account.

    After a change to nix.conf, run sudo systemctl restart nix-daemon and then root-steps.sh again. The script never edits nix.conf. Each time it runs it reads the settings again and tries Nix as the account: nix store info from Nix 2.19, nix store ping before it (an older Nix does not know store info), and the other one if the first fails. If both fail, it stops and prints both commands' errors. Listing flux in trusted-users would also do all of this, but a trusted user can do nearly what root can, so the script does not suggest it.

    A private repository over HTTPS¶

    With an HTTPS origin (--origin https://...), the account needs a credential for the clone and for Admin › Version's fetch. The report says whether the account has one for the origin's host and whether your ~/.git-credentials has a line for that host. It never shows a token. root-steps.sh first tries git ls-remote as the account, which needs nothing for a public repository. If that fails:

    • It copies only your ~/.git-credentials line or lines for the origin's host into the account's /var/lib/flux/home/.git-credentials (0600, owned by flux) and sets credential.helper store in its ~/.gitconfig. Lines for other hosts are never copied.

    • With --no-git-credentials, or when you have no line for the host, it copies nothing. It prints the steps and stops. To store a token as the account, typed so it stays out of the shell's history:

      sudo -u flux -H bash -c 'read -rsp "Token for github.com: " t; echo; git config --global credential.helper store; printf "protocol=https\nhost=github.com\nusername=x-access-token\npassword=%s\n\n" "$t" | git credential approve'

    Use a token of its own rather than a broader personal one: a fine-grained token for this repository only, with Contents: read-only. The server's fetch uses the same stored credential and never prompts either.

    Behind a proxy¶

    A systemd service gets none of your shell's variables, so behind a proxy its first start times out fetching the flake's inputs from GitHub. The report lists your http_proxy, https_proxy, all_proxy and no_proxy (in either case) by name and the proxy's host:port only. A user and password in a proxy URL are never shown. The report also says whether nix-daemon has a proxy. root-steps.sh then:

    • writes them into /etc/flux/service.env, each only if that file does not set it already. A proxy URL with a user and password is never written into the script; it names it for you to add by hand. With --no-proxy-env it writes nothing and prints the lines instead.

    • prints, when nix-daemon has no proxy, the lines for its binary cache downloads. It never edits the daemon itself:

      sudo systemctl edit nix-daemon    # add:
[Service]
Environment=https_proxy=http://proxy.example:3128
sudo systemctl restart nix-daemon

    • tries each GitHub input of flake.lock as the account, with those variables (curl, 15 s). A timeout points to a proxy it lacks. A 404 means a private input: Nix needs a token in the account's own ~/.config/nix/nix.conf (access-tokens = github.com=<token>), and the step prints how to store one without it landing in the shell's history.

    The copied loops' paths¶

    A server's records name its folders by their full paths: each start's record and log, the folder each campaign traced into (in the cache), a loop's source, the usage log's transcripts, and a design's trace folder in the loop's own record. move-data.sh's last step, flux web-move, says each of them under /var/lib/flux and /var/cache/flux. Without --write it only counts, per file and table:

      flux-web.db: runs 40, usage_turns 156, usage_rate 142, usage_files 5, usage_loops 7
  users/cedric/apps/nlu/out/nlu.db: trials 231
  users/cedric/apps/nlu/out/nlu.db.runs.json: paths

    Logs, journals, transcripts and other free text stay as written: they are history.

    The server reads a copied loop even when that step never ran (for example when its nix develop failed on the first try). A path that names a loop's folder (.../users/<owner>/apps/<loop>/...) or its cache (.../apps/<owner>.<loop>/...) under another root is read at the same place under the server's own folders, when the copy is there. The copy wins even when your old folders are still readable to the account. Two things still need the step: the usage log would read every transcript again at its new path and count those turns twice in Admin › Usage, and the record keeps naming the old folders. To run it afterwards, with the service stopped (dry run first, then the same with --write):

    sudo systemctl stop flux.service
sudo runuser -u flux -- env HOME=/var/lib/flux/home FLUX_DATA_HOME=/var/lib/flux \
  FLUX_CACHE_HOME=/var/cache/flux FLUX_ROOT=/opt/flux/src/flux \
  sh -c 'cd /opt/flux/src/flux && nix develop --accept-flake-config --command flux web-move \
    --from-data /home/you/.local/share/flux/web --from-cache /home/you/.cache/flux \
    --from-source /home/you/src/flux/flux'
sudo systemctl start flux.service

    --from-source is the folder of your own checkout's flake.nix. If the service ran on the copy before the step, it has already read the transcripts again at their new paths. The step then drops the rows of the old paths instead of moving them, so no turn is counted twice. A second run changes nothing.

    A loop's traces live in the cache (/var/cache/flux/apps/<owner>.<loop>/tmp/flux-traces). Without them, Results, the report and the designs still show, but the journal (Live, a start's journal) and the agents' turns do not. move-data.sh copies the whole cache except slots/.
