    Run, stop, resume¶

    Use this page after creating and configuring a loop. In the web app, the same actions are a loop's Start and Stop (Tour). Replace sums with your loop's folder. Commands use the active Flux environment.

    Check before running¶

    flux task check sums
flux task run sums --passes 1 --json sums/out/answer.json

    task check validates the document, lists the stages and required tools, and reports problems before a run: every file the document names must be in the folder (a missing one is listed with the key that names it and what the folder holds), and the golden model must run. It exits 2 when the document does not load (not a task:) and 1 when something is missing or refused (MISSING:, REFUSED:, or WILL NOT RUN: when a flux/fluxpreset command's words are refused by its own --help). Like a run, it runs in the sandbox; --no-sandbox checks on this machine. It does not execute the candidate checks and measurements. A bounded first run checks the actual scripts and their output.

    A folder normally contains problem.yaml. Additional NAME.problem.yaml files describe alternate problems in the same folder and use separate records. When a folder contains several valid documents, specify the file explicitly for unattended runs:

    flux task run sums/small.problem.yaml --passes 1

    Runtime overrides¶

    Values in budget are persistent settings; command-line options override them for one run. Use flux task run --help for the complete command syntax.

    Option Effect
    --passes N Stop after N passes (one design each, however many run at once); default is budget.passes, or until stopped when omitted/zero
    --tries-per-pass N, --repairs-per-design N Override budget.tries_per_pass and budget.repairs_per_design
    --db FILE Use a different record
    --out FILE Choose where the feasible decision artifact is written
    --json FILE Write the answer and results as JSON
    --tui Open the terminal task, log, and results view
    --model NAME, --think, --num-predict N Choose a model, request reasoning, and bound output tokens
    --role ROLE=NAME Override a role; task check lists available choices
    --agent orchestrate plan Give the direct model orchestration and planning; all enables both (its tool calls are budget.tools, on by default)
    --tool-hops N, --hop-share F, --patience N Override model tool rounds, context share, and prototype patience
    --no-prototype Disable prototype work
    --skill DIR Add a skill directory; repeatable
    --replies FILE Supply scripted model replies, useful for repeatable experiments
    --rerun-baseline Measure the baseline (pass 0) again, though the document's baseline is unchanged
    --reevaluate At this start, after the baseline: check and measure again every design on the record (those Invalidate set aside, else every one), after a check or measurement changed; then the passes
    --reevaluate-tabs accepted,failed With --reevaluate: only the designs of these Results tabs (accepted, rejected, failed, pending); all four, or none said, is every design
    --remeasure Measure again the designs a rejection asked for, then rest
    --no-sandbox Run on this machine, not in the sandbox (also FLUX_SANDBOX=0)

    Stop, resume, and keep experiments separate¶

    An unlimited run continues until you stop it. Limits and timeouts can end individual attempts or passes; a satisfied objective or a stalled search does not automatically end the run. Stop with Ctrl-C, q in the TUI, the browser's Stop action, or another terminal:

    flux stop sums/out/sums.db        # finish the current pass
flux stop sums/out/sums.db --now  # interrupt immediately

    Run the document again to continue its record; unchanged measurements are reused. One run a record at a time: while a loop runs, from the browser or a terminal, a second start of it (the other way too) is refused with not started: this loop's record (sums.db) is being run by pid N (...), naming the run that has it. While a terminal's run has it, the browser's Delete, Rename, Reset, Archive, Replace (import) and Set aside are refused the same way, and Stop says to stop that run where it runs. A run that was killed holds nothing. Changing the objective can reuse observations; changing the measurement changes what can be reused.

    A loop run as a trunk stops the same way. flux stop: its agents' turns end, the running branches finish, the designs waiting stay for the next start. --now: everything ends; the designs that were running are kept, and the next start runs them first, then the ones waiting, and its agents go on where they were. --passes N counts hand-ins there; the queue drains after the last.

    When a measurement still counts¶

    A measurement still counts (for the decision, the ranking, the best and the charts) until one of these changes for its stage: the measure command (its words; spacing, quoting and comments do not count), how its numbers are read (metrics / metrics_re, a dictionary's aggregate), its parameters (the document's params:, when the command takes {params}), its input files (the files and scripts the command uses), or its tools (the build of each program the stage runs or needs). Nothing else of the loop makes a measurement stale: not the prompt, other stages, the checks, objectives, cutoffs, agents and their settings, budgets, names, comments, or files no measurement reads (a README, notes).

    A change counts from when the loop judges it: at the loop's next start, or at once when the file is saved on the page (the configurator, the Files editor) and the loop is not running. A file edited elsewhere (a shell, an agent) is judged at the next start; until then every page and flux loop summary say the last judgement, and when it was made ("what counts was judged ... by ...").

    When a stage changes, its older measurements stop counting, but nothing is hidden: in Results they keep their numbers and their tab, muted, with a "measured before a change" mark; the decision, the pool, the best and every chart leave them out, as the loop does. The loop's Overview says so on top, in the card a failed start uses ("12 designs were measured before a change to how synth is measured (the measure command and input file a.txt)"), and the loop's owner or an editor chooses:

    • Accept as current: the measurements count again, at once, for the loop and every page (audited);
    • Leave as stale: they stay uncounted and the card is closed for that change; a later change shows the card again;
    • Re-measure: those designs are checked and measured again under today's setup: by the running loop before its next pass, else by a run of its own that starts at once.

    For a separate experiment, use a fresh --db or a new folder name. Copying a folder's generated out/ and workbench/ also copies its history and agent files; leave them out for a fresh loop. In the browser, a stopped loop's Settings › Preferences › Archive, reset or delete offers Reset, which asks what to keep. Reset removes generated data while retaining the source document and scripts.

    For a process that outlives the terminal:

    flux run -- flux task run sums
flux status sums/out/sums.db
flux attach sums/out/sums.db

    Upgrading older loops¶

    Flux never upgrades a document silently. flux task migrate FOLDER shows what would change in a loop's documents and --write saves them (the original kept as <file>.orig). This Flux reads documents from the format of Nov 12, 2026 on, and records from version 7 on: no document step is above that yet, so the command says every document of today current. A record of an older version, or a loop file of an older format, is refused saying the commit that still brings it up -- open the loop with Flux 9957e3728, run flux task migrate --write (and a start, or Compact and check, for its record) there, and export it again. A document saying a key of an older document is refused naming the key and Flux e7a0f9cba, which says what became of it.

    Moving a loop in one file¶

    flux loop export writes a loop as one .zip, as the web's Settings › Export does (see Export and import); flux loop import replaces a loop's contents from one, with the same checks:

    flux loop export sums --loop-only -o sums.loop.zip     # the document, files and library (hidden files too)
flux loop export ada/sums --full -o sums.full.zip      # and the record, workbench, answer, notes (a web loop: USER/LOOP)
flux loop import sums.full.zip --into other --dry-run  # every check, nothing replaced
flux loop import sums.loop.zip --into ada/sums --keep-results --json

    LOOP is a loop's folder or USER/LOOP of the web server's data (--data; then a running loop is refused and both are on the audit). Import keeps the loop's name and settings, migrates the file's documents up from the format of Nov 12, 2026 (an older file, a record in it older than version 7, or a newer file is refused, the older ones naming the Flux that brings them up), runs nothing of it, and leaves the loop as it was on any refusal. Exit 0 done, 1 refused, 2 the loop or the file is not there.

    Read the result and full output¶

    flux loop summary --loop sums/out/sums.db --html
flux log sums/out/sums.db

    The report shows measured designs, trade-offs, refusals, and the standing design. The chosen artifact is written under out/ only when a design meets the requirements. An estimated metric or a shallower screening result should not be read as a confirmed measurement.

    task run exit Meaning
    0 A measured design meets every requirement; the decision artifact is written
    3 Correct designs were measured, but none meets every requirement; the report shows the shortfall
    1 No design was measured, or the run could not start
    130 Interrupted

    In the web app, a loop's Live tab shows passes, tools, agent activity, and their output as a graph and a timeline. Its Start picker opens an older start; its tasks and conversations belong to that start. Files, logs, and results provide raw or fullscreen views. History is available while its files and records are retained; resetting a loop clears the generated history.

    Read a loop from a shell¶

    flux loop reads a loop's results back, one question a command, read-only, so a running loop is safe. Name the loop with --loop FOLDER (a folder, a document or a record file; default: the current folder); every command takes --json. The options are in the CLI reference.

    Command What it answers
    flux loop summary The loop's state: running or not, its last phase, the budget, how many at once, a trunk's queue, its stages and checks; the baseline, the best per objective and the standing pick, each against the baseline
    flux loop passes [--last N] Each pass: its direction and why, its decision; "checks changed at pass N" where the document's checks or stages changed
    flux loop notes The people's notes and the decisions' reasons
    flux loop results [--top N] [--stage S\|all] [--goals] The measured designs ranked by the loop's objectives, meeting or missing the goals
    flux loop tried [--failed] [--gate G] [--match TEXT] Every design tried: how far it got, its numbers or why it stopped; a draft a stop cut before it was handed in, "stopped before handed in"
    flux loop show NAME [--rows] One design whole: its pass, its idea, its gate check by check, each stage's numbers or error, what changed since it was judged; --rows: every row of it in order
    flux loop design NAME [--print] A design's files, written read-only to a folder of yours, one path a line
    flux loop compare A B ..., flux loop diff A [B] Designs side by side, metric by metric; two designs (or a design and a file) line by line, or one design against the design it was built from (else the baseline); --stat counts the lines
    flux loop stages Each stage: designs reached, passed, refused, running; how long its rows take
    flux loop events [--kind K] [--since 2h] The record's events; --since those after a time ago or an ISO time
    flux loop ideas [--top] The ideas notebook, the best-scored first, with each idea's evidence
    flux loop starred The designs people starred in Results

    A first look at a loop:

    flux loop summary --loop sums
flux loop results --top 5 --loop sums
flux loop tried --failed --loop sums
flux loop show '#6' --loop sums

    Sandbox¶

    flux task check, flux task run and flux ask run inside a container, so neither an agent nor the document's own code (its commands, scripts, golden.py) can touch the rest of the machine. The engine is rootless Podman when installed, else Docker (FLUX_SANDBOX_ENGINE=podman|docker). Without either, these commands stop with the sandbox needs Podman or Docker.

    • It sees the host read-only: the system, /nix/store, Flux itself, the programs on PATH, and the loop's folder.
    • It writes only the loop's out/ and workbench/ and the loop's own cache. Scratch is gone after the run, and a loop's Scratch /tmp size (Admin › Runtime › Sandbox, or the loop's Settings › Advanced) caps it on disk: write what must last under the loop's out/ or workbench/.
    • Its home holds the agents' configuration and logins for Flux, not your own home: ~/.ssh, other repositories and the Docker socket are not there.
    • Network is the host's by default. FLUX_SANDBOX_ALLOW=host,domain,10.0.0.0/8 limits HTTP(S) to those destinations; add FLUX_SANDBOX_RAW_NETWORK=1 for direct TCP/UDP to them (needs nft on the host). Behind a proxy, HTTP_PROXY/HTTPS_PROXY/NO_PROXY pass in; an allowlist's hosts are reached through it. On a server, its admin sets it (Proxy).
    • Limits: FLUX_SANDBOX_MEMORY in GB (e.g. 16), FLUX_SANDBOX_CPUS, FLUX_SANDBOX_PIDS (default 4096), FLUX_SANDBOX_TMP_SIZE in GB (e.g. 0.5). On a server, its admin's defaults and maximums apply (Sandbox limits), and the server stops the biggest loop before the machine runs out of memory (The memory guard).
    • Off: --no-sandbox or FLUX_SANDBOX=0 runs on this machine as you. Use it only for code you trust, such as the first loop.
    • Where Podman keeps its state: FLUX_SANDBOX_STORAGE names its storage and FLUX_SANDBOX_RUNTIME its runtime folder (by default /run/user/<uid>, else /tmp).

    When the sandbox cannot start¶

    A start that cannot reach the engine stops with what the engine said and what to do, for example the podman sandbox cannot start: .... Check that the command it names (podman ... info) answers as the account that runs Flux. Flux repairs Podman's own state by itself when no Flux container runs, and says so in the loop's log.

    To keep Podman's state in one place, let the account linger (sudo loginctl enable-linger <user>) before its first sandboxed run, or name a folder with FLUX_SANDBOX_RUNTIME (for a system service, in its environment file); keep that folder's path short, as Podman refuses long ones (the error says how long it may be). ... belongs to another account: remove the folder it names as root, or set FLUX_SANDBOX_RUNTIME to a folder of the account's.

    Compiling¶

    Checks, measurements and an agent's probes often build C or C++ (a Verilator testbench, a simulator, a benchmark). Flux sets three things for every tool it runs, in the sandbox or not, and its built-in checks and measurements use them:

    • Flux clears MAKEFLAGS. A -j inherited from your shell's profile (MAKEFLAGS=-j32) would make Verilator's own make build one file at a time. Never put -j in MAKEFLAGS in a script.
    • Use FLUX_JOBS for a build's parallelism: make -j"$FLUX_JOBS", verilator --build-jobs "$FLUX_JOBS", cmake --build . -j "$FLUX_JOBS", ninja -j "$FLUX_JOBS". For a check or a measurement it is the cores of its resource hint (needs: {cores: 8}), never above the sandbox's CPU limit; with no cores said, and for a tool run outside them, it is the machine's cores shared among the loop's tool slots (cores ÷ tools_at_once, at least 1).
    • ccache is on. Each user has a cache of their own (ccache/<user> in Flux's cache folder, at most 10 GB), shared by all of that user's loops and runs, so a design built again, or the same files in another design's folder, compile in a fraction of the time. No user's run can read or write another user's cache: a shared one would let a run plant a compiled file that another user's build then uses. Each user's first builds fill their own cache. Verilator's builds use it on their own. Another build uses it with CC="ccache gcc" CXX="ccache g++", or with PATH="$FLUX_CCACHE_BIN:$PATH", where gcc, g++, cc, c++, clang and clang++ go through ccache. A build that does neither is not cached. The tool's step in Live says the run's ccache hits and misses; Admin › Activity › Resources says each user's cache's size.

    The built-in checks and measurements build with FLUX_JOBS and through your ccache on their own, and within a pass the steps of one design share what they built: rtl measure --stage place after --stage synth at the same clock and settings continues from the synthesised floorplan, rtl power, energy, path and breakdown read a stage already made, and rtl cycles, power and energy run the model the golden test built. To benefit, measure a design's stages at the same --clock-ps. Nothing is shared with another design, loop or user, and none of it changes a number, a verdict or a netlist.

    System service¶

    A server for a team runs as a system service, set up by one command, as root, from flux/:

    sudo python3 scripts/install-service.py -- --host 0.0.0.0 --port 8765

    Options for flux serve go after --. The service runs neither as you nor from your checkout:

    What Where
    Account flux, a system user (--account)
    Code its own clone, /opt/flux/src (--src), of main from your checkout's origin (--origin, --branch)
    Web data /var/lib/flux/web
    Sandbox home /var/lib/flux/home, the account's HOME, where its agents log in
    Caches /var/cache/flux
    Settings /etc/flux/service.env, one NAME=value a line

    In order, the command makes the account, lets it use Nix (below), gives it sub-ids and linger (rootless Podman needs both), lets Podman limit its jobs (below), clones the code as the account, creates /etc/flux/service.env (with your proxy settings, below), installs the unit, builds the environment, makes the first admin account when there is none (it asks for a password), and turns the service on. Each step is skipped when it is already done, so it can run again after a fix. For an SSH origin it first makes the account a key and stops until that key is a read-only deploy key of the repository. For an HTTPS origin, see A private repository over HTTPS.

    --dry-run needs no root: it says what is there and what is missing, and prints the unit and every step, writing nothing. The service is protected from the out-of-memory killers (--oom-score-adjust, default -500; --memory-low 2G keeps memory for it) and starts at boot. journalctl -u flux.service -f shows it.

    At the end the command prints how each agent logs in as the account (codex login, claude setup-token, opencode auth login); a web user logs in in Account › Agents.

    A flux serve started by hand is for development only.

    The environment is built before the restart¶

    Updates go through Admin › Server › Version. An update that changes Flux's toolchain builds its new environment first, while the old server keeps serving, and the server restarts only once that build has finished; a failed build leaves the server running as it was. A code-only update restarts in seconds. Admin › Server › Version shows the build's state.

    Updates never stop running loops: they finish on the version they started on, and their next start uses the new one.

    Host commands as the flux account¶

    flux web-loop and flux web-agent (from the server's machine) must run as the flux account, in the service's prepared environment:

    sudo -u flux -H env -C / FLUX_DATA_HOME=/var/lib/flux sh /opt/flux/src/flux/scripts/flux-env.sh run flux web-agent test

    Run as yourself, they say "permission denied on …" and print this command.

    Nix for the flux account¶

    The account runs the daemon's (multi-user) Nix, and the daemon decides two things from /etc/nix/nix.conf. The installer reads both (nix config show, else nix show-config, else the file and what it includes, never your own ~/.config/nix) and sets what is missing itself:

    • May it use Nix? allowed-users must name it, a group of it, or *. When it does not, the installer adds flux to it (your entries kept).

    • Does it get the binary caches? The flake's nixConfig names a cache (its substituters and keys are read from flake.nix). Nix uses it for an untrusted account only when the cache is in substituters or trusted-substituters and its key in trusted-public-keys. Otherwise OpenROAD and the other tools build from source, which takes hours. The installer adds what is missing, for example:

      # Flux: the account that runs Flux and the binary caches its tools come from (written by its installer)
extra-allowed-users = flux
extra-substituters = https://nixchip0.cachix.org
extra-trusted-substituters = https://nixchip0.cachix.org
extra-trusted-public-keys = nixchip0.cachix.org-1:nT5gEHc4661JFHoDukEnF1NFQ0XvS0TE7P370HLm4Ng=
# end of Flux

      It writes this block to /etc/nix/nix.custom.conf when nix.conf includes that file (the Determinate installer's), else to the end of nix.conf, after copying the file once to nix.conf.before-flux. Lines you added yourself are found and left alone. After a change it runs systemctl restart nix-daemon and checks, as the account, that Nix now shows the values. On NixOS (nix.conf made by the system's configuration) it prints the nix.settings to add and stops. With FLUX_INSTALL_BUILD=1 it leaves the caches alone.

    • Can it reach the daemon's socket? This is decided by the files' modes, not by nix.conf. Debian's and Ubuntu's nix package (/usr/bin/nix) makes /nix/var/nix/daemon-socket root:nix-users 0750, so an account outside nix-users gets "getting status of /nix/var/nix/daemon-socket/socket: Permission denied" even when allowed-users = *. The installer reads the folder's and the socket's group and mode. When only their group may reach them, it adds the account to that group (usermod -aG nix-users flux), never to root, wheel, sudo, admin or adm. When only such a group or only the owner may reach them, it stops and says so.

    The report also says which nix the service runs: /nix/var/nix/profiles/default/bin/nix when it is there, else the nix on your PATH (/usr/bin/nix with a distribution's package). It names Nix's version and warns when it is older than the flake needs (Nix 2.4, the first with flakes, for its flake.lock). It also says whether that nix is a client of the daemon. With no daemon socket, Nix is single-user, which cannot serve another account.

    Each time it runs, the installer reads the settings again and tries Nix as the account: nix store info from Nix 2.19, nix store ping before it (an older Nix does not know store info), and the other one if the first fails. A daemon that closes the connection ("Connection reset by peer": it has not read its settings since they let the account in) is restarted once. If both still fail, it stops and prints both commands' errors. Listing flux in trusted-users would also do all of this, but a trusted user can do nearly what root can, so the installer never does it.

    cgroup delegation for the flux account¶

    Rootless Podman limits a job's CPU, memory and processes inside the account's systemd user manager (user@<uid>.service). It can do that only when systemd hands the manager the cpu, memory and pids controllers. The host must use cgroup v2. On an older host that still uses cgroup v1 or the hybrid mode, the installer stops and says to boot with systemd.unified_cgroup_hierarchy=1. It never switches the mode itself.

    When the account's manager lacks one of those controllers, the installer:

    1. Writes /etc/systemd/system/user@.service.d/delegate.conf:

      [Service]
Delegate=cpu cpuset io memory pids

      It leaves your files alone when one of them, or systemd's own default, already delegates them. A delegate.conf of yours that delegates too little is first copied to delegate.conf.before-flux. 2. Runs systemctl daemon-reload. 3. Restarts the account's manager, and no other user's, when nothing of the account's runs under it. If something is still running there, it stops instead and asks you to restart user@<uid>.service once that has finished, or to reboot. Then run the installer again. 4. Checks that the manager now has the controllers.

    When the controllers are already there, it changes nothing and prints nothing.

    A private repository over HTTPS¶

    With an HTTPS origin (--origin https://...), the account needs a credential for the clone and for Admin › Server › Version's fetch. The report says whether the account has one for the origin's host and whether your ~/.git-credentials has a line for that host. It never shows a token. The installer first tries git ls-remote as the account, which needs nothing for a public repository. If that fails:

    • It copies only your ~/.git-credentials line or lines for the origin's host into the account's /var/lib/flux/home/.git-credentials (0600, owned by flux) and sets credential.helper store in its ~/.gitconfig. Lines for other hosts are never copied.

    • With --no-git-credentials, or when you have no line for the host, it copies nothing. It prints the steps and stops. To store a token as the account, typed so it stays out of the shell's history:

      sudo -u flux -H bash -c 'read -rsp "Token for github.com: " t; echo; git config --global credential.helper store; printf "protocol=https\nhost=github.com\nusername=x-access-token\npassword=%s\n\n" "$t" | git credential approve'

    Use a token of its own rather than a broader personal one: a fine-grained token for this repository only, with Contents: read-only. The server's fetch uses the same stored credential and never prompts either.

    Behind a proxy¶

    A systemd service gets none of your shell's variables, so behind a proxy its first start times out fetching the flake's inputs from GitHub. The report lists your http_proxy, https_proxy, all_proxy and no_proxy (in either case) by name and the proxy's host:port only; under sudo, which keeps none of them, it reads them from the shell you ran sudo from. A user and password in a proxy URL are never shown. The report also says whether nix-daemon has a proxy. The installer then:

    • writes them into /etc/flux/service.env, each only if that file does not set it already. A proxy URL with a user and password is never written; it names it for you to add by hand. With --no-proxy-env it writes nothing and prints the lines instead.

    • prints, when nix-daemon has no proxy, the lines for its binary cache downloads. It never edits the daemon itself:

      sudo systemctl edit nix-daemon    # add:
[Service]
Environment=https_proxy=http://proxy.example:3128
sudo systemctl restart nix-daemon

    • tries each GitHub input of flake.lock as the account, with those variables (curl, 15 s). A timeout points to a proxy it lacks. A 404 means a private input: Nix needs a token in the account's own ~/.config/nix/nix.conf (access-tokens = github.com=<token>), and the step prints how to store one without it landing in the shell's history.

    Moving the server's data by hand¶

    Never copy the server's database (flux-web.db) alone while the server runs. Either copy the backup that Admin › Server › Maintenance › Compact and check saved (with backups kept over 0), or stop the server first (Backups and restore). The next start refuses a database with stray files beside it and says which to move aside.

    After copying a server's data to new folders by hand, run flux web-move with the service stopped, so the records name the new folders (a dry run first, then the same with --write):

    sudo systemctl stop flux.service
sudo runuser -u flux -- env HOME=/var/lib/flux/home FLUX_DATA_HOME=/var/lib/flux \
  FLUX_CACHE_HOME=/var/cache/flux FLUX_ROOT=/opt/flux/src/flux \
  sh -c 'cd /opt/flux/src/flux && nix develop --accept-flake-config --command flux web-move \
    --from-data /home/you/.local/share/flux/web --from-cache /home/you/.cache/flux \
    --from-source /home/you/src/flux/flux'
sudo systemctl start flux.service

    --from-source is the folder of your own checkout's flake.nix. A second run changes nothing.

    Where a loop's files are¶

    folder what is in it
    out/ the results: designs, measurements, decisions
    runs/ the log, the notes, the answer, the loop's conversations
    workbench/ the agents' notes and tools

    Everything else Flux writes for a loop is scratch, which the clean-ups may delete.
