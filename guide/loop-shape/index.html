    Search and agents¶

    A loop separates what to try next (flow.search) from how to make the design (flow.design). The gate and measurement stages establish the results. You can change the search or generator while keeping those checks, measurements, and objectives.

    The configurator's Graph draws the loop as a ring: Search (search) chooses what to try, Design (design) makes it, Check (check) and Measure (measure) establish the facts, and Choose (choose) decides. A failed check goes back to Design. The setup boxes beside the ring run before the passes or feed every prompt. Each key under flow: (and trunk:) is its box's name in the Graph; an older document's names (orchestrate, generate, test, select, feedback, and Search's search for params) still load, meaning the same.

    Search a space of settings¶

    Use a finite space when you can list meaningful choices. The generator and other commands receive those choices as placeholders:

    flow:
  search:
    params: sweep
    space:
      algorithm: [list_sieve, slice_sieve, odd_sieve]
      wheel: [0, 1]
    seeds:
      - {algorithm: list_sieve, wheel: 0}
  design: {run: "{python} {home}/render.py {artifact} {algorithm} {wheel}"}

    The seed is measured first; an omitted knob uses its first choice. The first seed is the home point. Order numeric choices meaningfully because local search uses that order.

    search How it chooses experiments
    sweep Enumerate distinct combinations; a useful baseline for a small space
    montecarlo Sample distinct random points
    gradient Follow measured improvements among nearby choices
    anneal Make local moves and sometimes accept worse points to escape a region
    genetic Evolve a population through selection and mutation
    pareto Explore trade-offs; requires at least two objectives
    by: flux beside the space, no search FluxAgent proposes legal points from the space and measured history; by: claude an agent does
    control Compare the home point with only some of the incumbent's knobs kept (keep: [...])
    phases Run several of these in order, each with its own options
    run Your own search script: search: {run: "...", timeout_s: 600} (contract)

    A pass carries what the search proposes, and each search decides how much that is:

    Search One pass carries It hears back
    sweep every point (batch_size for fewer) nothing: it reads no result
    montecarlo batch_size points, 8 unsaid nothing: it reads no result
    anneal one neighbour after each pass
    gradient a wave of moves from the incumbent: all of them, or wave after each pass
    genetic a generation: population points, 8 unsaid after each pass
    pareto up to wave points after each pass
    by: flux beside the space batch_size points, 4 unsaid after each pass
    control one point
    phases what the phase at work proposes as that phase does
    run what the script prints in one round after each pass

    So --passes counts proposals, not points: a pass of a sweep over 48 points measures all 48, and one of a gradient a whole wave. budget.designs_at_once is how many of a pass's designs are made and checked at once. A search finishing its finite walk does not, by itself, stop an unlimited run. Use a pass cap for a bounded sweep.

    Within a pass, its designs climb the stages cheapest first. After each stage, every design past its cutoffs goes on to the next stage, so only the cutoffs save the costly runs (between stages).

    Designs checked again -- a rejected result's Measure again, a re-evaluation, a probed draft a person asked to Evaluate -- are the re-check, a pass of its own between two passes (R, numbered 1.5 after pass 1), never counted in budget.passes.

    Configure a search's own options under its name:

    flow:
  search:
    params:
      gradient: {steps: 16, patience: 2, reach: adjacent}
    space:
      block: [16, 32, 64, 128]
      order: [ijk, ikj, jki]

    The search reference lists each search's options and defaults. For a multi-phase search, keep the space and list the phases in order, each {search: ..., <its options>} (policy: beside a phase's search sets that phase's emphasis):

    flow:
  search:
    space: {block: [16, 32, 64, 128], order: [ijk, ikj, jki]}
    params:
      - {search: montecarlo, name: sample, samples: 8, seed: 0}
      - {search: gradient, name: tune, knobs: [block], steps: 8, policy: tune}

    Conditional choices and components¶

    Avoid measuring a knob that has no effect on a chosen algorithm:

    space:
  algorithm: [list_sieve, slice_sieve, odd_sieve]
  wheel: {values: [0, 1], when: {algorithm: [list_sieve]}}

    This is the space inside flow.search. Inactive choices sit at their home values and are not repeatedly measured as different designs. A nested component groups its knobs:

    space:
  prefetch:
    optional: true
    distance: [1, 2, 4]
    degree: [1, 2]

    The search sees prefetch.on, prefetch.distance, and prefetch.degree. {point} provides these as nested JSON to a generator. A choice can also use from: "out/invented/*.sv" beside values to include filenames discovered when the document loads.

    Let a model or agent explore designs¶

    A model or agent can write designs without a predefined knob space. Say who decides what to try next (by; unset, the rules) and the policy (policy) in flow.search; who writes the code is flow.design, set apart:

    flow:
  search: {by: claude, policy: adaptive}
  design: claude

    policy sets the search's emphasis: adaptive (the default), explore, improve, tune, finetune or variations. search picks an algorithm over a space (and decides alone; by beside it has no effect). Prefer search: sweep for enumerating knob combinations. gradient is coordinate descent over discrete choices, rather than derivatives; pareto explores trade-offs across the first two objectives. Without a space, these walks do not run.

    In the configurator, the whole search is the Search box on the Graph: its Policy, then its Parameters fold, closed until a parameter or a search is set: the parameters to vary (each a name and its values) and, once there is one, Search by (an algorithm, or AI: FluxAgent or an agent, picked under it).

    A finite budget or manual stop controls the run; reaching a goal or keeping the same incumbent does not stop an unlimited run.

    Put agents in the right steps¶

    Name an installed agent directly, and use {by: ..., ...} only when adding options:

    flow:
  search: {by: claude, policy: adaptive}
  plan: {by: claude, session: pass}
  design: {by: claude, timeout_s: 1800, probe: {gate: 20, stages: 3}}
  choose: {by: claude}
  knowledge: {by: claude, insights: {by: rules}}

    claude, codex, and opencode are built in; a server can offer additional named agents. They can plan, generate, and advise decisions. flow.check and flow.measure remain commands: an agent cannot replace their factual results. Selection still uses the objectives; an agent's advice is checked and can fall back to the rules.

    A critic is a second opinion on one box: critic: under search (the direction picked for a pass), check (a design the checks passed), measure (a stage's numbers) or choose (the pick). It is flux (FluxAgent), an agent, or {by: ..., rounds: N}. A rejection is a verdict: the direction is picked again, the design fails, the numbers are marked, or the pick is made again without it.

    flow:
  check:
    correctness: "{python} {home}/check.py {artifact}"
    critic: claude
  choose: {critic: {by: flux, rounds: 2}}

    See critics for each box's rules.

    An agent keeps one session per pass, unsaid: on design one until the design is admitted, its repairs and send-backs going on in it -- begun as a warm start unsaid; on a decision step such as plan or a critic one for that step's turns in the pass (session: pass), each critic its own. session: keep keeps it across passes (below). The papers' digest, the workbench and the ideas have no session: each of their turns stands alone.

    Several Design agents¶

    Design may list coding agents, the way a trunk does: each pass's design is made by the next agent in turn -- pass 1 by the first, pass 2 by the second, and round again.

    flow:
  design:
    by:
      - claude
      - {by: codex, model: gpt-5-codex, effort: high}
      - {by: opencode, model: anthropic/claude-sonnet-4-5}
    timeout_s: 900
    • Each entry is an agent's name, or {by: <agent>, ...its own options}; its model is its model:, as one agent's is (design: {by: codex, model: gpt-5-codex}). The older args: [--model, <model>] still works. Design's own options (timeout_s, session, probe, ...) are every agent's; an entry's own options win for that agent.
    • Designs at once. With budget.designs_at_once, a pass that starts takes the agent whose turn it is, so the agents keep taking turns whichever design ends first. The turn follows the pass's number, also across a stop and a start.
    • A design stays with its agent. Its repairs, the turns that continue it after a time-out and its last turn are the same agent's.
    • Sessions are each agent's own. Each agent has its own warm start, and with session: keep its own kept sessions, one per design at once: an agent never resumes another's session.
    • The prototype (design.prototype) is written by the first agent of the list.
    • Refused: an empty list, the same agent with the same options twice (give it another model or options of its own, or drop it), and FluxAgent in the list (by: flux designs alone).
    • Where it shows. The Agents tab and Live's Timeline name the agent of each turn; Results tags each design with the agent that made it (and its model) once the loop has designs by two or more.
    • In the configurator, Configure › Graph › Design: Add an agent, then a tab per agent, named by the agent and its model; each tab holds that agent's settings and, past the first, its remove. One agent alone is written as before (design: claude).

    Warm starts¶

    Unsaid, a design by Claude Code, Codex or OpenCode starts warm (session: seeded): before the first design the agent spends one turn reading the loop's folder, its scripts, the checks, the stages and its tools, and designs nothing. Each design's session then starts from where that one ended, with its own whole brief, so it does not read all that again. Designs never see each other's work this way: what each reads of earlier designs, results and ideas, it reads itself, as they stand when it starts.

    flow:
  design: {by: claude}                        # warm starts (the default)
  design: {by: claude, session: fresh}        # every design's session starts from nothing
  design: {by: claude, seed_timeout_s: 1800}     # warm starts, that first turn at most 30 minutes

    • That first turn has up to an hour (seed_timeout_s, in seconds: 300 to 10800, that is 5 minutes to 3 hours) to study the loop: it reads the scripts, runs the help of the tools and commands they use and tries the build and check commands' help or dry runs, writing only in its own folder. It ends as soon as it has summed up what it learned, so the limit is a cap. It is its own: the agent's time limit, the turns that may time out and the last turn are the designs'. If it runs past its limit, the designs start from nothing. Changing it does not make that first session again. Refused beside session: fresh or keep, and on any other box.

    • The shared first session is made again when the problem document, the loop's files, the agent or its model change, after 24 designs, and after 12 hours.

    • With several designs at once, one is made and the others wait for it, at most 10 minutes. A design that cannot wait that long starts from nothing; only the designs that start while it is being made do, and every later one starts warm.
    • If it cannot be made or a design cannot start from it, that design starts from nothing; the Agents tab says why.
    • FluxAgent and an agent of your own (run:) always start from nothing. Trunks keep their own sessions.
    • Live's Timeline shows that first turn on the Setup row; the Agents tab marks each design that started warm.

    Sessions kept across passes¶

    Off unless said. session: keep on any box an agent works, or a critic, keeps the agent's sessions from pass to pass, so it goes on in the conversation it had -- the files it read, what it worked out -- instead of reading the problem again each pass:

    flow:
  design: {by: codex, session: keep}            # a new session after 8 turns
  plan: {by: claude, session: keep, turns: 4}
  search: {by: claude, session: keep, turns: forever}        # never renewed for its turns
    • turns: N (8 unsaid) starts a new session after N turns; turns: forever never renews it for its turns. A change to the problem document, the agent, its model or Flux starts a new one too.
    • One session per design at once (budget.designs_at_once).
    • An agent of your own keeps its session only when it declares a resume command (agent options); without one it starts a new session every pass, and flux task check says so.
    • The Agents tab says whether each turn resumed its session or started a new one.

    Agents can check their current file against the loop's gate and stages during a turn (a probe). probe budgets those checks per turn. Direct use of certain raw tools is restricted by default; allow can give specific tools back when that suits the task. See agent options.

    Probed drafts are kept, unverified. Drafts an agent probed but did not hand in are listed as unverified, named by the pass they were probed in and their try there (#p4.1, #p4.2 ...). They never count -- not in a frontier, a standing, a chart, a decision or an idea's evidence. Evaluate (Results, or flux loop evaluate p4.2) has the loop's next re-check check and measure one as a design of its own.

    For FluxAgent, use search: {by: flux, policy: adaptive} and design: flux (model, its old name, is refused: the check says to write flux). Models and agents explains endpoint and agent setup.

    Two ways to run: passes or a trunk¶

    A document runs its loop one of two ways, and the root key says which: flow: runs passes, trunk: runs a trunk. Both are complete ways to run a loop; pick by how the designs are made.

    • Passes (flow:): each pass makes one design -- a search picks a point, a script, FluxAgent or an agent writes it -- then checks, measures and decides it; a failed check goes back to Design for a repair, and the next pass starts from what was learned. Choose passes for a search over a space, a scripted generator, a plan, FluxAgent's drafts, or an agent you want to steer pass by pass (designs_at_once runs several passes side by side, budget.pipeline starts the next design once the current one passed Check; several Design agents take turns).
    • Trunk (trunk:): a coding agent keeps one session for the whole run and hands in one design a turn; branches check, measure and decide each one meanwhile, so neither waits for the other. Choose a trunk when a coding agent is the designer and you want it to keep going on its own, with several agents or models at once if you like.

    Everything else -- checks, measurement stages, objectives, knowledge -- is written the same under either key. Say trunk: where the document says flow:, with the same contents:

    trunk:
  design: {by: [claude], timeout_s: 3600}     # a list: one trunk each (one agent is fine)
  check: {...}                                 # as under flow:
  measure: {...}
budget:
  designs_at_once: 3                          # branches at once (the admin's limit applies); twice that may wait
  passes: 0                                   # designs handed in; 0 = until stopped
    • The trunk. Each Design agent keeps one session for the whole run, resumed at the next start. A turn is one design: the agent hands it in (flux hand-in) and its turn ends; the next design is a new turn that resumes the same session, told what it handed in, what ended since and its probe budget, whole again for each design. The agent keeps its memory; its own compaction keeps the conversation bounded. A turn lasts design.timeout_s at most. A turn with no design is followed by the next at once: the run ends only when stopped. An agent with no resume: command starts each design in a new session, its brief pointing at flux loop tried --by for what it handed in before.
    • The branches. Up to budget.designs_at_once branches take the designs off the queue, first in first out (the agents in turn). A branch is a pass that runs Check, Measure's stages and Choose exactly as a pass does, with no Search, no Design and no repair. Each check and stage in it is bounded by its own timeout_s.
    • The queue. At most twice the branches that run designs wait: twice budget.designs_at_once, or twice the admin's limit when it is lower (each agent at most its share). Lowering designs_at_once keeps every design already waiting: the next start says when more wait than the queue now holds, and no hand-in is taken until fewer than the new limit wait.
    • Ideas work as they do in passes. Each turn of a trunk is told the idea queued in Results › Ideas to test next, else the best-scored idea not measured yet as a suggestion (ideas: {suggest: false} turns that off). A design handed in names the idea it tests, and its check and measurements become that idea's evidence; the agent can add ideas for later. The ideas cleanup runs once the notebook has grown, as it does before a pass.
    • Notes (Overview › Note to the loop) reach the trunk agents as they reach a pass's Design agent: a note reaches each agent at every turn while it stands -- every turn's message starts with the notes, the ones the agent has not seen yet marked (new), and a new session's brief with all of them. A removed note is gone from the next turn. When the notes are long, the newest are said and the agent reads the older ones with flux loop notes. The branches read them too, and the Notes card shows a note read once the loop has taken it, whoever took it.
    • Search is off by default under trunk:: the trunk agents decide what to try. Say search: flux (FluxAgent) or an agent (search: claude) and a Search bud writes new ideas to the notebook every 10 decided designs; it never picks a direction. The Graph's Search box then reads "bud · every 10". A bud is short: an agent's turn has 5 minutes and 15 commands; FluxAgent answers in one reply, reading the record with its tools for 5 rounds at most within the same 5 minutes.
    • Repairs are the agent's own: repairs_per_design does nothing under trunk:.
    • Refused under trunk:: a space or a search (a search script too), plan, a Design not by a coding agent, both flow: and trunk:. flux task check says what runs.
    • The prototype stage (design.prototype) does not run under trunk:, and flux task check warns.
    • The start is a loop of passes' start: the baseline when the document asks it, then the re-check (Re-Evaluate's designs, the re-measures a rejection asks), then the Setup and the trunks.
    • Written otherwise: a document that says flow: with design: {session: trunk} (an older form) is refused now: say trunk: in place of flow:, the same contents.
    • Setup runs once before the trunk starts. Run setup on Live runs it again; it also runs again when the library changes.
    • Several agents. Each agent of Design's list is a trunk of its own, tagged t1, t2, ... in the list's order. An agent of the list is its name or {by: <agent>, model: <model>}; Design's own options (timeout_s, session, ...) are every agent's. The same agent may appear twice with different models: two trunks.
    trunk:
  design: {by: [claude, {by: claude, model: opus}, codex], timeout_s: 3600}

    One loop, one design¶

    A loop answers one problem with one design. Several blocks of one IP are one design: say them in the statement and the contract, and bundle them under one top module, as the bundled nlu does. Several problems are several loops; a chart can draw them side by side.
